# Promotion Review — 晋升评审指南

本指南用于指导晋升评审报告的撰写。适用于以下场景：
- 收到员工晋升材料，需要输出评审意见
- 收到员工信息 + 绩效数据，需要判断晋升匹配度
- 只有员工的原始工作材料，需要从中提炼评价

## 意图识别

以下信号表明这是一个晋升评审任务：

| 信号 | 示例 |
|------|------|
| 明确提到"晋升评审/评审意见/晋升评价" | "帮我写一份晋升评审报告" |
| 提供晋升材料 + 候选人信息 | "这是张三的晋升文档，帮我评估一下" |
| 提到晋升层级（如 P6→P7） | "李四要 P7 升 P8，帮我看看" |
| 提供绩效数据要求评价 | "王五绩效 3.75/3.5+，帮我写评审" |
| 提到 JobModel 或岗位标准 | "对照 P7 JobModel 帮我评价" |

**意图确认后**，立即进入信息收集流程，不要等待更多指令。

## 信息收集

### 输入方式

用户通过提示词提供本地晋升材料文件路径（或目录），直接读取即可。不支持 URL 抓取，不执行脚本下载。

```
/p9 帮我评审一下这个同学的晋升材料 /path/to/晋升文档.md
/p9 帮我写一份晋升评审报告，材料在 ~/Downloads/张三晋升材料.pdf
```

### 姓名提取

按以下优先级尝试获取候选人姓名：

1. **提示词中已给出** — 用户直接说了"帮我评审张三的晋升材料"
2. **从文档中提取** — 读取晋升材料后，查找以下格式：
   - `姓名：XXX` 或 `姓名: XXX`
   - `花名：XXX` 或 `花名: XXX`
   - `Name: XXX`
   - `候选人：XXX`
   - 文档标题或前 5 行中的中文姓名（2-4 个汉字）
3. **询问用户** — 如果文档中也找不到，通过 `AskUserQuestion` 询问：
   ```
   AskUserQuestion(
     question="候选人姓名是？",
     options=[
       {label: "请在 Other 中输入", description: "输入候选人姓名（中文）"}
     ]
   )
   ```

### 晋升层级和绩效确认

从提示词和文档中提取晋升层级和绩效信息。**任何缺失的必要信息，都通过一次 `AskUserQuestion` 收集**：

```
AskUserQuestion(
  question="请确认候选人的晋升层级和绩效信息",
  header="基本信息",
  options=[
    {label: "P5→P6", description: "从 P5 晋升到 P6"},
    {label: "P6→P7", description: "从 P6 晋升到 P7"},
    {label: "P7→P8", description: "从 P7 晋升到 P8"},
    {label: "P8→P9", description: "从 P8 晋升到 P9"}
  ],
  questions=[
    {
      question: "候选人最近两次绩效分别是多少？（格式：前一次/最近一次，如 3.5+/3.75）",
      header: "绩效",
      options: [
        {label: "3.75/3.75", description: "连续高绩效"},
        {label: "3.5+/3.75", description: "连续高绩效"},
        {label: "3.5/3.75", description: "前一次未达 3.5+"},
        {label: "请在 Other 中输入", description: "格式：前一次/最近一次"}
      ],
      multiSelect: false
    }
  ]
)
```

如果提示词中已经给出了层级和绩效，跳过询问。

### 岗位方向

从文档内容推断（技术方案多为技术岗，产品规划多为产品岗）。不确定时询问：

```
AskUserQuestion(
  question="候选人的岗位方向是？",
  options=[
    {label: "前端", description: "前端工程师"},
    {label: "客户端", description: "客户端工程师（iOS/Android/鸿蒙）"},
    {label: "后端", description: "后端/服务端工程师"},
    {label: "产品", description: "产品经理"}
  ],
  multiSelect: false
)
```

### 信息优先级

1. **有晋升材料 + 绩效信息**：最理想，直接综合两方面输出评价
2. **只有晋升材料**：从材料中提取关键信息，基于材料内容输出评价
3. **信息有限**：基于框架做评价，明确标注信息不足的维度

## 分析框架

### 三维度评估模型

晋升评审的核心是判断候选人是否已在下一层级工作，而非在当前层级做得好。

**维度一：在下一层级运作（Operating at Next Level）**
- 不是"完成了下一层级的任务"，而是"以下一层级的思维方式和判断力运作"
- 关键问题：候选人是在执行分配的任务，还是在主动定义问题和方向？
- 证据要求：至少 2 个跨团队或跨域的影响案例

**维度二：不可替代的贡献（Irreplaceable Contribution）**
- 如果候选人离开，哪些能力/系统/关系会断裂？
- 关键问题：候选人的贡献是否可以被同层级其他人替代？
- 证据要求：具体的系统/能力/方法论，而非"态度好"、"努力"

**维度三：成长轨迹（Growth Trajectory）**
- 不是"在当前层级持续优秀"，而是"展现出向更高层级跃迁的趋势"
- 关键问题：半年前和现在的表现有质变吗？
- 证据要求：不同时期的对比证据

### 岗位标准对照

根据候选人岗位方向，读取对应 JobModel 参考文件：

| 岗位方向 | 参考文件 | 备注 |
|----------|----------|------|
| 产品 | [产品岗 JobModel](jobmodels/promotion-jobmodel-product.md) | 内置完整 JobModel |
| 前端 / 客户端 / 后端 | 参照下方通用技术岗标准 | 详细 PDF 标准见 promotion 项目 |

**技术岗通用层级标准**（适用于前端、客户端、后端等技术方向）：

| 层级 | 核心要求 |
|------|----------|
| **P5→P6** | 独立完成模块级任务，代码质量稳定，开始参与技术方案讨论 |
| **P6→P7** | 主导端到端完整解决方案，技术创新取得显著结果；参与业务规划，协同上下游发起专项并完成里程碑交付；技术突破在跨业务场景可复用 |
| **P7→P8** | 主导跨域技术架构演进，在 BU 层面形成技术影响力；系统性解决关键问题，方案为他人复用；参与业务决策，推动"技术赢"到"业务赢" |

> 如需更详细的前端/客户端岗位晋升标准 PDF 和终端研发 JobModel xlsx，参考 `references/jobmodels/` 目录下对应文件。

**AI 能力评估**（技术岗必须包含）：
- 参考文件：[AI 能力专项评估模板](promotion-ai-coding-assessment.md)

## 报告结构

生成的晋升评审报告必须包含以下章节。完整模板见 [promotion-report-template](promotion-report-template.md)，直接复制模板填写即可。报告保存到 `review_files/{name}/report.md`。

**章节清单**：
1. **基本信息** — 晋升方向、绩效、门槛判断
2. **技术方向** — 候选人技术领域概述（1-2 句）
3. **量化指标** — 性能/效率/业务等可衡量数据
4. **做的好的** — 2-4 条，每条：具体项目 + JobModel 引用 + 价值判断
5. **有待提升的** — 1-3 条，每条：短板 + JobModel 引用 + 改进方向
6. **综合判断** — 初步判断 + 匹配点(2-3条) + 差距(1-2条) + 保守措辞建议
7. **AI Coding 专项评估**（技术岗必须）— 4 维度评估 + 层级对照 + 改进建议

### 综合判断措辞规范

**重要原则**：避免给出明确的是否建议晋升的结论。

| 措辞 | 是否可用 |
|------|----------|
| "可以考虑晋升，但风险是 XXX" | ✅ 推荐 |
| "候选人基本具备晋升条件，但需要在 XXX 方面继续加强" | ✅ 可用 |
| "建议晋升" | ❌ 过于明确 |
| "不建议晋升" | ❌ 过于绝对 |
| "强烈推荐晋升" | ❌ 避免 |

**原因**：晋升决策涉及多种因素（名额、组织需要、时机等），评审意见应提供判断依据而非替代决策。

## 报告编写风格

参考 [历史评价范例](promotion-evaluate-examples.md)，遵循以下原则：

### 语言风格

- **简练直接**：言简意赅，避免泛泛而谈。每条评价 2-4 句话
- **具体举例**：必须结合候选人的具体项目和技术点，不写空话
- **关联 JobModel**：明确引用层级要求（如 "P7 要求 '参与业务规划...'"）
- **有温度**：适度加入感性评价词汇（如 "实属不易"、"非常难得"、"值得肯定"）

### 评价结构（每条）

```
{具体事实描述}。{关联 JobModel 要求的分析}。{价值判断}。
```

示例：
> 张三长期在酒店客户端团队持续打磨端体验，初步做到了 App 酒店交易链路的秒出，可交互时间降低至 0.7s 以内，主导设计沉淀了可复用的优化方案 performanceKit。很好地符合 P7 对"主导端到端完整解决方案，通过技术上的创新取得显著结果"的要求。

> 完整的简评写作公式、候选人画像类型学、常见改进方向模式，见 [promotion-report-template](promotion-report-template.md)（简评撰写指南章节）。
> 按画像分类的 15 个真实简评范例，见 [promotion-evaluate-examples](promotion-evaluate-examples.md)。

### 待提升部分的结构

```
{短板描述}。{引用 JobModel 对应要求}。{改进方向建议}。
```

示例：
> 提升表达能力，不要太腼腆，要敢于发起对话，合理应对组内与业务搭档之间沟通协作问题。从 P7 层级对于"主动协同上下游组织发起专项并完成里程碑交付"的要求来看，有一定的提升空间。

## 绩效门槛

### 连续高绩效定义

- **连续高绩效**：最近一次绩效 ≥ 3.75，且前一次绩效 ≥ 3.5+
  - ✅ 3.5+/3.75 — 算
  - ✅ 3.75/3.75 — 算
  - ✅ 3.75/3.5+ — 算
  - ❌ 3.5/3.75 — **不算**（前一次 3.5 未达到 3.5+）
  - ❌ 3.5/3.5 — 不算

### 门槛判断

- 连续高绩效在评审中有重要权重，但不是唯一条件
- 如果绩效不满足连续高绩效，需要在报告中明确指出，并说明对晋升的影响
- 绩效信息缺失时，标注"绩效信息未提供"，不做假设

## 特殊情况处理

### 信息不足时

如果只有员工的原始材料（无绩效、无明确晋升层级），报告应：
1. 在"基本信息"中标注缺失项
2. 在分析中基于材料可推断的内容进行评价
3. 在"综合判断"中明确说明哪些维度因信息不足无法判断
4. 给出"建议补充 XXX 信息后再做完整评估"的建议

### 跨岗位评审

如果候选人的工作跨越多个岗位方向：
1. 以候选人主要岗位方向为主进行评审
2. 跨域贡献作为加分项在"做的好的"中体现
3. 不因跨域工作而降低主要方向的要求

### 绩效数据与材料不一致

如果提供的绩效数据与晋升材料中的描述不一致：
1. 以绩效数据为准进行门槛判断
2. 在报告中明确指出差异
3. 不做假设或调和

## 反模式

| 反模式 | 检测 | 修正 |
|--------|------|------|
| **空泛好评** | "该同学工作认真负责" 无具体事例 | 补充具体项目、数据、成果 |
| **层级错位** | 用当前层级的标准评价，而非目标层级 | 每条都对照目标层级 JobModel |
| **只说优点** | 有待提升部分敷衍或空缺 | 至少 1 条实质性改进建议 |
| **替代决策** | "建议晋升" / "不建议晋升" | 改为"可以考虑晋升，但风险是..." |
| **照搬材料** | 直接复述晋升文档内容 | 用自己的语言重新组织，加入评审视角 |
| **忽视 AI 评估** | 技术岗报告中无 AI Coding 专项 | 必须包含 AI 能力评估章节 |
