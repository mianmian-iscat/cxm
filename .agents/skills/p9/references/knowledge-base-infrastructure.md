# AI 时代工程师的知识库基建

> 本文件从 repo-bot 项目的实践中蒸馏而来。repo-bot 是一个本地代码知识库系统，为本地代码仓库提供四路检索 + RRF 融合 + AI 对话能力。这里提炼的不是代码实现，而是背后的方法论——AI 时代工程师该怎么管理自己的知识库，让 AI 真正在结构化证据上推理，而不是在散装片段上瞎猜。
>
> 本文件与以下文件互补：
> - `ai-era-viewpoints.md` — 观点二（60% 深水区）和观点三（三个闭环）提供了"为什么要做"的判断
> - `technical-leadership.md` — AI-Native 转型章节的飞轮 1（知识闭环）提供了组织视角
> - `directional-judgment.md` — AI 方案判断框架，可用于评估知识库方案

## 一）核心理念：知识库是 AI 协作的第一公民

### AI 的输出质量上限 = 你喂给它的证据质量上限

这句话我反复说，但很多人还是没听进去。

35 个 TL 访谈里，零个人说"模型能力不足"是瓶颈。所有瓶颈都指向同一个方向：闭环没跑通。其中知识闭环排在第一位——知识库质量参差不齐，有的写了 CLAUDE.md 但内容是空话，有的把架构文档、编码规范、业务上下文完整灌入。同样是 AI 编码，产出质量简直天上地下。

所以第一个判断是：**不是模型不行，是你喂给模型的东西不行。**

### 从"靠记忆 + grep"到"先建索引再提问"

传统工程师的知识管理是什么？收藏夹、笔记、grep 一把梭。遇到问题先搜浏览器历史，搜不到再 grep 代码库，grep 不到就拍脑袋。

AI 时代这个模式彻底不行了。因为 AI 不记得你上个月写过什么、上周改过什么、前天 review 过什么。它只能看到你此刻喂给它的东西。

所以范式转变是：**先建索引，再提问。** 不是遇到问题再找资料，而是平时就把知识库建好——代码仓库有结构索引，文档有语义索引，调用关系有图索引——然后让 AI 在索引上检索和推理。

### 知识库不是文档集合，是可检索、可推理的证据基础设施

很多人把"建知识库"理解为"把文档收集起来"。这是最大的误解。

文档集合的问题是：它只能被人阅读，不能被 AI 推理。AI 需要的不是文档，是**结构化的证据**——有来源、有置信度、有交叉验证的证据。

一个合格的知识库基建应当满足：
- **可检索**：多路检索路径，不同问题用不同的"眼睛"
- **可排序**：不同来源的证据能融合排序，给出最相关的结果
- **可验证**：每条证据都有来源和置信度，AI 能区分事实和猜测
- **可维护**：增量更新，不是每次全量重建

## 二）四路检索架构：不同问题需要不同的"眼睛"

这是 repo-bot 最核心的架构决策。不是用一种检索方式打天下，而是四路并行、各取所长。

### 精确检索（Zoekt / grep）

**适用场景**：关键词和正则匹配，函数名、类名、import 语句、字符串常量。

**优势**：确定性最高。搜 `ProxyServer` 就是搜 `ProxyServer`，不存在"语义相近但不是"的问题。

**局限**：只能搜你确切知道的东西。问"这段代码的逻辑是什么"搜不出来，因为你不知道关键词是什么。

**工程选择**：Sourcebot 基于 Zoekt trigram 引擎，比原生 grep 快几个数量级。对大型代码库（几十上百个仓库）来说，速度是硬约束。

### 语义检索（向量库）

**适用场景**：自然语言描述的功能定位、概念搜索、相近代码片段发现。

**优势**：模糊匹配。"处理用户认证的代码"能匹配到 `AuthService`、`loginHandler`、`tokenVerifier`，即使这些名字里没有"认证"二字。

**局限**：**语义相似 ≠ 代码存在。** 向量检索的结果是"语义相近的片段"，不是"确实存在的代码"。把语义检索当事实用，会编造不存在的函数和调用链。

**工程选择**：Qdrant 向量库，1024 维 COSINE 距离，Embedding 用 DashScope text-embedding-v4（对中文理解好）。

**核心原则**：语义检索只能辅助定位，不能独立证明事实。它的证据等级是 weak，除非被其他路径交叉验证。

### 结构检索（AST）

**适用场景**：按符号名查定义位置、调用者和被调用者关系、导入导出信息。

**优势**：结构化的代码事实。"谁调用了 `handleRequest`"这个问题，grep 能搜到字符串匹配，但 AST 能告诉你真正的调用关系——哪些是调用、哪些是定义、哪些只是注释里提了一嘴。

**局限**：不是完美的类型感知调用图。ast-grep 的 pattern matching 是近似匹配，不是编译器级别的精确解析。但对我们来说，80% 的准确率够用了——完美的调用图需要完整的类型系统，而跨语言、跨仓库的场景下，完美的调用图根本不存在。

**工程选择**：ast-grep 做离线扫描，YAML 规则定义匹配模式，SQLite 存储结果。支持 Python、TypeScript、Go、Rust、Java、C/C++、Swift、Dart 等主流语言。

### 图关系检索（Neo4j）

**适用场景**：多跳遍历、调用链、影响分析。

**优势**：跨文件、跨模块的关系遍历。"改了 `AuthMiddleware` 会影响哪些模块"这个问题，需要沿着调用链走 2-3 跳，grep 和 AST 都做不到。

**局限**：图数据库是派生视图，不是权威源。Neo4j 的数据来自 ast-service 的离线扫描，如果 ast-service 没扫到，Neo4j 里就没有。

**工程选择**：Neo4j 5-community，SQLite 是权威源（本地事实存储），Neo4j 是派生图（可重建）。

### 关键洞察：单一检索路径永远不够

这是最重要的一条。

任何一种检索方式都有盲区：
- 纯 grep：只能搜精确关键词，搜不到语义相近的
- 纯向量：能搜到语义相近的，但可能搜到不存在的
- 纯 AST：能搜到结构关系，但搜不到自然语言描述
- 纯图遍历：能搜到多跳关系，但搜不到细节实现

**组合才有信心。** 当 grep 和 AST 同时指向同一个函数，当语义检索和精确检索交叉验证，置信度才从"可能"变成"确实"。

这就是为什么 Evidence Pack 里有 Evidence Tier：
- **strong**：精确检索 + 结构检索交叉验证的代码内容
- **supporting**：单一路径确认的代码事实（AST 或 grep 单独命中）
- **weak**：语义检索的定位提示（需要其他路径验证）

## 三）RRF 融合与证据分层

### Reciprocal Rank Fusion

不同检索路径返回的结果怎么融合？不能简单合并——grep 返回 5 条，向量返回 5 条，AST 返回 3 条，直接拼起来 13 条，谁排前面？

RRF（Reciprocal Rank Fusion）的做法：每个来源按排名给分（第 1 名得分最高，第 N 名得分递减），同一个结果在多个来源都出现就累加得分。这样既考虑了排名，又考虑了多源交叉验证。

在我们的实现里，不同来源的得分权重不同：
- 精确检索（Sourcebot）命中 import/require/dependencies：10 分
- AST 结构匹配：8 分
- Sourcebot 普通命中：7 分
- Neo4j 图关系：6 分
- 向量检索高相似度（≥0.75）：4 分
- 向量检索低相似度：2 分

这个权重不是拍脑袋的，而是从实践中调出来的。精确检索的确定性最高，所以权重最高；语义检索的确定性最低，所以权重最低。

### Evidence Tier：三层证据分级

给 LLM 的上下文不是平等的。有的证据硬（代码里确实写了），有的证据软（语义上可能相关）。LLM 需要知道哪些证据可以当事实用，哪些只能当参考。

```
strong    → 精确检索 + 结构检索交叉验证，或直接读取的代码内容
supporting → 单一路径确认的代码事实（AST 单独命中、或 Sourcebot 单独命中）
weak      → 语义检索的定位提示（需要其他路径验证才能当事实用）
```

**核心原则**：语义检索只能辅助定位，不能独立证明事实。

为什么这条原则这么重要？因为 LLM 有一种倾向：看到上下文里有的东西，就当事实输出。如果你把语义检索的结果（"可能相关的代码片段"）和精确检索的结果（"确实存在的代码"）混在一起给 LLM，它会一视同仁地引用，输出一个看起来很自信但实际上编造了一些不存在代码的答案。

Evidence Tier 就是为了解决这个问题：在 prompt 里明确告诉 LLM，strong 的证据可以当事实引用，supporting 的证据需要标注不确定性，weak 的证据只能用来定位、不能用来证明。

### 置信度判定

一组证据的整体置信度怎么判定？

```
high       → ≥2 个不同来源的 strong 证据
medium     → strong 证据 + supporting 证据，或仅 strong 证据
low        → 仅有 supporting 证据
unconfirmed → 没有任何证据
```

这个分级直接影响 LLM 的输出行为：high 置信度直接给结论，medium 标注假设，low 和 unconfirmed 明确说"信息不足，还需要查什么"。

## 四）多轮检索循环：从一次性 RAG 到受控研究过程

传统的 RAG 是"一锤子买卖"：用户问一个问题，系统搜一次，把搜到的片段塞给 LLM，LLM 生成答案。搜到了就答得好，搜不到就答得差。

这个模式对简单问题够用，但对复杂问题不够。比如"block-proxy 是怎样依赖 anyproxy 的"——第一轮搜索可能只搜到 block-proxy 的 package.json 里有 anyproxy，但不知道运行时是怎么用的。需要第二轮搜索去 grep `require('anyproxy')` 和 `ProxyServer`，找到具体的调用代码。

所以我们设计了一个多轮检索循环。

### 循环流程

```
Plan（规划）
  → 意图分类 + 实体提取 + 领域词表扩展
  → 候选仓库派生（从查询词匹配可用仓库名）
  → [可选 LLM 重新规划]
  → Query Expansion（查询扩展）

Round 1（第一轮全局搜索）
  → Sourcebot + Qdrant 全局搜索
  → Snippet Hydration（读取代码片段上下文）
  → AST + Graph 搜索（基于候选符号）
  → 提取 confirmed_repos（排除合成仓库如 ast-service）
  → 仓库排序（rank_code_repositories）
  → 候选仓库探针（bounded local_tool_grep，验证候选仓库是否真的相关）

Gap Observation（观察证据缺口）
  → observe_gaps() 纯函数：检查计划、命中、排序结果、已确认仓库
  → 输出 GapAction 列表（MissingManifest / MissingImport / MissingApiUsage 等）

Precision Search（精搜）
  → 对 confirmed_repos 执行本地精搜（read_manifest / local_tool_grep / local_tool_read）
  → 每轮最多 3 个探针，每个探针最多 5 条匹配

Round 2（第二轮补充搜索）
  → 先执行本地 gap actions + 候选探针
  → 再用 discovered terms 做全局 Sourcebot 查询
  → discovered terms 来自 extract_discovered_terms()：从强文本命中中提取 package 名、API 符号

循环终止条件
  → 达到 max_rounds（默认 2 轮，最多 3 轮）
  → 或无新 hits / 无新 queries
```

### 候选仓库发现与探针确认

这是一个容易出问题的环节。LLM 可能会"猜"一个仓库名——比如用户问"PassWall 的配置是怎样的"，LLM 可能猜 `passwall-any`，也可能猜 `Xray-core`。猜对了还好，猜错了就把后续所有搜索带偏。

所以我们的做法是：**entity ≠ repo。** LLM 猜的仓库名只是候选（candidate），不是确认（confirmed）。候选仓库必须通过探针验证才能进入 confirmed_repos。

探针是什么？就是在候选仓库里做一次有界的 grep（最多 5 条匹配），看看这个仓库是不是真的有相关内容。如果有，promote 到 confirmed_repos；如果没有，不 promote。

还有一个细节：**泛化词不能单独 promote 候选仓库。** 如果探针搜 `config` 命中了，不能就此确认这个仓库——因为 `config` 太泛了，几乎每个仓库都有。必须至少有一个 specific term（如 `passwall`、`luci-app-passwall`）命中，才能 promote。

### Gap Observation：观察证据缺口

这是一个纯函数，输入是当前检索状态，输出是"还缺什么证据"的结构化动作列表。

比如对于依赖关系问题：
- 有没有读过依赖清单（package.json）？没有 → MissingManifest
- 有没有 grep 过 import 语句？没有 → MissingImport
- 有没有搜过运行时 API 调用？没有 → MissingApiUsage

Gap Observation 不是让 LLM 自己决定"还需要查什么"——LLM 经常会过度查询或查错方向。Gap Observation 是代码控制的、有界的、可测试的。

### 有界循环：不是无限追问，2 轮足够

默认 2 轮，最多 3 轮。为什么不是更多？

因为每一轮的边际收益递减。第一轮覆盖 80% 的信息，第二轮补 15%，第三轮补 4%，再往后就是噪声了。

更重要的是，每一轮都有成本：搜索 API 调用、代码读取、LLM token。无限追问会把一个简单问题搞成 30 秒的长等待，用户体验直接崩掉。

**有界循环的核心是：接受"足够好"的证据，不追求"完美"的证据。**

## 五）意图分类与模板驱动输出

### 9 种查询意图

用户的提问千变万化，但意图是有限可枚举的。我们分了 9 种：

| 意图 | 触发词示例 | 典型问题 |
|------|-----------|---------|
| dependency_relation | "A 依赖 B"、"X 用了 Y" | block-proxy 是怎样依赖 anyproxy 的？ |
| call_chain | "调用链"、"怎么调到" | 从入口到数据库的调用链是什么？ |
| implementation_location | "在哪里实现"、"定义位置" | 用户认证在哪里实现的？ |
| troubleshooting | "为什么报错"、"怎么解决" | 为什么报 ConnectionRefused？ |
| symbol_explanation | "这个函数干什么"、"解释 X" | handleRequest 这个函数是干什么的？ |
| impact_analysis | "改了会影响什么"、"影响范围" | 改了 AuthMiddleware 会影响哪些模块？ |
| comparison | "A 和 B 的区别"、"对比" | Redis 和 Memcached 在这个项目里怎么用？ |
| architecture_overview | "整体架构"、"怎么组织" | 这个项目的整体架构是什么？ |
| generic_code_answer | 其他查询 | 通用代码问答 |

意图分类用规则实现（关键词匹配），不用 LLM。因为意图是有限集合，规则比 LLM 更快、更稳定、更可控。

### 每种意图对应固定的输出骨架

意图确定后，输出模板就确定了。比如 dependency_relation 的输出骨架：

```
## 结论
subject 对 object 的依赖类型与关系概述。

## 依赖链路
展示声明、引入、调用、配置流入的完整链路。

## 代码行为说明
subject 如何使用 object，object 在系统中的角色。

## 补充说明
如有信息缺口或需进一步确认的点，在此简要说明。

## 引用来源
列出知识采引自的仓库，按相关度从高到低排列。
```

这个骨架不是给 LLM 的"建议"，而是**硬约束**。LLM 必须按这个结构输出，不能自由发挥。

为什么？因为自由发挥的 LLM 输出不稳定：有时候先说结论有时候先说过程，有时候引用来源有时候不引用，有时候详有时候略。用户每次问同类问题得到的答案结构不一样，心智负担很大。

模板驱动的输出保证了：同类问题，同类结构。用户知道答案的"形状"，知道去哪里找关键信息。

### Evidence Pack：给 LLM 的不是散装片段，是结构化的证据包

传统 RAG 给 LLM 的是什么？一堆搜到的代码片段，按相关性排序，直接塞进 prompt。

我们的做法是构建 Evidence Pack：

```json
{
  "question": "block-proxy 是怎样依赖 anyproxy 的",
  "plan": { "intent": "dependency_relation", "entities": {...} },
  "items": [
    {
      "tier": "strong",
      "source": "precision_search",
      "repo": "block-proxy",
      "path": "package.json",
      "content": "\"anyproxy\": \"^4.0.0\"",
      "claim": "代码内容匹配"
    },
    {
      "tier": "strong",
      "source": "ast",
      "repo": "block-proxy",
      "path": "src/proxy.ts",
      "line_range": "L12-L15",
      "content": "const { ProxyServer } = require('anyproxy');",
      "claim": "结构符号/导入/调用事实"
    }
  ],
  "confidence": "high",
  "repo_roots": { "block-proxy": "/repos/block-proxy" }
}
```

Evidence Pack 不是简单的"搜索结果列表"。它是：
- **分层**的（strong / supporting / weak）
- **有来源**的（每条证据标注了来自哪个检索路径）
- **有声明**的（每条证据说明了它证明了什么——"代码内容匹配"还是"结构符号事实"还是"语义相似匹配"）
- **有置信度**的（整体置信度基于证据组合计算）

LLM 拿到 Evidence Pack 后，知道哪些证据可以当事实引用，哪些只能当参考。这比给它一堆散装片段效果好得多。

## 六）架构原则

### 权威源与派生视图分离

这是最重要的架构原则之一。

在我们的实现里，SQLite 是权威源（本地事实存储），Neo4j 是派生视图（可重建）。

为什么这么分？因为：
- SQLite 是本地文件，事务性强，不依赖网络
- Neo4j 是网络服务，可能宕机，可能连接超时
- 如果两者是"双写"模式（同时写两个），Neo4j 挂了会导致 SQLite 也写不了
- 如果 Neo4j 是派生视图，它挂了不影响 SQLite，恢复后从 SQLite 重建即可

这个原则适用于所有知识库系统：**总有一个"真相源"是本地、可靠、可审计的；其他存储都是从这个真相源派生出来的、可丢弃、可重建的。**

### 优雅降级

四路检索，任何一路挂了，其余路径继续工作。

```
Sourcebot 挂了 → 继续用 Qdrant + AST + Graph
Qdrant 挂了 → 继续用 Sourcebot + AST + Graph（少一些语义匹配，但精确度不受影响）
AST 挂了 → 继续用 Sourcebot + Qdrant（少一些结构事实，但文本检索不受影响）
Neo4j 挂了 → 继续用 SQLite 里的 AST 数据（少一些多跳遍历，但单跳关系不受影响）
```

优雅降级不是"挂了不影响"，而是"挂了影响可控"。少一路检索，答案质量会下降，但不会完全不可用。

### 不依赖完美解析

ast-grep 的 pattern matching 不是编译器级别的精确解析。它会漏掉一些调用关系，也会误判一些。

但我们接受这个不完美。因为：
- 完美的调用图需要完整的类型系统，跨语言场景下做不到
- 80% 的准确率对大多数场景够用
- 不完美但可用 > 完美但不可用

这个原则适用于所有知识库系统的索引层：**不要追求完美的索引，追求"足够好"的索引 + "能容忍不完美"的上层逻辑。**

### 增量索引

代码变更后不需要全量重建。增量索引只扫描变更的文件，只更新变更的部分。

全量重建的成本太高：几十上百个仓库，全量扫描可能要几十分钟。增量索引只需要几秒。

增量索引的前提是：权威源（SQLite）记录了每个文件的最后索引时间和 content hash。变更检测基于文件修改时间和 hash 对比。

### 测试隔离

后端函数注入，测试时用 FakeBackends 替代真实服务。

```python
@dataclass
class RetrievalBackends:
    search_sourcebot: Callable[[str, int], list[dict]]
    search_qdrant: Callable[[str, int], list[dict]]
    search_ast_structure: Callable[[str, list[dict], int], list[str]]
    search_graph_relations: Callable[[str, list[dict], int], list[str]]
    ...
```

生产代码传入真实的搜索函数，测试代码传入 fake 函数。测试不需要启动 Docker，不需要网络连接，不需要真实的数据库。

这个设计让检索逻辑的测试变得简单：构造 fake backends 返回预设数据，断言检索循环的行为是否符合预期。90 个测试，全部在本地跑，不依赖任何外部服务。

## 七）反模式

### 反模式：只有一种检索

**症状**：系统只有 grep，或只有 RAG（向量检索 + LLM）。

**问题**：单一检索路径的盲区太大。纯 grep 搜不到语义相近的；纯 RAG 会编造不存在的代码。

**修复**：至少两路检索——精确 + 语义。有条件的话加 AST 和图遍历。

### 反模式：把语义检索当事实

**症状**：向量检索返回的代码片段直接当事实引用，不验证代码是否真的存在。

**问题**：向量检索的结果是"语义相近的片段"，不是"确实存在的代码"。把语义检索当事实用，LLM 会输出看起来很自信但实际上编造了代码的答案。

**修复**：语义检索的证据等级是 weak，必须被精确检索或 AST 交叉验证后才能升级为 strong。

### 反模式：无界检索

**症状**：不限制检索轮次和结果数，"搜到满意为止"。

**问题**：每一轮检索都有成本（API 调用、LLM token、用户等待时间）。无限追问会把简单问题搞成 30 秒的长等待。而且边际收益递减——第 3 轮以后的搜索结果大多是噪声。

**修复**：有界循环，默认 2 轮，最多 3 轮。每轮限制查询数（Sourcebot ≤8 个查询，Qdrant ≤3 个查询）和结果数（每个查询 ≤5 条）。

### 反模式：散装上下文

**症状**：直接把搜索结果列表塞给 LLM，不分层、不标注来源、不标注置信度。

**问题**：LLM 不知道哪些证据可以当事实用、哪些只是参考。它会一视同仁地引用所有上下文，包括语义检索返回的可能不准确的片段。

**修复**：构建 Evidence Pack，分层（strong / supporting / weak）、标注来源、标注置信度。在 prompt 里明确告诉 LLM 不同层级的证据怎么用。

### 反模式：忽视索引维护

**症状**：知识库建好后就不管了，代码改了索引没更新。

**问题**：过期的知识库比没有知识库更危险——因为用户会基于过期的索引得到错误的答案，而且不知道答案是基于过期数据。

**修复**：增量索引机制，代码变更后自动更新索引。索引状态可视化（最后索引时间、索引覆盖率）。定期全量重建作为兜底。

### 反模式：entity = repo

**症状**：用户说"PassWall 的配置"，系统直接去 `passwall-any` 仓库搜——但万一用户说的是 `Xray-core` 呢？

**问题**：LLM 或规则猜的仓库名只是候选，不是确认。把候选当确认，会把后续所有搜索带偏。

**修复**：候选仓库必须通过探针验证（有界 grep）才能进入 confirmed_repos。探针命中必须包含 specific term，泛化词（如 `config`）不能单独 promote。

### 反模式：让 LLM 决定检索策略

**症状**：让 LLM 自己决定"还需要搜什么"、"用什么关键词"。

**问题**：LLM 经常会过度查询（搜一堆不相关的）或查错方向（用错误的关键词）。而且 LLM 的检索决策不可测试——同样的问题，不同时刻可能搜出不同的策略。

**修复**：检索策略由代码控制（Gap Observation 是纯函数），LLM 只负责最终的证据综合和答案生成。LLM 可以作为"可选的查询扩展输入"（LLM Planner），但不能直接执行检索。

## 八）给个人的行动建议

如果你是一个工程师，想为自己的代码知识库搭建一套 AI 可用的检索基建，以下是优先级建议：

### 第一步：先把 CLAUDE.md 写好

这是最低成本、最高收益的知识库投入。CLAUDE.md 是给 AI 的上下文文件，告诉 AI 这个项目的架构、约定、常用命令。

写好 CLAUDE.md 的标准：不是写一段"本项目采用微服务架构"之类的空话，而是写具体的——目录结构、关键模块、技术栈、常用命令、注意事项。

### 第二步：接入精确检索

在本地或 CI 环境里，确保代码可以被 grep 到。这一步几乎零成本——代码本身就在文件系统里，grep 就能搜。

如果你用 Claude Code，它已经内置了 Grep 和 Read 工具，可以直接搜索和读取本地代码。

### 第三步：建语义索引

用向量数据库（Qdrant、Chroma、Pinecone 等）对代码和文档做 Embedding 索引。这一步需要调用 Embedding API（DashScope text-embedding-v4 对中文支持好），有一定成本，但收益很大——语义检索能解决"我不知道关键词是什么"的问题。

### 第四步：建结构索引

用 ast-grep 或 tree-sitter 对代码做结构分析，提取符号、调用关系、导入信息。这一步对大型项目（几十上百个文件）收益明显，对小项目可以先跳过。

### 第五步：建图索引

用 Neo4j 或其他图数据库存储调用关系和依赖关系，支持多跳遍历和影响分析。这一步是锦上添花——如果前四步已经覆盖了 80% 的场景，图索引可以后做。

### 核心原则

- **增量推进**：不要一步到位，从 CLAUDE.md 开始，逐步加检索路径
- **先跑通闭环**：先让 AI 能在你的知识库上回答一个简单问题，再追求复杂场景
- **维护比建设重要**：知识库过期比没有更危险，增量更新机制是必须的
- **证据分层**：不同检索路径的证据质量不同，给 LLM 的上下文必须标注来源和置信度
