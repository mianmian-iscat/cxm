## Probation Evaluation — 试用期评语

### 适用场景

新员工试用期结束，需要出具通过/不通过的评语。输入可能是：
- 主管提供的简要描述 + 绩效数据
- 员工自述的试用期工作总结
- 同事反馈 + 项目产出

### 评估维度（5 个）

| 维度 | 核心问题 | 证据要求 |
|------|----------|----------|
| **上手速度** | 多快能独立产出？ | 从入职到首次独立交付的天数，以及交付质量 |
| **学习曲线** | 遇到不懂的东西怎么解决？ | 自学 vs 频繁求助的比例，是否有知识沉淀 |
| **交付质量** | 做的事靠不靠谱？ | 代码质量/文档质量/方案质量，返工率 |
| **协作融入** | 和团队配合得怎么样？ | 沟通主动性、协作口碑、是否主动同步信息 |
| **潜力信号** | 有没有超出预期的表现？ | 主动发现问题、提出改进、承担额外责任 |

### 评语结构

```
## 试用期评语 — {员工姓名}

### 基本信息
- 入职时间：{日期}
- 岗位/方向：{描述}
- 试用期：{X} 个月

### 总体判断
{一句话结论：通过/建议延长/不通过}

### 做的好的（2-3 条）
- {具体事实 + 体现的能力维度}
- {具体事实 + 体现的能力维度}

### 有待观察的（1-2 条）
- {具体事实 + 改进方向}

### 期望与建议
{对未来 3-6 个月的具体期望，不是泛泛的"继续努力"}
```

### 通过 vs 不通过的判断标准

| 判断 | 条件 |
|------|------|
| **通过** | 5 个维度中至少 4 个达标，且"交付质量"必须达标 |
| **建议延长** | 2-3 个维度不达标，但有明确的潜力信号，且问题可在 1-2 个月内改善 |
| **不通过** | "交付质量"不达标 + 至少 2 个其他维度不达标 + 无明显潜力信号 |

### 评语写作原则

- **具体**：每条评价都要有具体事例，不写"工作态度认真"这类空话
- **平衡**：即使通过，也要指出 1-2 个有待观察的点
- **可操作**："期望"部分给出具体方向，不是"希望继续努力"
- **与层级对齐**：P5 试用期的期望和 P7 试用期的期望不同，不要混淆

### 反模式

| 反模式 | 修正 |
|--------|------|
| "该同学工作积极，学习能力强" | "入职第 3 周独立完成 XX 模块开发，代码一次 CR 通过" |
| 全篇好评无短板 | 至少指出 1 个有待观察的点 |
| "希望继续努力" | "接下来 3 个月重点：独立负责 XX 方向，提升 XX 能力" |
| 用 P7 标准要求 P5 | 试用期期望必须与入职层级对齐 |

### 叙事范例（实习生转正）

> 以下是一个真实的实习生转正评语范例，展示"具体事实 + 能力维度 + 原因分析"的写法。

**总体评价**：XX 同学加入后一直认真踏实，前端专业技能掌握迅速，很快参与项目开发并能坚持写日报，内容充实有想法，对前端技术有兴趣，且有不错的计算机基础储备，后劲更足。参与项目包括"新年嘉年华活动"、产品介绍页、首页关键区块等，Demo 完成度高，无返工。

**优势**：
1. 态度认真，虚心求教，对前端感兴趣，潜力大
2. 专业基础不错，主动参与多个项目开发
3. 有不错的学习能力，能认识到自身不足，坚持写日报锻炼归纳总结能力
4. 编程基础好，学习框架迅速，对项目有责任心，执行力强，无拖沓无返工

**不足**（注意每条都有原因分析）：
1. 业务深入程度不够——主要是业务逻辑复杂且实习时间短，需要更多时间消化
2. 项目经验不够——应对需求变化不够灵活，目前处于成长阶段需要更多项目积累
3. 前端技术需深入——如 JS 高级编程技巧和浏览器引擎知识需要进一步学习

**关键写法**：优势用"事实+体现的能力"，不足用"现象+原因分析"。原因分析区分了"时间短"（客观）和"能力不足"（主观），这决定了后续培养方向。

### 转正评价原文

总体评价：
1，彩票2012新年嘉年华活动
2，彩票新产品介绍的若干页面（TMS）
3，彩票首页的一些新区块的开发（TMS）
4，送彩票的帮助页面改版

某同学加入淘宝之后，一直比较认真踏实，前端专业技能的掌握比较迅速，很快就参与到了彩票的项目开发，并能够坚持写日报，内容充实有想法，对前端技术非常感兴趣，并有不错的计算机基础知识储备，后劲更足。
参与的项目包括"彩票新年嘉年华促销活动"、彩票产品介绍、彩票首页的一些关键区块等，Demo完成度高，无返工，接下来会参与到彩票投注页面的开发。在淘宝的这段时间虽然不长，但非常投入，得到周围同事的认可。现在处于积累经验的阶段，建议多参加培训。

优势：
1，态度认真，虚心求教，对前端感兴趣，潜力大
2，尽管是本科，专业基础不错，主动参与很多项目开发
3，有不错的学习能力，能认识到自身不足，坚持写日报，锻炼自己的归纳总结能力
4，不错的编程基础，学习YUI比较迅速，对项目有责任心，有很好的执行力，工作无拖沓无返工

不足：
1，对业务的深入程度还不够，主要是因为彩票投注逻辑相对复杂/玩法多样，实习时间短，需要更多时间来消化这些业务知识
2，项目经验还不够，应对需求变化不够灵活，主要是因为目前处于成长阶段，需要更多的项目积累
3，Web前端技术需要深入，比如JS的高级编程技巧以及浏览器引擎等知识需要进一步深入学习

## Project Phase Summary — 项目阶段性总结

### 适用场景

项目进行到某个里程碑（如 M2、M3），需要向干系人同步进展。不是结项，是中途检查点。

### 与结项复盘的区别

| 维度 | 阶段性总结 | 结项复盘 |
|------|-----------|----------|
| **时点** | 项目中途 | 项目结束 |
| **目的** | 同步进展、暴露风险、调整方向 | 评估结果、沉淀经验、明确后续 |
| **语气** | "我们走到哪了，下一步怎么走" | "我们做到了什么，学到了什么" |
| **详细程度** | 精简，聚焦变化和偏差 | 完整，覆盖全过程 |

### 结构

```
## {项目名称} — {阶段名称}总结

### 一句话概括
{本阶段最重要的成果或进展，1 句话}

### 计划 vs 实际

| 里程碑 | 计划时间 | 实际/预计 | 状态 | 偏差原因 |
|--------|----------|-----------|------|----------|
| M1 | {日期} | {日期} | ✅/⚠️/❌ | {如有偏差} |
| M2 | {日期} | {日期} | ✅/⚠️/❌ | {如有偏差} |

### 本阶段关键成果（2-4 条）
- {成果 + 数据}
- {成果 + 数据}

### 风险与问题（按严重程度排序）
1. {风险描述 + 影响 + 应对措施 + 责任人}
2. {风险描述 + 影响 + 应对措施 + 责任人}

### 下阶段重点（2-3 条）
- {重点工作 + 预期产出 + 时间}

### 需要决策/支持的事项
- {具体事项 + 需要谁做什么 + 截止时间}
```

### 写作原则

- **结论先行**：第一句话就是本阶段最重要的事
- **偏差透明**：计划和实际的差异必须说明，不回避
- **风险前置**：不要等到问题爆了才说
- **请求明确**："需要支持"不是"希望领导关注"，是"需要 XX 在 XX 日前批准 XX"

### 反模式

| 反模式 | 修正 |
|--------|------|
| "项目进展顺利" | "M2 按期交付，核心指标 X 提升 15%" |
| 风险部分写"暂无" | 如果真没有风险，说明为什么没有（运气好还是管理好） |
| 长篇大论描述过程 | 阶段总结不超过 1 页，聚焦变化和偏差 |
| "需要领导支持" | "需要 VP 在本周五前批准 XX 预算" |

## Project Closure Retro — 项目结项复盘

### 适用场景

项目完成（或终止），需要做完整的结项复盘。与 `leading-large-initiatives.md` 中的 Closure 不同，这里适用于任何规模的项目。

### 结构

```
## {项目名称} — 结项复盘

### 项目概览
- 起止时间：{实际 vs 计划}
- 参与人员：{核心成员}
- 项目目标：{KO 时定的目标}

### 结果评估

| 目标 | 预期指标 | 实际指标 | 达成 | 说明 |
|------|----------|----------|------|------|
| {目标1} | {指标} | {指标} | ✅/❌ | {说明} |

### 做得好的（值得保留的做法）
1. {具体做法 + 为什么好 + 数据支撑}
2. {具体做法 + 为什么好 + 数据支撑}

### 做得不好的（需要改进的做法）
1. {具体问题 + 根因分析 + 改进建议}
2. {具体问题 + 根因分析 + 改进建议}

### 意外发现
{项目过程中发现的非预期结果——好的或坏的}

### 知识沉淀
- {沉淀了什么：文档/工具/流程/模板}
- {存放在哪里}
- {谁负责维护}

### 后续跟进
- {未完成的收尾事项 + 责任人 + 截止时间}
- {长期跟进指标 + 检查节奏}
```

### 复盘的 4 个原则

1. **对事不对人**：分析"什么流程导致了这个问题"，不是"谁犯了错"
2. **根因不止一层**：每个问题至少追问 3 次"为什么"
3. **好和坏都要写**：只写问题不写亮点，团队会抗拒复盘；只写亮点不写问题，复盘没有价值
4. **可操作的改进**：每条改进建议必须有具体行动、责任人、时间

### 根因分析模板

```
问题：{描述现象}
  → 为什么？{直接原因}
    → 为什么？{流程/机制原因}
      → 为什么？{根本原因}
改进措施：{针对根本原因的行动}
```

### 反模式

| 反模式 | 修正 |
|--------|------|
| "项目圆满完成" | 列出未达成的目标和遗留问题 |
| 复盘变成表彰会 | 至少 2 条实质性的"做得不好" |
| 改进建议是"加强沟通" | 具体到"每周三下午 3 点站会同步 XX 进度" |
| 复盘文档写完就扔 | 指定 1 人负责跟进改进措施落地 |

## Upward Reporting — 向上汇报（速查）

> 完整方法论见 `communication.md` 的 Upward Report 章节。以下是速查清单。

### 向上汇报的 4 个阶段

| 阶段 | 核心问题 | 篇幅占比 |
|------|----------|----------|
| **我们在哪** | 当前状态，一句话 | 10% |
| **我们做了什么** | 关键动作和结果 | 30% |
| **我们建了什么** | 可复用的能力/系统 | 30% |
| **我们需要什么** | 显式请求，具体到人 | 30% |

### 速查清单

- [ ] 第一句话是结论，不是背景
- [ ] 数据和事实在前，判断在后
- [ ] 坏消息不藏在好消息后面
- [ ] "需要支持"有具体的请求对象和截止时间
- [ ] 篇幅与受众匹配（VP 只看 1 页，直属 TL 可以看 3 页）

### 最常见的错误

| 错误 | 修正 |
|------|------|
| 用 80% 篇幅描述过程 | 过程放附录，正文放结论和请求 |
| 坏消息藏在中间 | 坏消息提前，且附带应对方案 |
| "希望领导关注" | "需要 VP 在周五前审批 XX 预算" |
| 只报喜不报忧 | 风险和坏消息必须显式呈现 |

## Downward Reporting — 向下汇报

> 年度/半年度团队总结的完整方法论见 [annual-team-summary](annual-team-summary.md)。向下汇报聚焦日常沟通，年度总结聚焦长周期的温度与凝聚力。

### 适用场景

向团队/下属同步信息。包括：全员会、周会同步、Release 公开信、决策通报、方向调整说明。

### 向下汇报 vs 向上汇报的区别

| 维度 | 向上汇报 | 向下汇报 |
|------|----------|----------|
| **目的** | 获取决策/资源/支持 | 对齐认知/激发行动/建立信任 |
| **受众关心** | "结果怎么样，需要我做什么" | "为什么做这个，对我意味着什么" |
| **语气** | 请求式、数据驱动 | 解释式、共情式 |
| **长度** | 越短越好 | 可以更长，但要结构化 |

### 向下汇报的 5 种形式

#### 1. 决策通报

当做出一个重要决策后，向团队说明。

```
## {决策标题}

**一句话**：{我们决定做什么，以及为什么}

**背景**：{2-3 句，交代为什么需要做这个决策}

**决策**：{具体决定是什么}

**为什么选这个方案**：{对比 2-3 个选项，说明取舍}

**对团队的影响**：{具体到各小组/个人会发生什么变化}

**时间线**：{什么时候生效，过渡期多长}

**Q&A**：{预判 2-3 个团队最可能的问题，提前回答}
```

#### 2. 方向调整说明

当战略或方向发生变化时。

```
## {调整标题}

**变了什么**：{一句话概括变化}

**为什么变**：{外部原因/内部原因，诚实说明}

**不变的是什么**：{稳定军心——哪些东西不会变}

**新方向下我们做什么**：{具体的行动变化}

**对大家的影响**：{工作内容/目标/KPI 会有什么调整}

**开放讨论**：{预留讨论时间/渠道}
```

#### 3. Release 公开信 / 版本发布说明

项目交付后向全团队通报。

```
## {项目名称} {版本号} 发布

**我们交付了什么**：{一句话概括核心价值}

**关键数据**：{3-5 个核心指标}

**感谢**：{具体到人，不是"感谢大家的努力"}
- {张三}：{具体贡献}
- {李四}：{具体贡献}

**遗留问题**：{已知问题 + 跟进计划}

**下一步**：{接下来的重点}
```

#### 4. 周会同步

```
## 本周同步

**本周最重要的事**：{1 件，不是 10 件}

**关键进展**：{2-3 条}

**下周重点**：{2-3 条}

**需要大家知道的**：{跨团队信息/政策变化/人员变动}

**开放讨论**：{预留 5 分钟}
```

#### 5. 坏消息通报

```
## {事件标题}

**发生了什么**：{事实，不加修饰}

**影响范围**：{具体到哪些人/系统/业务}

**我们做了什么**：{已采取的应对措施}

**接下来会怎样**：{预期发展 + 我们的计划}

**需要大家做什么**：{具体行动要求}

**复盘时间**：{什么时候做详细复盘}
```

### 向下汇报的原则

1. **诚实优先**：坏消息不包装成好消息。团队能感知到信息被过滤，一旦失去信任，后续所有沟通都打折
2. **解释 Why**：不只是说"做什么"，要说"为什么做这个决定"。团队理解原因后执行力更强
3. **具体到人**：感谢要具体到人和事，不是"感谢大家的努力"
4. **预留讨论空间**：单向通知不够，留出让团队提问和反馈的渠道
5. **频率稳定**：不要只在有大事的时候才沟通，保持固定的沟通节奏

### 反模式

| 反模式 | 修正 |
|--------|------|
| "经过深思熟虑，我们决定..." | 直接说决定是什么，然后解释为什么 |
| 感谢写"感谢所有人的付出" | "张三在 XX 项目中连续 3 周加班解决了 XX 问题" |
| 坏消息藏在好消息里 | 单独通报坏消息，不包装 |
| 只通知不解释 | 说清楚为什么，团队需要理解原因才能执行 |
| 一年沟通一次 | 保持周/双周/月的固定节奏 |
