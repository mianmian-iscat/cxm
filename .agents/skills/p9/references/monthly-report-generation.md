# 月报生成指南

> 根据素材文件生成飞猪用户技术月度报告。完整的生成 pipeline，从素材获取到成稿输出。
>
> 与 [templates-more](templates-more.md)（模板 30）的关系：模板 30 是写作规范的精简版，适合轻量场景；本文件是完整生成流程，包含团队拆分、跨团队合并、外链处理等 pipeline 逻辑。
>
> 与 [communication](communication.md)（月报写法章节）的关系：communication.md 从管理视角讲月报该怎么写（提炼主线、呈现趋势、暴露结构性问题）；本文件从执行视角讲怎么从素材生成月报。

---

## 调用方式

```
/p9 帮我生成月报 <素材文件>
/p9 帮我生成月报 <素材文件>，重点关注 <重点事项>
```

## 生成流程

### 1. 获取素材

如果调用时传了文件路径，读取该文件；否则列出当前目录下常见素材文件（`.txt`、`.md`、`.docx`、`.pdf` 等），让用户选择。

### 2. 记录重点事项

检查用户是否指定了重点事项（对话中明确提出关心的重点），如有则记录下来，后续月报中必须覆盖：

- **优先提取**：在素材中搜索与重点事项相关的描述、数据、进展
- **独立成段**：重点事项应在月报中有明确的段落或编号条目，不能被合并或省略
- **信息补全**：素材中某重点事项描述较少时，可标注"素材中未提及详细数据"
- **位置灵活**：重点事项按其业务属性归入对应板块，不必集中放置
- **不编造**：重点事项仅用于引导信息提取和编排方向，不据此虚构内容

### 3. 读取组织结构

读取 [monthly-report-team](monthly-report-team.md) 的使用门禁，先判断素材是否属于飞猪用户技术团队语境。命中门禁时使用其中的团队组织架构；未命中时忽略该组织结构，从素材中提取实际组织关系。

### 4. 按团队拆分素材

将素材内容按所属团队进行拆分归类，识别每个团队汇报了哪些事项。

### 5. 跨团队事项合并

同一件事可能散落在多个团队的素材中（如大促稳定性可能被前端、客户端、各业务线同时提及），需要识别重复描述，提取共同要素，合并为一条统一汇报项。详见下方「跨团队事项合并」。

### 6. 信息完整性评估

检查合并后的内容，判断关键信息是否完整（背景、方案、数据、结论是否齐全）。

### 7. 按需读取外链

仅当必要信息在素材中缺失时，才读取对应外链补充。详见下方「外链处理」。

内网链接（语雀、钉钉文档等）仅在当前平台具备访问能力时读取；无法访问时直接跳过，不阻塞月报生成。

### 8. 读取风格范例

读取 `references/monthly-report-examples/` 目录下所有历史月报，理解格式结构和行文风格。以 **用户技术10月份月报** 为主要参考模板。

### 9. 综合分析

将外链补充内容与原始素材结合，提炼关键信息、补充细节、生成摘要；同时针对重点事项定向搜索相关信息。

### 10. 生成月报

参考范例的结构和语言风格，将综合分析后的内容组织成正式月报，确保重点事项有独立段落或编号条目。

### 11. 输出

生成到当前工作目录，文件名格式为 `飞猪用户技术月报-年-月.md`（如 `飞猪用户技术月报-2025-10.md`）。

## 月报格式规范

### 标题层级

| 级别 | 格式 | 示例 |
|------|------|------|
| 月报总标题 | `### 飞猪用户技术月报-年-月` | `### 飞猪用户技术月报-2026-04` |
| 一级标题 | `一）二）三）` | `一）V10 项目` |
| 二级列表 | `1. 2. 3.` | `1. 架构设计：...` |
| 三级列表 | `1) 2)` | `1) 细节A...` |

### 列表强制要求

**每个一级标题下必须使用二级列表（`1. 2. 3.`）来呈现该板块下的各条事项。** 不允许在一级标题下写大段段落而不分条。

### 正交枚举原则

列表中每一项聚焦一个**独立的方面或子事项**，做到：

- **正交不重叠**：同一板块下的列表项之间不应描述同一件事的不同表述
- **一事多面**：如果一个重点事项有多个方面的进展，应拆成多条列表项，每条聚焦一个方面
- **颗粒度**：每条列表项约 1-3 句话，包含具体数据、状态、时间节点，信息密度高但不冗长

### 行文要则

**这是给老板看的汇报，内容必须易读、清晰、准确。**

| 原则 | 不要 | 要 |
|------|------|------|
| **带时间** | "项目完成 spec 改造" | "本月开始速推 spec 文档化，截止本月底完成所有客户端工程新项目的 spec 改造" |
| **带范围** | "完成 spec 改造" | "完成所有客户端工程新项目的 spec 改造"（限定范围） |
| **先介绍再讲进展** | "途灵生图平台：第一...，第二..." | "途灵生图平台：我们的多媒体 AI 生成平台本月有了大量新功能优化..." |
| **完整上下文** | "AI 线路规划 4.9 发布" | "特价机票基于地图交互的 AI 线路规划 4.9 发布，为用户完成线路规划和特价出行方案的组合推荐" |
| **数据准确** | "性能大幅提升" | "秒开率从 44.99% 提升至 47.86%，提升 2.88PT" |
| **风险说完整** | "存在一定风险" | "存在人力风险，需要从行业协调部分人力支持" |

**时间标注要求**：
- 技术事项必须带时间，至少精确到月（"本月初""本月中""本月底"），精确到天更好
- 已完成的事项写明上线日期或发布版本
- 进行中的事项写明预计上线时间

### 行文风格

- **数据驱动**：关键指标用具体数字（秒开率 90.4%、UV 43.9w 等）
- **链接保留**：素材中的内部链接（语雀、Aone、钉钉文档等）原样保留在月报中
- **语气**：客观汇报，避免过度修饰，适当提及风险和后续计划
- **去 AI 味**：
  - 不使用"值得注意的是""值得一提的是""总的来说"等套话
  - 不使用"积极推进""深入探索""全面赋能"等空泛动词
  - 不用"首先...其次...最后"等连接词堆砌
  - 不添加总结性段落或"展望未来"类收尾
  - 直接陈述事实：做了什么、数据多少、下一步是什么
  - 像人写的，不像 AI 生成的——简洁、直接、有信息密度

### 示例对照

**正确写法**：

```
一）双十一和营销大促会场

1. 双十一会场，10.15 上线预热，10.20 上线正式，全端秒开率 90.4%，端内 95.1%，日均 UV 43.9w，转化率 7.7%。
2. 爆款榜单，市场部今年重用，针对性做了微信 H5 二次分享卡片、分享口令复制、钉钉分享唤端等优化。
3. 行业侧双十一需求进展：
   1. 交通：宝贝链路支持海外版淘宝，1111 前发布一单链路。
   2. 酒店：套餐双十一交付顺利，月底上线切流。
4. 双十一稳定性保障：
   1. 本月完成端侧双十一链路问题排查，沉淀了端侧双十保障手册。
   2. 直播性能：李佳琦直播峰值 8402QPS，降级率 4%，对比去年 3300+ 峰值、50% 降级率，提升明显。
```

**错误写法**（大段不分条、多条重复同一件事）：

```
一）双十一和营销大促会场

双十一期间各团队全力保障，完成了会场搭建和性能优化。双十一会场 10.20 上线，秒开率 90.4%，UV 43.9w。各行业也完成了各自需求交付...
```

## 月报板块结构

月报通常包含以下板块（按素材内容灵活裁剪，不必全部出现）：

| 板块 | 说明 |
|------|------|
| 体验治理/体验专项 | 性能指标、秒开率、SSR改造、流式渲染等 |
| 端侧稳定性和安全生产 | 故障、Patch、监控、容灾 |
| 大促/营销活动 | 双十一、国庆、春运等会场数据和性能 |
| 手淘/入淘 Tab | 入淘交付、Tab 改版、轻应用等 |
| 用户产品与用增 | 会员、CRM、群聊、评价、支微多端等 |
| AI 产品/问一问 | AI Agent、拍照讲解、厂商合作等 |
| 生产端 AI 赋能 | AI会场搭建、途灵生图、生成式 UI 等 |
| 各行业端侧进展 | 交通、酒店、度假、商旅、保险等各域 |
| 基建和性能保障 | 脚手架、容器、包大小、鸿蒙适配等 |
| 团队建设 | 绩效、盘点、技术分享等（见下方说明） |
| **AI 工程实践**（**固定放在最后**） | 本月 AI 工具链使用、AI 辅助开发、前沿技术探索与落地 |

---

## 篇幅约束

**月报总篇幅不得超过 65 行。**

- 素材内容丰富时：精炼表达，只保留核心数据和关键进展，合并相似条目
- 素材内容较少时：如实反映，不强行扩充
- AI 工程实践板块计入总篇幅，约 3-5 条

## 跨团队事项合并

**同一件事往往散落在各个团队的素材中，必须从各团队中提取共同要素，合并为一条统一汇报。**

### 识别重复事项的典型场景

| 场景 | 示例 |
|------|------|
| 大促/重大活动 | 双十一、国庆、春运等，前端、客户端、各业务线都会汇报 |
| 稳定性/安全生产 | 故障修复、监控建设、容灾演练，各团队可能都提及同一故障 |
| 基建/公共能力 | 脚手架升级、容器改造、鸿蒙适配，多个团队可能都引用了同一个基建项目 |
| AI 相关项目 | AI 会场搭建、AI Code Review，各团队可能都汇报了各自的接入情况 |
| 组织/团队事项 | 绩效考核、技术分享、人员变动，各团队可能都提及了同一次活动 |

### 合并方法

1. **提取共同要素**：找出各团队描述中指向同一事项的关键标识（活动名、项目名、时间、负责人）
2. **整合各角度**：将不同团队的视角合并为一条，保留各团队的关键数据和贡献
3. **避免重复汇报**：同一事件在月报中只出现一次，用"各团队"或"多个团队"等概括词替代逐个列举
4. **保留关键差异**：如果不同团队的数据有明显差异，分别保留关键数字

### 合并示例

**素材中散落的描述**：
- 火车票前端："双十一期间火车票会场秒开率提升至 85%"
- 机票前端："双十一期间机票会场首屏加载优化至 1.2s"
- 酒店前端："双十一酒店会场性能优化，LCP 降低 30%"
- 交通线前端（总览）："双十一期间各业务线均完成性能优化"

**合并后的月报条目**：
> 双十一期间各业务线会场性能优化：火车票会场秒开率提升至 85%，机票会场首屏加载优化至 1.2s，酒店会场 LCP 降低 30%。

## 组织结构整合

素材文件往往同时包含多个团队的内容，包括上级团队总览、各子团队的独立汇报。命中 [monthly-report-team](monthly-report-team.md) 使用门禁时，按照其中的组织架构进行有机整合；未命中时，按素材自身呈现的组织关系整合。

### 整合策略

1. **自顶向下扫描**：先识别素材中哪些段落属于上级团队视角（总览、大盘、公共事项），哪些属于子团队视角（具体业务、独立项目）
2. **父子去重**：如果上级团队已概括某事项，子团队又详细汇报了同一件事，以子团队的详细内容为准，合并为一条
3. **子团队独立汇报**：子团队独有的项目，在月报中归属到对应业务板块
4. **公共事项上提**：多个团队都参与的公共事项，提取出来作为独立汇报项

## 外链处理

**核心原则：默认不读取外链，仅当必要信息缺失时按需读取。**

### 需要读取外链的场景

| 场景 | 判断标准 |
|------|----------|
| 素材仅有链接无描述 | 素材中只放了一个链接，没有任何文字说明 |
| 关键数据缺失 | 某事项的核心数据在素材中完全未提及 |
| 重点事项信息不足 | 用户指定的重点在素材中描述过少 |
| 冲突信息需要验证 | 不同团队对同一事项的描述有明显矛盾 |

### 不需要读取外链的场景

| 场景 | 判断标准 |
|------|----------|
| 素材已有充分描述 | 素材正文已经包含了项目背景、数据、结论 |
| 仅作为引用标注的链接 | "参考文档：[链接]" 类链接，用于溯源 |
| 图片/截图链接 | 不影响月报文字内容的生成 |
| 重复信息的多个链接 | 多个链接指向同一内容，已有一份描述即可 |

### 外链获取方式

对内网链接（语雀、钉钉文档等），只在当前平台具备登录态和读取能力时获取内容。没有访问能力时，不要猜测链接内容，直接跳过，基于已有素材生成月报。

### 外链内容处理

1. **仅补充缺失信息**：外链内容仅用于补充素材中缺失的关键信息
2. **提炼关键信息**：从外链内容中提取项目背景、技术方案、核心数据、里程碑、风险点中素材缺失的部分

## AI 工程实践（固定放在月报末尾）

这是月报的**独立板块**，始终在月报末尾单独列出。

### 写作维度

从以下维度中选取素材中涉及的内容，组织成 3-5 条要点：

| 维度 | 关注点 |
|------|--------|
| AI 工具链 | Claude Code、Cursor、Copilot 等工具在团队中的使用覆盖率和产出 |
| AI 辅助开发流程 | AI Code Review、AI 测试用例生成、Prompt 工程 |
| 前沿技术探索 | 最新模型/框架/协议（MCP、A2A、GenUI、Agent 编排）的调研与 PoC |
| AI 能力落地 | 将 AI 能力实际接入到生产链路中的工程化工作 |
| 团队 AI 基建 | Prompt 模板库、AI 开发规范、AI 知识沉淀 |
| 行业 AI 动态对标 | 竞对或行业标杆的 AI 实践对比 |

### 行文要求

- 遵循与其他板块相同的格式：使用 `1. 2. 3.` 二级列表组织条目
- **必须先简要介绍项目是什么**
- **带时间限定**：如 "本月开始...""截止月底..."
- **必须**与最新技术趋势结合：提到具体模型版本、框架版本、协议标准等
- **必须**有具体数据或里程碑
- 本板块标题序号顺延正文编号，如 `九）AI 工程实践`

---

## 团队建设板块写作要求

**以用户技术整体视角总结，不罗列各小团队各自的事项。**

- 提取素材中跨团队的共性事项：绩效盘点、组织架构调整、技术氛围活动、招聘进展等
- 小团队独立的事项不写入月报
- 1-2 条即可，精炼概括

---

## 注意事项

- 不要编造素材中没有的数据或项目
- 如果素材中某板块内容较少，可以合并或省略该板块
- 月份信息需要从素材或文件名中推断，不确定时询问用户
- 输出前检查编号是否连续、格式是否一致
