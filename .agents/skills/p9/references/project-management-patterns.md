# 项目管理方法论

> 本文件聚焦不同类型项目的管理模式匹配。大型战役的组织指挥（initiative charter、三层指挥体系、M1-M5 里程碑）见 [leading-large-initiatives](leading-large-initiatives.md)。

## 项目类型与管理模式

不是所有项目都用同一种管理方式。根据目标、周期、复杂度选择匹配的模式：

| 类型 | 典型项目 | 管理重点 | 周期 | 关键节奏 |
|------|----------|----------|------|----------|
| **战役型** | 百天无线体验大战 | KO → 分兵 → 会战 → 收口 | 3-6 月 | 周会 + 里程碑汇报 |
| **Sprint 型** | 王者归来 DAU 冲刺 | 目标聚焦 → 快速迭代 → 数据验证 | 4-8 周 | 每日站会 + 周数据复盘 |
| **大促型** | 双十一 | 预案 → 压测 → 值守 → 复盘 | 固定周期 | 倒计时节奏 |
| **跨公司对齐型** | 超级对齐 | 利益对齐 → 接口定义 → 联合作战 | 6-12 月 | 月度里程碑 + 域级汇报 |
| **调研驱动型** | Push 数据报告、Design2Code 调研 | 假设 → 数据 → 结论 → 决策 | 2-4 周 | 访谈/数据分析 + 汇报 |

### 选择原则

1. **目标明确度决定管理模式**：目标清晰用 Sprint，目标模糊先做调研
2. **跨域程度决定组织方式**：单团队用扁平管理，跨团队用虚拟组+PM 制
3. **周期长度决定汇报节奏**：短周期日报/站会，长周期周报+月度里程碑
4. **风险等级决定验证密度**：核心链路高频验证，内部工具低频验证

## 战役型项目的 KO 方法论

战役型项目是 P9 层级最常操盘的项目类型。KO（Kickoff）不是开个会就完，是一个结构化的启动过程。

### KO 四步法

**第一步：问题定调**
- 清晰表达痛点（"体验阵痛"）和集体决策（"我们集体决定"）
- 将项目与更大的战略主题连接（"提升消费者体验，强化互动"）
- 这一步的输出：一页纸的问题陈述，所有人达成共识

**第二步：双重使命设计**
- 每个战役项目同时承载两个使命：
  - **用户面**：解决用户侧的具体问题（如体验优化、DAU 提升）
  - **基建面**：借机重塑核心系统（如架构升级、技术栈迁移）
- 双重使命的意义：让技术投资获得业务合法性，让业务项目留下技术遗产

**第三步：子域拆解与命名制**
- 经过短暂但紧张的对焦梳理，将大项目拆解为子项目（通常 5-15 个）
- 每个子项目指定一个**命名的技术 PM**——不是"某团队负责"，而是"某某负责"
- 拆解后与产品负责人对齐，确认边界和优先级
- 用蜘蛛图（spider diagram）可视化各子项目的关键维度

**第四步：集中办公与士气动员**
- 条件允许时，将相关人员集中到一个地点（消除沟通摩擦）
- KO 结尾要有战略意义宣导和团队动员，将项目从"任务"提升为"使命"

### 战役型项目的过程管理

- **周会制度**：每周固定时间，所有子项目 PM 汇报进展、风险、依赖
- **运营报告**：作为项目的"中枢神经系统"，包含 4 个部分：进展、风险、问题、决策需求
- **风险 vs 问题管理**：风险是可能发生的，问题是已经发生的。风险要预防，问题要解决
- **等权汇报**：风险和信心同等权重，不能只报喜不报忧

## Sprint 型项目的数据驱动

Sprint 型项目的核心特征是**目标可量化**和**快速迭代**。

### 多波次 Sprint 累积模型

一个大的目标（如 DAU 从 147 万到 500 万）不是一次 Sprint 能完成的，需要多波次累积：
- 每一波 Sprint 都建立在前一波的方法论积累上
- 每一波结束后做复盘，将方法论沉淀为可复用的资产
- 波次之间允许调整目标和方法

示例：百天大战 → 场景化战役 → 王者荣耀一期 → 王者荣耀二期 → 王者归来。每个波次不只是做数据，更是在积累方法论。

### 三管齐下的 Sprint 焦点

每个 Sprint 同时推进三个方向：
1. **用户权益**：创造 App 独有价值的功能（驱动安装/活跃）
2. **运营工具**：互动产品（签到、流量中心）提升回访率
3. **架构优化**：与业务并行推进的基础设施工作

### 诚实的结果汇报

- 目标达成的，用数据说话（DAU 均值、峰值、同比）
- 目标未达成的，诚实承认（"实际 410 万 vs 目标 500 万"），同时分析趋势线
- 永远命名 PM 和关键贡献者
- 将每一波的收获与全年累积价值连接

### 能力累积理论

**每个 Sprint 的最大收获不是数据变化，而是方法论和团队能力的积累。** Sprint 的真正价值在于：下一次 Sprint 能更快启动、更精准执行、更有把握交付。

## 跨公司对齐型项目

跨公司对齐是 P9 层级最难的项目类型之一，因为**你没有直接管辖权**。

### 核心挑战

1. **利益对齐**：各参与方有自己的 KPI 和优先级，不会为你的项目放弃自己的目标
2. **接口定义**：跨团队的接口如果没有明确定义，执行中会不断出现灰色地带
3. **联合作战**：多方协同需要一个中立的协调机制，而不是某一方的命令

### 管理模式

- **按业务域拆解**（不按技术层）：每个业务域有自己的进展汇报
- **里程碑节奏**：设定明确的里程碑节点（如 615、830），每个节点有域级汇报 + 总体汇总
- **可视化进展**：用 GIF、截图等可视化方式展示域级进展，让进展可感知
- **PMO 中立协调**：设立 PMO 角色负责跨域协调，而不是某一方兼管

### 向上汇报的框架

跨公司对齐项目的汇报，需要让老板看到的不是过程，而是：
1. 各域当前状态（用红黄绿灯）
2. 关键风险和需要老板介入的事项
3. 下一里程碑的预期结果

## 调研驱动型项目

调研型项目的目标是**形成判断**，而不是交付产品。

### 四步调研法

1. **定义假设**：调研前明确"我怀疑/假设什么"，而不是"我要了解什么"
2. **设计数据采集**：访谈、数据分析、对标分析——选择与假设匹配的方法
3. **结构化分析**：将数据按维度整理，发现模式和异常
4. **形成结论和决策建议**：不是"发现了什么"，而是"基于发现应该做什么"

### 调研报告的结构

- 结论先行（不是先讲方法再讲结论）
- 数据支撑（每个结论都有具体数字）
- 分维度分析（不同角色、不同场景的差异化发现）
- 反直觉发现优先（打破预设认知的发现最有价值）

### 调研规模与深度

| 调研类型 | 样本量 | 周期 | 适用场景 |
|----------|--------|------|----------|
| 快速验证 | 3-5 人 | 1 周 | 方向初步判断 |
| 深度调研 | 20-40 人 | 3-4 周 | 转型规划、组织变革 |
| 全景扫描 | 100+ 人 | 6-8 周 | 公司级战略 |

## 共创会方法论

共创会是 P9 层级驱动团队达成共识的核心工具。它不是"开会讨论"，而是一个结构化的共识构建过程。

### 共创会四阶段

**第一阶段：现状感知（听）**
- 核心原则："站在本位思考，对问题不作回应，只作感受同步"
- 每个参与者分享自己观察到的现状——痛点、困惑、依赖关系
- 领导者只听，然后做综合归纳

**第二阶段：信息输入（讲）**
- 多个 TL 做结构化简报，给团队一个共享的信息基础
- 高层领导提供元框架：将具体问题放入更大的上下文

**第三阶段：技术共创（做）**
- **上半场（发散）**：各组提名和讨论"最重要的 N 件事"——广度优先
- **下半场（收敛）**：聚焦 3-4 个预先识别的核心痛点
  - 每个痛点用统一模板：问题本质 → 目标 → 解法 → 落地
  - 每个议题有指定的讨论主持人
  - 各组汇报后接受跨组挑战
- **投票排名**：各组按汇报质量排名，激励充分准备

**第四阶段：总结展望（定）**
- 承认未深入讨论的部分
- 宣布组织机制：虚拟组 + PM 责任制
- 明确评估标准的变化
- 回应跨地域协作等现实关切

### 共创会后续沟通

共创会结束后，发布一份三段式公开总结：
1. **共创环节**（发生了什么）
2. **核心输出**（决策了什么，谁负责什么）
3. **小结**（组织决策和前瞻框架）

每个行动项必须有：命名的技术负责人 + 具体交付物 + 与绩效目标的连接。

## 反模式

| 反模式 | 检测 | 修正 |
|--------|------|------|
| **所有项目都用同一种管理模式** | Sprint 项目用战役的汇报节奏 | 先判断项目类型，再选择匹配的管理模式 |
| **KO 只是开个会** | KO 没有子域拆解和命名制 | KO 必须有：问题定调 + 双重使命 + 子域拆解 + 命名 PM |
| **Sprint 只看数据不看方法论** | 复盘只讲"达标没达标" | 每个 Sprint 结束后沉淀可复用的方法论 |
| **共创会没有收敛** | 讨论了很多但没有行动项 | 必须有下半场的收敛聚焦和命名负责人 |
| **调研只做不决策** | 调研报告写完了但没有决策建议 | 调研的终点是"应该做什么"，不是"发现了什么" |
| **跨公司项目试图命令对方** | 用行政权力推动跨团队配合 | 用利益对齐和接口定义代替命令 |
| **战役型项目不设双重使命** | 只做业务交付不留技术遗产 | 每个战役项目都要同时推进业务和技术基建 |
