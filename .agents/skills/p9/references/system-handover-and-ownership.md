# 接手系统与权责边界

> 接手外部系统、技术遗产、或二方包时如何保持专业的技术动作。故障定责复盘时如何不被动。

## 核心理念——接手系统不是签收快递

技术团队经常遇到这种情况：组织调整、团队变动、规划方向变更，甚至晋升结束后，大量"技术遗产"等待接盘。接手一个系统，不是签收一个快递——你接过来的不只是代码，还有它的消费方、它的历史包袱、以及出了问题之后的责任。

最常见的失败模式是"稀里糊涂的接手"——不知道这个系统被谁用、不知道自己的权责边界在哪里、没有建立任何监控、出了问题之后在复盘会上两眼一抹黑。这种"无意"会被解读成不专业，每一条都够让当事人喝一壶。

接手系统这件事，需要**在接手的那一刻就完成专业动作**，而不是等出了问题再补课。

---

## 一）接手外部系统的四项功课

接手任何外部系统（二方包、共享服务、平台组件、技术遗产），在接手的那一刻就要完成以下四项功课。不是"以后慢慢做"，是接手时就做。

### 第一项：搞清楚谁是消费方

你的服务到底被谁用了？这个问题听起来简单，实际往往搞不清楚。依赖泛滥是常态——一个二方包可能被十几个应用引用，一个共享服务可能有跨 BU 的消费方，你根本不知道。

**具体动作**：

1. 找到所有依赖方列表——谁在 `include` 你的代码、谁在 `install` 你的包、谁在调用你的接口
2. 区分核心消费方和边缘消费方——核心消费方出问题直接影响业务，边缘消费方出问题影响体验
3. 建立消费方联系方式——不只是"在群里吆喝一声"，而是能钉到具体的人

> 案例：某前端资源版本管控二方包（FEB），被天猫招商后台、飞猪多个业务应用引用，但接手方对消费方列表一无所知。出了问题之后，天猫招商后台说"你提供的服务出了问题"，飞猪同学说"我不知道你在用啊"——这就是没做第一项功课的后果。

### 第二项：定义 SLA 和权责边界

SLA 不是大厂才需要的东西。哪怕你维护的只是一个小组件、一个工具函数，也要在明显位置写清楚：

- **这是什么**——定位（BU 级方案 / 集团级方案 / 社区开源方案）
- **负责什么**——功能边界、性能承诺、可用性目标
- **不负责什么**——明确排除项
- **出了问题找谁**——On-call 机制、响应时间承诺

**量力而行**，不要贪图大而全。先掂量自己有没有这个金刚钻。一个诚实的"我只承诺 X"，比一个假大空的"我全都能搞定"值钱得多。

> 案例：FEB 接手后从未发布过 SLA 声明。故障发生后，手淘 GOC 直接要求下掉 FEB——因为没人知道 FEB 的定位到底是给飞猪用的还是给集团用的。含混不清，连仲裁的门槛都没够到。

### 第三项：建立监控

**监控、监控、监控。** 重要的事情说三遍。这是最基本、却最容易被忽略的事项。

监控不是指"我有个 Grafana 看板"就完了。监控要做到：

1. **知道谁在用** — 通过埋点、日志、调用链追踪，掌握消费方的使用情况
2. **知道用的怎么样** — 核心指标（可用性、延迟、错误率）有实时告警
3. **知道出了问题影响谁** — 消费方级别的故障影响评估
4. **能主动发现** — 不依赖消费方来报障，你自己先知道

> 案例：某工程师的代码被 fork 了几百上千份，通过埋点的办法监控谁在用代码、他们的页面运行状况如何、浏览器 UA 分布、地域分布、操作系统分布、版本分布等。尽管代码的部署已经不受控制，仍然对运行状况一清二楚。出了问题可以直接钉到个人沟通，而不是在群里吆喝一声"该升级了"了事。**因为监控，所以不失控。**

### 第四项：学习安全生产准则和争议定责条款

这不是官僚主义，是保护自己的基本功课。你需要知道：

- 公司的安全生产准则里，哪些条款和你的系统相关
- 争议故障的定责逻辑是怎么定义的——哪些情况算提供方责任，哪些算消费方责任
- 跨团队协同的权责边界通常是怎么划分的

这些信息平时没人看，出了事之后就是仲裁的依据。你不看，对方看了，你就被动了。

## 二）故障复盘的专业姿势

当一个你接手的系统出了故障，消费方来找你定责时，复盘会上的表现直接体现了你的专业水准。以下是最常见的失败模式和正确姿势。

### 复盘会前四项功课

**参加复盘会之前**，必须完成以下准备。不是"到了会上再说"，是会前就做：

| # | 功课 | 做什么 | 不做会怎样 |
|---|------|--------|----------|
| 1 | 安全生产准则匹配 | 翻阅安全生产准则，找到与本次事件匹配的条款 | 对方引用条款你接不住，被动挨打 |
| 2 | 争议定责条款 | 找到争议故障定责条款，逐条比对哪些对你有利 | 丧失仲裁机会，只能被动接受定责 |
| 3 | 权责边界复盘 | 回顾协同双方的权责定义，确认你承诺了什么、没承诺什么 | 对方说"你没定义 SLA 所以你全责"，你无言以对 |
| 4 | "我"做错了什么 | 诚实地盘点自己的问题，准备好承认和改进方案 | 被评价为"通篇对自身问题只字不提"，态度问题比技术问题更致命 |

### 复盘会的致命错误

**错误一：不做功课就去参会。** 对安全生产准则、定责条款、权责边界两眼一抹黑。对方准备充分，你毫无招架之力。

**错误二：内部未对焦就上场。** 团队内部对系统定位理解不一致，带着歧义去参会，让对方看笑话。"反复跟我确认说这个系统到底是不是你在负责，是就说是，不是就说不是，干脆点。"

**错误三：只强调对方的问题，回避自己的问题。** 复盘记录通篇在强调对方的监控缺失、回归不到位，对自己的 SLA 缺失、容错不足只字不提。这已经不是技术问题了，是态度问题。

**错误四：缺少承担责任的姿态。** 基本态度应该是"谁都可以甩锅唯独我不能甩锅"——但因为功课没做好，表现出来的就是推卸和辩解。

### 复盘会的正确姿势

```
1. 会前完成四项功课，带着准备上场
2. 先承认自己的问题——主动承认比被指出来好得多
3. 再客观陈述事实——不带情绪，不指责对方
4. 引用条款和边界——有据可依，不是凭感觉争论
5. 给出改进方案——不只是"以后注意"，是具体的制度性改进
```

### 复盘邮件的结构

故障复盘的内部邮件不是活动日志，而是一次**管理沟通**。结构如下：

```
一）缘起——用 2-3 句话说清楚发生了什么
     不要流水账，抓住核心因果链
     "某系统出了某问题，导致某消费方某功能不可用，由客诉造成 P[N] 故障"

二）焦虑的复盘——把过程中不专业的地方摊开
     不是为了追责，是为了让大家看到差距
     逐条列出做得不好的地方，附具体表现

三）关于权责——如果你是服务提供方，怎么做更专业
     不是教科书理论，是从这次事件中提炼的实操清单
     每一条都有案例支撑

四）关于成长——从事件中提炼的教训
     不针对个人，针对团队普遍性问题
     鼓励大家自查手头的类似项目
```

## 三）服务提供者的四项基本功

不管你是维护一个二方包、一个共享服务、还是一个平台组件，只要你把自己定位为"乙方"（服务提供方），就需要做好以下四项基本功。

### 1. 定义 SLA

SLA 是你对消费方的承诺，也是你保护自己的边界。

**SLA 的最小内容**：
- 这是什么（定位）
- 负责什么 / 不负责什么（边界）
- 可用性承诺（99.9% / 99.5% / 尽力而为）
- 故障响应时间
- 变更通知机制

**SLA 的放置位置**：首页明显位置、README 开头、文档首页。不是藏在某个子页面里。

### 2. 监控

前面已经详细讲过了。再强调一点：**监控的粒度要到消费方级别**。不只是一个聚合的可用性数字，而是能回答"A 应用调用我的服务，今天成功率是多少"。

### 3. 客户第一

所有引用你服务的开发者都是你的客户。"我"要像在乎生命一样在乎服务在他们心中的口碑。

> 案例：某工程师写过一个组件 Demo，尽管只是一个 Demo，还是被开发者拿去用了。因为代码带了 `@author` 标记，对方遇到问题会来咨询。但凡有条件，都找到当事人坐在旁边，看对方怎么使用、怎么带参、怎么操作，收集反馈的同时也收集建议。你用心对待消费方，消费方就会用同样的回馈对待你——这些回馈帮你提高、让你少走弯路，是一笔巨大的财富。

### 4. 敢于承担责任

阿里的环境就是边界不清、充满变化。我们当然希望事事理清、边界干净、权责分明。但这不代表为了不犯错就畏手畏脚。

**正确的态度**：

- 敢于承诺，敢于靠前占位
- 过程要有技术性和专业性——不是拍胸脯蛮干，而是做完四项功课之后有底气地承诺
- 没做到就认栽，别废话

## 四）三个结构性陷阱

接手外部系统时面临的三个结构性现象，如果处理不好，就成了"糟糕的常态"，很容易暴雷。

### 陷阱一：依赖泛滥到失控

你的服务到底被谁用了，往往自己搞不清楚。一个二方包被十几个应用引用，一个共享接口被跨 BU 调用，消费方列表从未被梳理过。

**应对**：接手时就梳理消费方，建立消费方清单，定期更新。

### 陷阱二：甲乙方权责交叉

服务提供方（乙方）和消费方（甲方）职责交叉，甚至一段功能代码到底应当实现在应用层（甲方）还是框架依赖层（乙方）成了技术性问题——谁技术好谁来做。

**应对**：在 SLA 中明确定义每一层的职责。不是"你该做的你做"，而是"第 X 层以上的逻辑由消费方负责，第 X 层以下的由提供方负责"。

### 陷阱三：交接过程缺失

很多系统交接都是不得已——团队调整、组织职责变化、规划方向变更，甚至晋升结束后。交接过程中，谁负责什么、边界在哪里基本定义不清楚。

**应对**：交接时不只是移交代码权限，而是移交一份"接手清单"——消费方列表、SLA 定义、监控面板、已知问题列表、On-call 机制。如果没有这些，接手方应当在接手时主动补齐。

---

## 五）反模式

- **稀里糊涂接手** — 拿到代码权限就算接手了，不做任何功课。出了问题才发现不知道消费方是谁、不知道 SLA 是什么
- **出了事才补课** — 平时不建监控、不定义 SLA，故障发生后才手忙脚乱地补。来不及了
- **复盘会上甩锅** — 只强调对方的问题，回避自己的问题。被评价为"通篇对自身问题只字不提"
- **内部不对焦就上场** — 团队内部对系统定位理解不一致，带着歧义去参加跨团队会议
- **不做功课就去仲裁** — 对安全生产准则和定责条款一无所知，丧失仲裁机会
- **贪图大而全** — SLA 定义时什么都承诺，超出自己的能力范围。出了问题兜不住
- **没有监控就接系统** — "因为监控，所以不失控"。没有监控的接手等于裸奔
- **把"无意"当借口** — "我没想到"、"我不知道"——你的"无意"会被解读成各种样子

## 六）速查清单

### 接手系统时的检查清单

接手任何外部系统时，逐项确认：

- [ ] **消费方梳理**：所有依赖方列表已建立，区分核心/边缘消费方
- [ ] **消费方联系方式**：每个核心消费方有具名联系人
- [ ] **SLA 定义**：定位、边界、可用性承诺、响应时间已明确，放在明显位置
- [ ] **监控建立**：可用性、延迟、错误率的实时监控和告警
- [ ] **消费方级别监控**：能回答"X 应用调用我的服务，今天成功率是多少"
- [ ] **变更通知机制**：消费方有渠道知道你的变更（钉钉群、邮件列表、Release Notes）
- [ ] **安全生产准则**：已学习与本系统相关的条款
- [ ] **争议定责条款**：已了解争议故障的定责逻辑
- [ ] **On-call 机制**：明确了谁在什么时间响应什么问题
- [ ] **已知问题列表**：前任维护者的已知坑和 workaround 已记录

### 故障复盘会前检查清单

参加跨团队故障复盘会之前，逐项确认：

- [ ] **事实已核实**：故障时间线、影响范围、根因已确认
- [ ] **安全生产准则匹配**：找到了与本次事件匹配的条款
- [ ] **定责条款比对**：逐条比对争议定责条款，标记了哪些对我有利
- [ ] **权责边界确认**：回顾了我的 SLA 承诺（或承认 SLA 缺失的事实）
- [ ] **内部对焦完成**：团队内部对系统定位和责任归属已达成一致
- [ ] **自身问题盘点**：诚实列出"我做错了什么"，准备好承认和改进方案
- [ ] **改进方案准备**：不是"以后注意"，是具体的制度性改进（建 SLA、加监控、补流程）
- [ ] **态度校准**：基本态度是"谁都可以甩锅唯独我不能甩锅"
