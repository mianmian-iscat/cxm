# AI 转型的风险与副作用

> 本文件蒸馏自 2026 年 5 月用户技术团队 AI 转型规划。不是"AI 转型有多好"的宣讲稿，而是"AI 转型会踩哪些坑"的清醒清单。
>
> 大跃进风气之下如何回归理性——这是写这份文件的初衷。
>
> 本文件与以下文件互补：
> - `ai-native-talent-development.md` — 选人、用人、文化建设（"怎么做"）
> - `ai-era-viewpoints.md` — 观点八"反 AI 大跃进"提供了判断框架
> - `technical-leadership.md` — AI-Native 转型章节的三轴诊断和三阶段路径

## 一）总判断：不要"只要快"

AI 转型的核心理念是**打造超级个体**——以人为最小转型单元，推动一专多能，用 AI 原生范式重建终端研发的工作方式。

但还有一个"不要"同样重要：**不要口号式 AI 大跃进，只顾得快、丢了稳。**

两个大方向必须并存：
- **要**：超级个体、一专多能、AI 原生
- **不要**：跃进式考核、责任摊薄、专业稀释

很多团队只喊"要"，不喊"不要"。结果是表面转型成功，底下全是隐患。

## 二）六大副作用

### 副作用一：过于激进的考核目标

**问题**：把"目标"当"考核指标"压下去。

AI Coding 的生码率、采纳率、覆盖率——这些数字是**管理视角的判断依据**，不是**一线员工的硬性考核指标**。

这一点必须澄清，否则：
- 一线员工盲目追求 AI 生码率而忽视主要矛盾（比如输出物质量）
- "上有政策、下有对策"——把简单的 CRUD 全交给 AI 做，复杂场景还是自己写，覆盖率数字好看了，AI 接管深度停在 L1
- 团队为了完成数字搞形式主义——写了 CLAUDE.md 但内容是空话，建了 CI 但测试全是 pass-all

**原则**：目标用来牵引方向，KPI 用来考核结果。两者不是一回事。"AI 生码率 85%"是管理视角的方向判断，不是每个工程师的季度 KPI。

**反模式**：把 AI 覆盖率作为团队或个人的硬性考核指标。结果是数字到了，效果没到。

### 副作用二："多能"带来的责任重叠

**问题**：AI 带来的直接受益是效率提升，不是直接的责任扩大。

跨界和全栈后，如果责任田的边界不清晰，后果是"无人担责"——
- 人人都能写前端、人人都能写后端，但出了 bug 谁负责？
- Agent 交付了一段代码，是一线开发的责任还是 Agent 配置者的责任？
- 跨栈写了一段不熟悉的代码，出了性能问题谁兜底？

**跨界 ≠ 责任扩大。** 能力可以跨界，但责任必须有清晰的归属。

**具体做法**：
- **每行代码关联到责任人**——不是 AI 写的就没人负责，而是 AI 写的代码由提交者负责
- **Agent 交付之初就设计好 SLA**——这个 Agent 的产出质量预期是什么，谁来验收，出了问题谁响应
- **TL 比一线员工更多担责**——跨界后的管理复杂度上升，TL 不能只当"传话筒"
- **组织松绑**——给跨界的人更多的自主权和决策空间，而不是更多的审批流程

**这是 AI 转型带来的最大管理难题**：能力跨界的同时做好责任划分。做不到这一点，跨界就是灾难——大家都踩油门导致赛车，都想快，整体上反而慢。

### 副作用三：专业深度被稀释

**问题**：表面上快了，但产品表面下的技术隐患没跟上。

AI 让"糊一个产品"变得很容易。但"糊"出来的产品，下面的这些东西没跟上就立不住：
- 技术隐患（架构漂移、技术债积累）
- 风险隔离（故障爆炸半径控制）
- 防火墙约束（安全边界、权限控制）
- 架构守门（一致性、可维护性）
- SLA 边界（性能基线、可用性承诺）

**对于终端技术来说**，以下这些需要专业经验加持才能做好的事，很难刚开始就被 AI 完全代替：
- 客户端架构水平
- 页面性能体验
- 网关的保护性设计
- UI 测试的自闭环和有效性

**专业性必须始终坚持贯穿整个转型期的始终**。需要有专人为重要基建的架构（被 AI 影响）漂移而负责。

**一专多能的"一专"不能丢**——在体验工程域或终端工程域有一个深入的专业方向，这是饭碗，决不能丢。**决不能因为扩大知识边界的广度而丢失掉技术深度。**

### 副作用四：反 AI 代码治理

**问题**：AI 屎山积累得更快、味道更浓。

人写的代码是屎山，AI 的代码多数也是屎山——而且 AI 屎山积累的速度是人工的数倍。

如果没人管，AI 快速生成的低质量代码会迅速污染公海池。一线开发为了应付交付，快速 AI 上线一个东西，技术负债就这么来了。

**治理方案**：

需要单独的角色（类似独立的架构组或架构师）做定期扫除：

**AI 治理工程师**（参见 [ai-native-talent-development](ai-native-talent-development.md) 三个新角色章节）：
- 定期扫描 AI 生成的代码，识别低质量产物
- 制定 AI 代码质量标准（什么是合格的 AI 产出、什么必须返工）
- 责任分担：AI 治理工程师 30%，一线开发 70%

**代码治理标准**（需进一步探讨，但框架如下）：
- AI 生成的代码必须附带测试通过证据
- AI 生成的代码必须经过人工 Review 后方可合入
- AI 生成代码的责任人是提交者，不是 AI
- 定期清理低质量 AI 代码，避免污染公海池

**需求确认也需要治理**："PRD 反编译"——确认核心价值和关键目标，剔除信息噪音。很多时候 AI 生成的代码不好，不是因为 AI 不行，而是因为输入的需求本身就是模糊的。

### 副作用五：过于复杂的上下文工程

**问题**：Agent Friendly 的度怎么把握，谁也不知道。

项目的 Agent Friendly 改造是 AI 转型的关键（CLAUDE.md、rules、AGENTS.md、docs），但这个度很容易过犹不及：
- 仓库的文档积累越来越多后，会造成 AI 对项目理解的**失真**——上下文太多，AI 反而抓不住重点
- 过度文档化还会增加维护成本——文档和代码不同步，比没有文档更危险
- 不同类型的仓库需要的上下文深度不同——核心业务仓库需要详细，工具库可以简略

**这个边界在哪里，还需要进一步摸索。** 在这里把这一条列出来，是说这个边界是存在的，需要技术高手不断摸索出来。

**经验法则**：
- CLAUDE.md 控制在 200 行以内，超过就该拆分到子文件
- rules 只写真正影响代码质量的规则，不要把编码规范全塞进去
- docs 是 AI 辅助生成和维护的，不是人肉写的
- 定期 review 上下文的有效性——过期的上下文比没有更危险

### 副作用六：TL 能力模型下移

**问题**：传统 TL 的能力模型不够用了。

当前团队 TL（包括我在内）的思想仍然停留在传统的多角色分工、组织和协同的层次。当管理对象从员工变成 Agent 后，TL 的能力模型需要重新定义。

**粗浅的理解**：阿里组织三板斧（P9）"懂战略、搭班子、做导演"的要求会被下放到团队的腿部力量：

| P9 级要求 | 下移后的一线 TL 版本 |
|-----------|---------------------|
| 懂战略 | 懂业务（需求 & 价值判断） |
| 搭班子 | 搭各种角色的 Agent，并为 Agent 搭建 workflow |
| 做导演 | 除了"导演"项目的实施，还有 AI 工程导演（spec → plan → 执行 → 验收的全链路） |

**这不是降低标准，是标准在变**——以前 TL 管人就行，现在 TL 要管人 + 管 Agent + 管人机协同的工作流。

**和设计师/PD/QA 的协同方式也在变**——结队编程：
- **前半程**（和 PD 衔接）：需求 → 概设 → 详设 → UI 稿 → Spec/Design/Plan
- **后半程**（和 QA 衔接）：TDD → CR → CI → 灰度/部署

TL 需要理解并驱动这个新的协同模式，而不只是"排期 + 催人"。

## 三）转型原则

四条原则，每一条都是"大跃进"的对立面：

1. **存量求稳，增量求变**：老业务不强行翻新，新项目和 V10 级战略项目全面 AI 原生
2. **示范带动，不搞大跃进**：V10 和度假经营工具做示范，沉淀方法论后再推广
3. **能力先行，组织跟进**：先具备 AI 原生能力，再调岗位和绩效
4. **度量驱动**：用生码率、采纳率、交付周期、bug 率数据验证效果

**"存量求稳"为什么排第一？** 因为 3300+ 仓库中绝大多数是老项目。如果强行全部翻新，团队会被拖垮。先在新项目和战略项目上跑出标杆，证明方法论有效，再逐步推广到存量。

**"能力先行"为什么排第三？** 因为很多团队的顺序是反过来的——先调组织、先改 KPI，指望组织变革倒逼能力成长。这是本末倒置。能力没到位之前，组织和 KPI 的调整只会制造焦虑，不会带来真实效果。

## 四）对标：我们更像谁

| 方向 | 更像谁 |
|------|--------|
| Harness 工程：spec/tdd/AutoTest | Google |
| 单兵交付 | Meta |
| 代码仓库的 Agent Friendly | Google |
| 创意小队 | Meta |
| 弱化技术栈边界 | Meta |
| 宪法规约/工程规格一致性 | Google |
| 责任归属 | Amazon |
| 保持稳定性红线 | Amazon |
| Copilot 工具化 | 微软 |

**对比亚马逊和 Google**：

亚马逊的 Ownership 文化导致它几乎没有 AI 转型迹象——因为成本敏感、基建薄弱、责任摊薄、业务驱动。每行代码都能回溯到责任人（而不是 AI），ROI 文化让"用 AI 替代自己"这件事缺乏动力。

Google 走了另一条路——Core Infra 部门（280 人，平均层级 P8+~P9）负责底层基础架构，只背稳定性指标，不背其他任何指标。一个几乎不计成本的平台团队托底，卸掉了前台业务的负担，迈过了 AI Native 组织转型的拐点。

**对我们的启发**：
- 飞猪业务形态类似亚马逊，AI 转型阻力跟亚马逊完全一样
- 但用户技术团队能从 Google 借鉴的是：基建归一、责任归一、高 P 密集型基建团队、原子化能力网关建设、结队编程 + 前线轻型敏捷组织

## 五）可预见的风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| AI 代码质量不可控 | 线上故障、技术债积累 | TDD 卡点 + QA 自动评估 + 人工 Review；代码提交人为责任人 |
| 责任边界混乱 | 人人都负责 = 人人都不负责 | 基建要有负责人，必备 SLA；跨界意味着担责，责任扩大必须配套激励措施 |
| Skills 集市推进受阻 | 工具碎片化持续 | 统一规范 + 核心同学带头贡献；渐进式（能力 → 岗位 → 组织），用提效正反馈建立信心 |

## 六）反模式总结

- **反模式：把目标当 KPI**。"AI 生码率 85%"是方向，不是考核。压下去就是形式主义。
- **反模式：能力跨界 = 责任扩大**。跨界是能力维度的事，责任必须有清晰归属。
- **反模式：专业深度让位于广度**。一专多能的"一专"不能丢，丢了就是全栈废柴。
- **反模式：AI 代码不上治理**。AI 屎山比人工屎山积累更快，必须有专人定期扫除。
- **反模式：上下文越多越好**。Agent Friendly 有度的边界，过犹不及。
- **反模式：TL 只管人不管 Agent**。AI 时代 TL 要管人 + 管 Agent + 管人机协同工作流。
- **反模式：先改组织后补能力**。能力先行，组织跟进。顺序反了只会制造焦虑。
- **反模式：存量翻新**。3300+ 仓库强推 AI 改造 = 团队被拖垮。存量求稳，增量求变。
