# 规划与战略

诊断、战略选择、战役选择、排序、资源配置、里程碑、度量、依赖关系，以及将宽泛方向转化为可执行计划的方法。

---

## 一）诊断方法论——站在时代的十字路口

规划之前，先理解现状。规划始于"看清事实"，而非"设定愿景"。诊断的深度决定了后续一切的质量。

### 多轮多视角诊断

单次诊断不可靠，必须从多个角度进行多轮诊断，在讨论方案之前，将原始发现归类为 3~5 个核心问题域（或称"核心矛盾"）。从原始观察直接跳到方向，会跳过关键的结构化步骤。

**自下而上：一线体感采集**

从团队中收集痛点——一线做事的人能看到管理层看不到的问题。收集时不做过滤、不做回应，只忠实记录真实感受。

以一次典型的技术共创为例，先让每位同学同步三件事：（1）过去一年/现在团队现状、业务支撑体感认知；（2）TL 信息输入；（3）核心痛点分组讨论。原始体感往往集中在以下几类：

- 编码规范、一致性、效率（"代码编码规范执行不彻底，各类命名混乱，不成体系"）
- 技术选型缺少深入的讨论，缺少达成一致的过程，缺少准确的判断
- 外部依赖了解深度（"对底层技术体系不了解，出问题需要依靠外部排查"）
- 历史包袱（"历史包袱太重，新业务累在老代码上；业务归属不确定，新人不敢动老代码"）
- 架构与业务过于分离（"基础架构组做了很多功能，但业务无感知，重复建设情况严重"）
- 体系站队问题（"在支付宝/手淘体系之间摇摆""脚踏两条船，了解所有系统，但所有系统都不能深入了解"）

这些原始感受非常有价值，但不能直接作为方向，需要先归类为结构化的核心矛盾。

**自上而下：数据走查与指标对标**

基于数据的关键指标和用户旅程走查。走查真实产品，而非看板。关注的典型指标维度：

- 性能体验：启动时间、页面加载、闪退率（对标手淘/行业头部，看差距是收敛还是拉大）
- 包体积与工程健康度：包体积（iOS 安装包是否逼近阈值）、SDK 占比（自有 vs 外来，如"猪客包内 60% 以上是外来 SDK"）、Bundle 数量
- 用户指标：DAU、新增设备数、留存率（次留/七留/三十留）、粘性
- 业务指标：转化率、交叉渗透率、类目覆盖率
- 研发效率：发版周期、自动化覆盖率、灰度能力

**外部校准：竞争对标**

将竞争对手的表现作为外部参照点，避免闭门造车。对标有三个用途：

1. **发现问题** — "我们在哪些方面弱于竞争对手？"（交互设计、产品体验、内容等方面与行业一流水平都有差距）
2. **设定目标** — "在 X 上达到行业领导者同等水平"（对标携程的服务闭环、美团的本地生活渗透、马蜂窝的内容深度）
3. **验证结果** — "我们在这个指标上是否缩小了差距？"

精准选择对标对象：对标相关领域的行业领导者，而非模糊的"行业标准"。对标对象按域拆分，而非笼统地对标一个竞品——在内容域对标马蜂窝/小红书，在服务闭环域对标携程，在本地生活渗透域对标美团。

**注意**：过度依赖对标会产生跟随者心态。用它来校准，而非用它来制定战略。差异化需要超越竞争对手已有的做法。

### 从体感到矛盾：核心问题域的结构化

将多轮诊断的原始发现，归纳为 3~5 个核心矛盾。矛盾是结构性的张力，不是具体的问题点。典型的矛盾表述模式：

> - 业务平台化互通 与 类目垂直化端技术体系 之间的矛盾
> - 性能体验提升 与 技术体系收敛 之间的矛盾
> - 飞猪自有技术体系 与 集团统一技术基建 之间的矛盾

这三个矛盾（以飞猪 2017~2019 年为例）不是拍脑袋的，而是从一线体感、数据走查、外部对标三个维度交叉验证后提炼出来的。每个矛盾背后都有具体的数据支撑和一线案例。

矛盾提炼的质量决定了后续战略选择的质量。好的矛盾表述应当：
- 两侧都是真实的诉求，不是"正确 vs 错误"的伪矛盾
- 能够映射到具体的技术决策和资源分配
- 团队成员读到时有共鸣（"对，这就是我天天纠结的"）

### 常见诊断失败

| 失败类型 | 表现 | 修正方法 |
|---------|------|---------|
| 跳过诊断 | 计划从方案出发，而非从问题出发 | 要求在任何计划之前先写"现状"部分 |
| 表面诊断 | 列举症状而非根因 | 追问根因——"代码可读性差"是症状，"缺少编程范式，整体方向不统一"是根因 |
| 乐观诊断 | 对一切做最好假设 | 要求每个结论都有证据；标注假设 |
| 孤立诊断 | 脱离上下文看单个团队/领域 | 梳理依赖关系和上下游影响 |
| 单视角诊断 | 仅有管理层视角或仅有数据视角 | 进行多轮诊断（自下而上 + 自上而下 + 外部） |
| 分析瘫痪 | 诊断永不结束，决策不断拖延 | 为诊断设定时间盒；接受"足够好"后继续推进 |

## 二）战略选择与显性化取舍

战略是关于选择做什么以及不做什么。

承上启下——诊断给出"我们在哪里"和"核心矛盾是什么"，战略选择要回答"我们要去哪里"以及"我们选择走哪条路"。

### 从矛盾到方向

战略方向不是凭空产生的，而是从诊断阶段提炼的核心矛盾中推导出来的。每个核心矛盾需要给出一个显性化的判断——倾向哪一侧、为什么、什么约束驱动了这个判断。

以飞猪端技术体系为例，面对"自有技术体系 vs 集团统一技术基建"这个矛盾，判断不是一刀切的，而是分层框定边界：

- **顶层业务 Bundle**：需要足够灵活的嫁接（业务支撑需要），飞猪自建
- **中间容器规范**：保持集团标准统一（规范和标准互通），借力集团
- **底层工程基建和 SDK**：要保持版本一致（能力复用），完全依赖集团

这个三层边界设计，就是对矛盾的结构化求解。不是"我们全自建"或"我们全跟手淘"，而是在不同层次上做出不同的取舍。

### 四字战略方向的表述

战略方向用四字动词短语表述，每个方向背后有明确的业务目标和技术路径。例如：

- **提升留存**（用户粘性增长乏力 → 完整旅行体验打造 → 端侧体验优化）
- **拓宽流量**（三端格局被框定 → Dolphin/飞流体系建设 → 被动用户转化通道）
- **夯实基建**（架构 2.0 问题累积 → 淘系体系迁移 → 架构 3.0 落地）
- **赋能商家**（商家私域诉求 → 行业化店铺搭建 → 店铺中后台工具链）

每个方向不是一句话，而是一个完整的叙事链：**业务问题 → 技术路径 → 预期结果**。

### 显性化取舍

当多个方向相互竞争时，不要回避张力，将其结构化：

1. **列出矛盾对** — 公开列出，而非假装矛盾不存在。典型矛盾：
   - 平台统一 vs 垂直深耕
   - 性能提升 vs 技术收敛（"要达到手淘水平需要从底层架构开始改造"vs"目前优化事项对性能体验提升虽有效果，但与手淘差异依然很大"）
   - 自主可控 vs 生态借力（"打铁还靠自身硬"vs"站在巨人的肩膀上"）
   - 业务驱动 vs 技术驱动（"目前飞猪阶段是业务驱动"vs"TL 技术前瞻性指导业务线开发"）

2. **给出取舍判断** — 对每一对，倾向哪一侧？

3. **给出推理** — 什么证据或约束驱动了这个判断？（DAU 量级、业务阶段、团队能力、时间窗口）

这三步模式（矛盾 → 判断 → 推理）防止最常见的战略失败：什么都选、什么都不放弃。"我们不做什么"应当与"我们做什么"一样被充分记录。

### 战略选择中的"不做什么"

显性声明不做的方向，和做的方向同等重要。以飞猪 2017 年为例：

- **不做**独立的 AR/VR 方向（行业尚未成熟，资源有限）
- **不做**自建的跨端渲染引擎（借力 DynamicX 共建，而非自研）
- **不做**大规模基础中间件自研（"站在巨人肩上不是拿东西过来用，而是思维方式站在同一层次"）

这些"不做"的决策同样需要记录和推理，否则后续很容易被"为什么不也做一下"的声音动摇。

### 战略选择反模式

- **万事皆优先** — 如果什么都重要，那就什么都不重要。强制排序。
- **只选不弃** — 说"我们要做 A、B、C"却不说放弃什么。
- **跟风** — 别人做什么就做什么，不分析适配性（"需求驱动/外因驱动带来的变化导致积累不深，频繁造新轮子"）
- **战略即愿景** — "我们要成为 X 领域的最佳"，但没有路径。
- **回避矛盾** — 承认多个方向在竞争，却从不说哪个胜出以及为什么。

## 三）战役选择与分类

并非所有项目都值得同等投入。承上启下——战略方向确定后，需要将其拆解为具体的战役，并对每个战役进行分类，匹配不同的投入和管理方式。

### 战役分类框架

| 类型 | 描述 | 投入方式 | 管理方式 | 举例 |
|------|------|---------|---------|------|
| **必赢之战** | 失败意味着生存风险或错失关键机会 | 全力投入、最强人员、密切跟踪 | 主动指挥，TL 直接盯 | 架构 3.0 迁移、双十一大促支撑 |
| **战略投资** | 对未来重要但非紧迫，需要耐心 | 专人投入、定期评审 | 委派并设检查点 | 端运维体系建设、LBS 技术深耕 |
| **基本盘** | 为留在牌桌上而必须做的事 | 最小可行投入 | 标准流程 | 日常版本发布、线上问题修复 |
| **期权/探索** | 探索性，可能没有回报 | 小团队、时间盒 | 轻量管理、明确终止条件 | 游戏互动方向、WebAR 尝试 |

### 战役选择的原则

1. **从目标出发** — 我们在朝什么结果推进？每个战役必须能回答"它推进了哪个战略方向？"
2. **按影响力和可行性打分** — 高影响力 + 可行 = 优先。
3. **检查资源匹配度** — 我们能否真正为优先选择配足资源？如果最强的人在基本盘上，必赢之战就是空话。
4. **定义终止条件** — 如果不见效，何时止损？期权型战役尤其需要："本季度末如果原型验证未通过则终止，人员回归主线。"

### 战役间的关系

战役不是孤立的。一场战役的产出可能是另一场战役的输入：

- 架构 3.0 的完成（必赢之战）是 DynamicX 接入（战略投资）的前提
- Dolphin 营销工具体系（战略投资）为流量转化通道试错（基本盘）提供基建
- 端运维能力建设（战略投资）依赖全链路日志（基本盘）的补全

战役间的依赖关系需要在选择阶段就梳理清楚，而非执行中才发现。

## 四）排序与依赖关系

顺序很重要。有些事必须在其他事之前完成。

### 依赖映射

1. **列出所有工作项**
2. **对每一对，问："A 是否需要在 B 开始之前完成？"**
3. **画出依赖图**
4. **识别关键路径** — 最长的依赖链
5. **将管理注意力聚焦在关键路径上**

### 排序原则

- **先疏通再建设** — 在增加功能之前先消除约束（"推倒重来成本很高，折中方案选取过程困扰很多"→ 先解决历史包袱，再上新方向）
- **先打基础再装修** — 基础设施优先于打磨（底层架构迁移先于业务层共建，"飞猪底层基建迁移到淘系，为 2018 年业务层的淘系打通打下基础"）
- **先验证再规模化** — 在小范围证明有效后再推广（度假类目导购链路先落地，再做跨类目覆盖）
- **先对齐再执行** — 在细化工作之前先就方向达成共识（"技术选型缺少深入的讨论，缺少达成一致的过程"→ 先对齐选型原则，再铺开发工作）

### 半年节奏（S1 筑基 / S2 冲刺）

将年度周期分为上下半年，刻意采用不同的节奏：

- **S1（上半年）— 筑基**：容忍投入期工作。聚焦基础设施升级、架构改进、工具建设、债务偿还。接受回报不会立即可见。这是做艰难结构性工作的时段。
  - 典型 S1 工作：容器改造、框架升级、编码规范收口、全链路日志补全、SDK 梳理瘦身
  - S1 心态："打铁还靠自身硬"

- **S2（下半年）— 冲刺**：追求产出期结果。聚焦交付、优化和数据验证的成果。年底目标的紧迫感让团队对 S1 投入是否产生回报保持诚实。
  - 典型 S2 工作：双十一大促支撑、新业务上线、性能数据验证、导购场景覆盖扩展
  - S2 心态："用结果证明 S1 的投入是值得的"

这个节奏有两个作用：保护基础性工作不被业务压力无限期推迟，并建立内置的问责闭环——S2 的交付验证 S1 的投入。

**跨周期项目**：有些计划横跨多个 S1/S2 周期（如端运维体系建设、LBS 技术深耕）。将其作为独立 track 管理，设定自身的里程碑节奏，而非强行套入半年节奏。

**应对变化**：当业务环境发生重大变化（市场变化、组织调整）时，S1/S2 节奏可能需要压缩或重组。原则不变——即使在缩短的时间线内也要区分"筑基"和"冲刺"阶段。

## 五）资源配置与组织对齐

资源总是有限的。刻意配置。

承上启下——资源配置不是规划之后的执行细节，它是战略本身的核心部分。团队的形态和预算的约束直接决定了哪些战略是可行的。资源约束不仅是战略的限制条件，更是影响战略选择的输入。

### 配置框架

1. **盘点现有资源** — 人员（按技能层次：架构、业务开发、基础中间件、工具链）、时间、预算、工具
2. **盘点所需资源** — 按战役、按阶段（必赢之战需要最强人员全职投入，战略投资需要专人但可兼职，基本盘按最低配比）
3. **识别缺口** — 哪里短缺？
4. **做出选择** — 砍范围、借资源（跨团队协作/共建）、招人、或延期。选择的依据是 ROI——每个战役的投入产出比是多少，优先投 ROI 最高的（[roi-thinking](roi-thinking.md)）
5. **明确风险** — 如果资源不到位会怎样？

### 组织对齐——战略需要组织架构支撑

每个战略计划必须回答三个组织问题：

1. **谁负责？** — 每个战略方向需要一个对结果负责的具名负责人。不是"团队"，而是具体的人。
   - 基础线：@吾常 团队负责端侧容器和全链路日志
   - 前端体系：@圣司 团队负责 Clam 开发体系和 Weex 基建
   - 内容互动：@剑轩 团队负责内容中心、内容分发、关系系统
   - 无线服务端：@敏刚 团队负责穹顶网关和触达体系

2. **资源如何配置？** — 每个方向的人员配比要具体到数字。
   - 必赢之战：N 人全职（N 取决于战役规模，但必须是足以打赢的数）
   - 战略投资：M 人专职 + 定期评审
   - 基本盘：按最低人力配比保障
   - 期权/探索：2~3 人小团队 + 时间盒

3. **组织结构是否需要调整？** — 战略所需的新团队边界、角色调整、能力缺口。
   - 是否需要新建架构组？（"目前无线不存在架构组"→ 是否需要、什么规模、向谁汇报）
   - 是否需要从业务开发中分化出基础中间件角色？
   - 跨域方向是否需要虚拟团队？

### 共建与借力原则

飞猪作为集团生态中的"小 App"，资源配置的核心命题是：如何在有限的团队规模下，最大化利用集团中台能力，同时保持行业体验的独立性。

**借力原则**（"站在巨人的肩膀上"）：
- 底层基建（网络库、登录、监控等 SDK）完全复用集团，不自研
- 容器规范跟随集团标准，但在设计规范内保留飞猪个性化空间
- 中间件能力（配置下发、消息推送等）复用集团基建，做飞猪场景化封装

**自建原则**（"打铁还靠自身硬"）：
- 行业特性强的领域（大导购、LBS、端运维中的旅行场景）必须自建
- 集团能力尚未覆盖的领域（端侧全链路日志、位移数据采集）先行自建，未来可反哺集团
- 业务层表达（DynamicX 模板、行业店铺搭建）需要自建，因为行业模型差异大

**共建原则**（"不是选择跟随，而是参与进去"）：
- 对于集团正在建设的核心能力（如 Weex、DynamicX），不只做使用方，要参与共建
- 共建的产出（如蜂鸟 WeexUI 库）服务集团内十几个产品，同时提升飞猪在集团技术生态中的话语权

### 资源配置反模式

- **撒胡椒面** — 每个项目都有人，但没有哪个项目人够
- **忽视上下文切换成本** — 同时参与 3 个以上项目的人什么都做不好
- **乐观的产能规划** — 假设 100% 产出，不留余量
- **不指明取舍** — 接受新工作却不同时放下其他事情
- **战略无组织** — 漂亮的计划却没有具名负责人、没有人员配置数字、没有结构性支撑
- **脚踏两条船** — 在多套体系之间摇摆，导致"了解所有系统，但所有系统都不能深入了解"

## 六）里程碑与度量体系

### 目标分层分解

战略目标必须分解为四个层次，每层回答不同的问题：

| 层次 | 回答的问题 | 示例 | 时间跨度 |
|------|----------|------|---------|
| **目标（O）** | 我们要去哪里？ | "打造业界最佳的旅行移动体验" | 年度 |
| **关键结果（KR）** | 如何知道到达了？ | "核心场景页面加载 P95 < Xs（YoY -Y%）" | 半年 |
| **项目** | 我们要建设/做什么？ | "资源调度架构重构""大导购跨类目覆盖" | 季度 |
| **里程碑** | 何时达到什么水平？ | "S1 结束前完成架构设计并灰度验证" | 月度/双周 |

量化的 KR 是区分真实目标与口号的关键。如果一个 KR 无法度量，它就是愿景而非结果。

**数据密度的要求**：每个 KR 都应当有具体的数字，并附带同比/环比对比（括号标注 YoY 变化）。示例格式：

- 启动时间：目标 Xs（当前 Ys，YoY -Z%）
- 闪退率：目标万分之 A（当前万分之 B，对标手淘万分之 C）
- DAU：目标 Nw（当前 Mw，YoY +P%）
- 包体积：目标 XMB（当前 YMB，QoQ -Z%）
- 自动化覆盖率：目标 X%（当前 Y%）

当数据脱敏时，保持格式但隐去具体数字："目标 Xs（当前基线的 N% 降幅，对标竞品 Y 水平）"。

### 里程碑设计

好的里程碑具备：

- **二元的** — 完成或未完成，不存在"80% 完成"
- **有意义的** — 代表朝目标的真实进展，而非仅仅是活动
- **有时限的** — 有具体日期（"S1 结束前""Q2 末"）
- **有负责人的** — 有人对达成它负责

里程碑的典型模式（以架构演进为例）：

| 阶段 | 里程碑 | 时限 |
|------|--------|------|
| 架构设计完成 | 完成架构 3.0 设计方案并通过评审 | S1 第 2 月 |
| 灰度验证 | 核心模块灰度 X% 用户，稳定性指标达标 | S1 第 4 月 |
| 全量上线 | 全量发布，旧架构下线 | S1 结束 |
| 业务验证 | 基于新架构的首个业务场景上线并验证效果 | S2 第 1 月 |
| 规模化覆盖 | N 个业务场景完成迁移 | S2 第 3 月 |

### 度量渐进式完善

度量体系不需要从第一天就完美。它随着团队理解的加深而成熟：

| 阶段 | 特征 | 示例 |
|------|------|------|
| **早期** | 方向性，定性可接受 | "提升性能"——方向正确比精度更重要 |
| **成长期** | 半量化，有基线 | "页面加载时间从当前基线降低 N%" |
| **成熟期** | 精确、多维、有对标 | "P95 加载时间 < Xs，覆盖 95% 会话；核心场景优于竞品 Y" |

不要让完美度量体系的缺失阻塞规划。从能度量的开始，设定完善的日期，持续迭代。坚持跟踪粗糙指标的团队，远胜于等待完美指标的团队。

### 指标体系的多维度设计

好的指标体系是多维度、多粒度的：

- **结果指标** — 我们是否达成了结果？（转化率、留存率、DAU、GMV）
- **过程指标** — 投入端是否健康？（迭代周期、部署频率、发版节奏）
- **健康指标** — 系统是否可持续？（技术债务比、包体积增长趋势、Crash 率、团队士气）

按相关维度分解每个指标：

- 按版本（V1 vs V2 vs V3 的 Crash 率趋势）
- 按场景（首页 vs 搜索 vs 详情 vs 下单 的加载时间）
- 按用户群体（新用户 vs 老用户、行中用户 vs 非行中用户——"行中用户日活占比接近 30%，这是一个非常高的比例"）
- 按端（iOS vs Android vs H5 的一致性）

**注意**：量化偏差——只度量容易量化的，忽略重要但难以度量的工作（文化、士气、长期能力建设）。每个周期至少安排一个定性检查点来覆盖这些维度。

### 常见度量失败

- **虚荣指标** — 好看但不能预测成功（累计用户数 vs 活跃留存率）
- **只有滞后指标** — 看到数字时已经来不及行动
- **指标过多** — 什么都跟踪，就什么都不关注
- **易被刷量** — 可以改善数字但实际结果并未改善
- **只有聚合值** — 单一平均值掩盖了特定群体或场景的回退
- **幸存者偏差** — "端稳定性数据实际存在大量幸存者偏差"，行中用户、弱网环境下的问题被数据采集机制过滤掉了

## 七）从方向到计划——架构演进的叙事

将宽泛方向转化为可执行计划，核心是构建一条从"旧貌"到"新颜"的演进叙事线。好的规划文档读起来像一部技术演进史——"从哪里来，经过什么转折，到哪里去"。

### 转化过程

1. **将方向表述为可度量的结果** — "大导购"→ "年底前跨类目导购场景覆盖率达到 X%，场景搭建效率提升 Y%"
2. **诊断现状** — 我们在这个指标上现在处于什么位置？（"目前飞猪在流量格局上依然被框定在三端""诸多业务纵深内的商品模型、内容模型和容器模型的统一尚未完成"）
3. **识别差距** — 缩小差距缺少什么？
4. **选择战役** — 优先缩小哪些差距？
5. **设计里程碑** — 如何跟踪进展？
6. **配置资源** — 谁做什么？
7. **定义运营节奏** — 如何跟踪和调整？

### 架构演进叙事模板

每个技术方向的规划，都应当能回答这条叙事线：

> **旧貌**：[历史状态，缘起和背景矛盾]
> → **转折点**：[触发变化的事件或判断]
> → **新颜**：[目标状态和达成路径]

以飞猪端架构为例：

> **旧貌**（架构 2.0）：基于支付宝 MPass 的框架（Platform），面临"用支付宝的架构做淘宝的业务"的困境，容器自建但规范分裂，包体积一度逼近 140MB，iOS Bundle 270+，三端不一致导致问题收口困难。
>
> → **转折点**：2017 年初成立用户技术部，启动飞猪移动端战略，决定底层基建迁移到淘系。"在航母庞大的移动端体系中，摘取所需，跟自建技术拼装起来。"
>
> → **新颜**（架构 3.0）：Mashup App 架构，三层边界清晰（顶层业务 Bundle 灵活嫁接 / 中间容器规范集团统一 / 底层工程基建版本一致），完成 MTL 和 Atlas 改造，DynamicX 共建落地，包体积控制在 X MB 以内（YoY -Y%）。

这条叙事线不是装饰，而是规划的核心骨架——它让每个参与者理解"为什么这样做"而不只是"做什么"。

### 计划文档的结构

一份完整的规划文档通常包含这些部分（以飞猪历年规划为参考）：

1. **历史回顾**（"旅客的原始积累 2014~2016"）— 用 1~2 页篇幅回顾上一周期的成果和遗留问题，建立上下文
2. **现状诊断**（"猪客端体系雏形""矛盾与取舍"）— 当前架构全景、核心矛盾、数据现状
3. **外部环境**（"机遇和挑战——战略 & 外部环境"）— 竞争格局、集团战略变化、行业趋势
4. **战略方向与取舍**（"猪客端架构演进 3.0""Web & Native 的再融合"）— 方向选择、矛盾求解、不做什么
5. **各领域计划**（"猪客服务端体系""内容互动技术体系""共建领域 & 创新"）— 按域展开的具体计划
6. **组织与人才**（"人才梯队"）— 组织调整、人员配置、能力缺口

### 计划质量检查清单

- [ ] 现状诊断有证据支撑（多轮、多视角：一线体感 + 数据走查 + 外部对标）
- [ ] 核心矛盾已结构化（3~5 个，每对矛盾有显性化取舍判断）
- [ ] 竞争对标已按域完成（内容域、服务域、流量域分别有对标对象和差距分析）
- [ ] 目标状态可度量（每个 KR 有数字、有 YoY/QoQ 对比格式）
- [ ] 战略选择已显性化（做什么 + 不做什么，同等详细）
- [ ] 架构演进叙事完整（旧貌 → 转折点 → 新颜）
- [ ] 战役已分类（必赢 / 投资 / 基本盘 / 期权）
- [ ] 依赖关系已映射，关键路径已识别
- [ ] 半年节奏已定义（S1 筑基 / S2 冲刺，各含典型工作项）
- [ ] 资源已配置，有具名负责人和组织对齐
- [ ] 共建/借力/自建原则已明确
- [ ] 目标已按四层分解（O → KR → 项目 → 里程碑）
- [ ] 里程碑是二元的、有时限的、有负责人的
- [ ] 指标是多维度的（结果/过程/健康），并按版本/场景/用户群/端分解
- [ ] 风险已列出并有应对方案
- [ ] 不确定性高的举措已定义终止条件
