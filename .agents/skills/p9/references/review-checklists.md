## 决策评审

### 检查项

- [ ] **问题定义用了数据，不是形容词** — "App 流量推高很快遇到天花板"比"流量增长乏力"好，前者有结构性诊断
- [ ] **方案对比有取舍记录** — 不是列了三个方案然后说"我们选了 B"，而是说清楚选了 B 之后放弃了什么、为什么 A 和 C 不适合当下
- [ ] **决策有具名负责人** — "@张三 牵头明确了两件事"这种写法，不是"团队决定"
- [ ] **可逆性已评估** — "quick and dirty 多数情况下会更有效"这种判断，说明已经评估过这个决策的可逆性（创新产品形态，可以快速试错）
- [ ] **假设已暴露** — "前提是产品回归行业后，在平台工具层面提供强有力的精细化运营能力"，不是把假设藏在方案里
- [ ] **成本有依据** — "人力投入 113 人月"比"投入较大资源"好，前者可追溯
- [ ] **决策者已确定** — "本周和李四一起明确了"，指名道姓
- [ ] **截止日期已设定** — "月底之前搞定"、"计划一期三月底之前上线"
- [ ] **结论先行** — 第一段就给出建议，不是先铺背景再慢慢引出结论

### 危险信号

- 只呈现了一个方案，然后说"建议采纳"
- "大家都同意"但没有记录谁参与了讨论、谁反对过
- 成本是"预计"但没有拆解依据
- 没有为结果指定负责人——"团队将负责"不是负责人
- 可逆决策用了不可逆决策的论证深度（反过来也是）

### 反模式

| 反模式 | 真实文档中的好写法 |
|--------|-------------------|
| "经过充分讨论，大家一致同意" | "本周和李四一起明确了内容方向的视频体系升级计划" |
| "综合考虑各方面因素" | "第一要强化客户端产品和基础服务体验，第二是借助流量冲锋为抓手，第三是技术侧的兜底" |
| "这个方案风险可控" | "最大的挑战在于两个，一是要清晰的明确服务主体...二是整个产品的定位" |

## 规划评审

### 检查项

- [ ] **数据密度足够** — 规划中每个方向都有当前基线数据，不是"提升用户体验"而是"Crash 率控制在万四以下"、"Weex 页面秒开率均值 91.6%"
- [ ] **竞对对标已做** — "对标竞品建设飞猪逆向工程能力"、"对标携程"这种写法，说明已经看过行业水位
- [ ] **S1/S2 节奏清晰** — 规划按半年为周期拆分，有明确的里程碑节点，不是"年内完成"
- [ ] **资源分配到人** — "@王五 在推进中"、"赵六、李四、孙七、周八和各行业"，不是"相关团队负责"
- [ ] **战役已分类** — 必胜（超级对齐）、投资（问一问 2.0）、基本盘（端架构治理）、可选（PWA 探索），不是所有事情都是"第一优先级"
- [ ] **取舍已命名** — "本次战役仍然聚焦在 App 端，手淘和支付宝端未涉及"，说清楚不做什么
- [ ] **组织策略配套** — 规划不能只说做什么事，还要说组织怎么调："出 2 进 1 补员"、"三个专项的人力协调"、"二级预备 TL 的培养"
- [ ] **风险带量化** — "飞猪全域六月下旬评审通过的需求总数是 2900 多个，与此同时研发人员需求并行数量是 4~5 个"，风险不是"可能存在"而是有数字
- [ ] **承上启下有交代** — "借助吴九趟平手淘小程序坑，春运完成直连收尾和 PC 通道建设，借力 POI 详情改造完成 Flutter 基建，为 22FY 打下很好的基础"
- [ ] **跨期对比** — "两期战役带来的变化"这种格式，拿上一期和这一期做对比，看趋势而不是孤立看当下

### 危险信号

- 所有事项都是"第一优先级"
- 没有命名任何取舍——"我们什么都能做"
- 里程碑模糊："提升 X"但没有可衡量目标
- 资源分配写"团队"不写人名
- 时间线没有依据："我们觉得需要 3 个月"
- 规划中看不到组织结构的变化——事在变但人不变，说明规划没落地

### 反模式

| 反模式 | 真实文档中的好写法 |
|--------|-------------------|
| "全面提升用户体验" | "解决一批（132 个体验问题）竞对差异的问题，缩小竞对差距" |
| "加大技术投入" | "校招 5HC 全部投入用户域" |
| "存在一定风险" | "7、8 月份密集的入淘、营销和会员等项目冲突" |
| "年内完成" | "一期 5/10~6/17，二期 6/20~9/2" |

## 项目评审

### 四级评价标准

项目评审的核心是给出达标判断。不是模糊的"进展顺利"，而是用四级标准衡量：

| 等级 | 含义 | 写法示例 |
|------|------|----------|
| **达标** | KO 目标全部实现，核心指标达成 | "达标。占座耗时从 15s 压缩到 10s 以内，直连成功率从 72% 提升到 90%" |
| **基本达标** | 大部分目标实现，有少量遗留但可控 | "基本达标。战役既定范围目标达成率是 OK 的，对导购、流量等项目支撑到位" |
| **部分达标** | 部分目标实现，关键指标有缺口 | "部分达标。享逛 UV CTR 55.7%，无固定入口，UV 过低" |
| **未达标** | 核心目标未实现，需要根因分析 | "未达标。行程 2.0 页面 UV 总量和创包量均未达标" |

### 检查项

- [ ] **每个子项目有四级判断** — 不是笼统的"项目进展顺利"，而是每个子项逐一给出达标/基本达标/部分达标/未达标
- [ ] **目标与实际指标对照** — "DAU 周日均达到 551 万、峰值 610 万"对照"春运流量峰值 1000w，周日均 800w"
- [ ] **"总的来看"综合评估** — 用 3-5 条分维度总结全局："总的来看：第一，流量冲锋方面...第二，手机墙建设和端稳定性保障...第三，核心频道改造效果并不理想...第四，导购方向达到了不错的效果...第五，体验烂尾节点进一步扫尾"
- [ ] **跨期对比** — "两期体验战役带来的变化"，拿上一期和这一期的核心指标做对比（App 成交占比一年内增长 7pct、MAU 增幅明显）
- [ ] **诚实差距分析** — "不足"部分不是"还有提升空间"这种客套话，而是：
  - 点名具体问题："本次战役仍然聚焦在 App 端，手淘和支付宝端未涉及"
  - 指出结构性原因："核心用户产品结构性调整缺少清晰的思路"
  - 承认组织影响："战役中途涉及部分组织调整和人员变动也影响部分项目落地"
- [ ] **需求交付数据完整** — "需求总数：311，交付数量：251，需求达标量：144，需求达标率：57%，缺陷量：940，人力投入：113 人月"
- [ ] **能力沉淀已识别** — 不只是做了什么，还要说沉淀了什么："动态模板技术在复杂场景下的应用得到了验证"、"首次打通了飞猪和淘宝在 native 技术上的互通能力"
- [ ] **过程管理透明** — "交付结果用图/视频来呈现，同时我们用项目大盘来呈现过程，配上 AI 的进展总结"
- [ ] **交付拥堵已分析** — "6 月 15 日到 6 月 25 日之间，问题处理的拥挤态势持续保持高位，集中发布较多"
- [ ] **参与团队和人力已量化** — "参与人数 260 人（问题创建者 93 人，解决者 167 人）"、"平均下来所有 167 个研发同学基本上一个月内 fulltime 在解决这些问题（4900/167=29 天/每人）"

### 危险信号

- 项目状态全是"绿色"或"进展顺利"——没有部分达标和未达标的子项目
- 有"不足"部分但都是外部原因："资源不足"、"优先级冲突"，没有反思自身
- 缺少需求交付数据——不知道做了多少、达标多少、bug 多少
- 缺少跨期对比——看不出趋势是变好还是变差
- "总的来看"部分全是好事，没有遗憾和反思

### "总的来看"格式模板

```
总的来看：
第一，{维度1结论}，{具体数据}
第二，{维度2结论}，{具体数据}
第三，{维度3结论}，{具体数据}
第四，{维度4结论}，{具体数据}
第五，{维度5结论}，{具体数据}

不足：
1. {具体问题}——{结构性原因}
2. {具体问题}——{结构性原因}
3. {具体问题}——{结构性原因}
```

### 项目小结叙事结构（来自王者归来项目）

```
一）数据结果
- 核心指标 + 去年同期对比 + 目标对比
- "尽管未能达到预定的日均 500 万的业务目标。但是从数据回落上看，整体的流量依然呈现着健康的向上的态势"

二）过程
- 做了什么（3-5 条，编号列表）
- 关键数据穿插其中

三）技术磨砺
- "除了这些用户有明显感知的部分的明显进步，在技术保障方面我们也做足了功课"
- 技术贡献单独成段，不和业务混在一起

四）小结
- 遗憾和未完成项（诚实列出）
- 跨期回顾（"回顾 2018 财年里我们经历的百天大战、场景化战役..."）
- 未来展望
- 具名感谢
```

## 技术方案评审

### 检查项

- [ ] **演进叙事完整** — 不是画一个目标架构图就完事，而是说清楚"从哪来到哪去"：
  - "从王者荣耀一期到财年结束前的冲刺，技术项目持续在稳定性尤其是 Push 的能力上持续优化"
  - "问一问 2.0：单 Agent 升级到多 Agent 并行支持"
  - "端侧原则：Flutter 容器+卡片内置（性能优先） -> H5 View 容器+卡片外置预取（效率优先）"
- [ ] **迁移策略已定义** — "端侧适配：App 捆绑 -> H5 打底+Native 增强：简单改造即可外投（Web 版、AI2G 版、鸿蒙智能体对接）"
- [ ] **技术选型有取舍记录** — 为什么选 A 不选 B，放弃了什么：
  - "关键选型降低 1+6+N -> 快速入淘转型的不利影响"
  - "1+6+N 后端选型 DSL 层面 DX 保留+移动中台 SDK 的进一步保留"
- [ ] **性能数据有前后对比** — "详情页打开速度从 989ms 优化到 600ms 以内，优化 39%"、"占座耗时从 15s 压缩到 10s 以内"
- [ ] **灰度/验证计划** — "PC 首页底层切成 Node，预计下周开始灰度...因为是飞猪的门户入口，升级需要谨慎"
- [ ] **运维和稳定性保障** — "建立了稳定性值班小组，运行正常"、"郑十完成了 Push 大盘监控"
- [ ] **技术沉淀有样板间价值** — "小程序多端能力拉平和多端适配技术建设极具含金量，具有样板间式的价值"
- [ ] **对遗留问题的诚实评估** — "性能指标看只摸到及格线，离'优秀'还有距离"、"部分基础库的改造和升级操之过急，在战役收尾阶段引入了若干个 P4 技术故障"
- [ ] **深水区挑战已识别** — "性能优化到深水区，死磕奥创平台化页面秒出性能"、"多数场景优化已经渗透到逻辑代码部分，挑战更大"
- [ ] **共建和反哺** — "与手淘共建 detailsdk 能力，首次打通了飞猪和淘宝在 native 技术上的互通能力，飞猪商品在淘内得到极致体验，反哺手淘商品能力"

### 危险信号

- 漂亮的目标架构图，没有迁移路径
- "运维的事以后再说"
- 技术选型因为时髦而非适配——"整个技术社区内，包括阿里集团内对 PWA 的讨论的多、实操的少，说的多做的少"
- 没有灰度计划就直接全量
- 没有回滚方案
- 只有性能提升数据，没有稳定性风险评估

### 反模式

| 反模式 | 真实文档中的好写法 |
|--------|-------------------|
| "采用业界领先的 XX 架构" | "端侧原则：Flutter 容器+卡片内置（性能优先）-> H5 View 容器+卡片外置预取（效率优先）" |
| "性能提升显著" | "国际转化率增加 0.08pt，国内转化率增加 0.13pt" |
| "方案成熟稳定" | "部分基础库的改造和升级操之过急，在战役收尾阶段引入了若干个 P4 技术故障" |

## 代码变更评审

### 与变更规模成比例

**小变更（单个函数 / 文件）：**
- [ ] 做了它声称要做的事
- [ ] 测试覆盖了变更
- [ ] 没有明显的 bug 或遗漏的边界情况
- [ ] 命名清晰

**中等变更（多个文件 / 功能）：**
- 所有小变更检查项，加上：
- [ ] 设计与现有模式一致
- [ ] 错误处理恰当
- [ ] 性能影响可接受
- [ ] 已考虑安全影响
- [ ] 必要时更新了文档

**大变更（架构 / 跨领域）：**
- 所有中等变更检查项，加上：
- [ ] 架构决策已记录——不是"我们决定用 X"，而是"为什么选 X、放弃了什么、有什么风险"
- [ ] 替换现有代码时有迁移计划
- [ ] 功能开关或灰度发布计划
- [ ] 监控和告警就位
- [ ] 运维手册已更新
- [ ] 回滚计划已记录

### 代码评审反模式

- **橡皮图章** — 不阅读就通过
- **舍本逐末** — 争论变量命名而忽略架构问题
- **走马观花** — 不理解上下文就留下评论
- **以风格阻塞** — 风格问题应由 linter 处理，而非评审者

## 报告评审

### 适用场景

周报、月报、里程碑报告、述职报告、向上汇报。

### 检查项

- [ ] **结论先行** — 第一句话就是要点，不是背景铺垫：
  - 好："经过两个月的奋战，日均 DAU 为 410 万，相比去年同时段的 147 万日均 DAU 翻倍不止"
  - 好："本周日活均值稳定在 360W，受出行人群整体回落的影响，日新增日活有缓慢回落"
  - 差："本月我们继续推进各项工作，取得了一定进展"
- [ ] **每个数据有时间标注** — "本周"、"近 7 日表现数据"、"截止 9 月初"，不是"目前"这种模糊时间
- [ ] **每个数据有来源** — "[数据来源](链接)"、"根据 Aone 的数据统计"，不是"据估计"
- [ ] **坏消息不藏在好消息里** — "尽管未能达到预定的日均 500 万的业务目标"单独成段，不藏在成绩堆里
- [ ] **风险和坏消息有应对方案** — "余量 Push 本周不太稳定，技术正在追查"、"浙江电信接入本周受阻，下单失败率很高...@王五 在推进中"
- [ ] **具名感谢** — "特别赞钱十一算法团队的支持"、"感谢我们各个项目的 PM：冯十二、陈十三、卫十四、蒋十五、沈十六、韩十七、杨十八"，不是"感谢大家的努力"
- [ ] **事实与判断区分** — 数据是事实，"总体表现平稳"是判断，两者清晰分开
- [ ] **问题有结构性分析** — "这两个问题从严重性上看并不大，但反映出的问题很典型，都是前端业务触发了端架构底层的 bug"，不是就事论事
- [ ] **请求明确** — "需要 VP 在本周五前批准 XX 预算"，不是"希望领导关注"
- [ ] **篇幅与受众匹配** — 周报可以详细，述职报告聚焦重点，向上汇报越短越好

### 周报质量标准（来自飞猪用户技术部周报）

好的周报有以下几个特征：

1. **稳定性数据先行** — Crash 率万分之二、Weex 秒开率 91.6%、H5 白屏时间 1S 内、接口运维达标率 94%
2. **项目进展穿插思考** — 不只是"做了什么"，还有"几个思考"："第一，搭配宝是创新产品形态，可以快速成型快速试错...第二，PM 需要正确看待技术选型和产品形态探索阶段之间的关系"
3. **问题不回避** — "架构改造的稳定性有相当的隐患，架构稳定性靠人肉，兼容性方面的覆盖测试成本高...尽管 App 在 Crash 率上控制有方，但在更多维度的'不可用'定义、监控和测试效率上仍然短板巨大"
4. **技术方向有历史纵深** — "早在 2016 年我刚 Base 到杭州时成立了流媒体技术攻关小组...VR 媒体没有上去规模，双首页也因为各种原因被暂停。但流媒体互动形式的探索不应当终止"
5. **团队声音有温度** — 周报末尾有"团队心声"，每人写自己的感悟，不是模板化的"本周工作顺利"

### 述职报告质量标准（来自 FY21 和 FY26S1 述职）

好的述职报告有以下几个特征：

1. **OKR 完成三句话概括** — "重点项目交付：交通线有惊无险的挺过春运...数字化经营：艰难起步...如何承上启下：借助吴九趟平手淘小程序坑..."
2. **每个板块有"思考"** — 不是只说做了什么，还要说"遗留下来的是难啃的历史包袱"、"目前只解决能用问题，远未到好用易用"
3. **组织数据配套** — 团队层级分布饼图、产研比、校招占比、司龄中位数
4. **组织挑战不回避** — "团队腰部的健壮性风险"、"一线研发的成长性诉求"、"业务模糊带来稳定风险"
5. **下一步有重心** — "22FY 工作重心"明确列出 2-3 个方向，不是面面俱到

### 危险信号

- "我们取得了良好进展"但没有指标
- "存在一些风险"但没有命名具体是什么风险
- 数据没有时间标注和来源——"提升显著"是多少？
- 坏消息藏在好消息中间，或者用"但也"一笔带过
- 1 页就够却写了 10 页
- 没有请求——只汇报不请求，领导不知道你要什么

### 报告反模式

| 反模式 | 真实文档中的好写法 |
|--------|-------------------|
| "项目进展顺利" | "本周日活均值稳定在 360W，受出行人群整体回落的影响，日新增日活有缓慢回落" |
| "感谢团队的努力" | "特别赞钱十一算法团队的支持" |
| "存在一定风险" | "7、8 月份密集的入淘、营销和会员等项目冲突" |
| "性能有较大提升" | "详情页打开速度从 989ms 优化到 600ms 以内，优化 39%" |
| "希望领导关注" | "需要 VP 在本周五前批准 XX 预算" |

## 复盘评审

### 检查项

- [ ] **根因分析不止一层** — 不是"测试覆盖不足"就结束，而是追问为什么覆盖不足：
  - "部分基础库的改造和升级操之过急" -> 为什么操之过急？ -> "在战役收尾阶段"时间压力大 -> 为什么收尾阶段还在做基础库改造？
- [ ] **好和坏都写** — "做得好的"至少 2 条值得保留的实践，"做得差的"至少 2 个实质性问题
- [ ] **遗憾和未完成项诚实列出** — "本次日活冲刺还是有不少遗憾，比如飞猪环游记和交易后翻牌等没赶上春促（这和这类互动游戏体验要求极高有关系）"
- [ ] **可复用能力已识别** — "我们用了一整年的时间来专注于基础体验、技术能力沉淀和流量建设方法论...是我们这一年来经历的这些项目后最大的收获"
- [ ] **具名感谢** — 点名感谢具体的人和具体的贡献，不是"感谢所有人"：
  - "最后感谢我们各个项目的 PM：冯十二、陈十三、卫十四、蒋十五、沈十六、韩十七、杨十八"
  - "感谢朱十九、秦二十、尤二一、许二二、何二三、吕二四、钱十一给予的大力支持"
- [ ] **可操作的改进** — 不是"加强沟通"、"加强协作"，而是"Android 安装包体积也需要纳入监控，开始控制上限"
- [ ] **意外发现有记录** — "行程 2.0 的行中用户的点击率高达 88%，这部分是留存用户，侧面说明行中用户对行程工具属性的依赖很强"
- [ ] **跨期视角** — 复盘不只看这一个项目，还要看"回顾 2018 财年里我们经历的百天大战、场景化战役、王者荣耀一期、王者荣耀二期、王者归来项目"
- [ ] **每个改进有负责人和截止日期** — "@张三 牵头明确了两件事...目前已经启动针对这些非活跃 Native Page 的梳理工作"

### 复盘的"一些感受"格式（来自 615 里程碑小结）

复盘结尾的"感受"部分不是客套话，而是提炼可复用的认知：

```
1. {协同模式}：{为什么有效}，{和长期积累的关系}
2. {工作方法}：{由点及面的价值}，{举例}
3. {做事态度}：{日拱一卒的意义}，{对长期主义的信念}
```

### 危险信号

- "项目圆满完成"但没有列出未达成的目标
- 复盘全是表扬和感谢，没有实质性问题分析
- 改进建议是"加强沟通"/"加强协作"但没有具体行动
- 复盘文档没有后续跟进负责人
- 根因分析停在第一层——"资源不足"不是根因，为什么资源不足才是

### 复盘反模式

| 反模式 | 真实文档中的好写法 |
|--------|-------------------|
| "项目圆满完成" | "尽管未能达到预定的日均 500 万的业务目标" |
| "团队配合良好" | "产品毫无保留的支持，设计积极主动的推动，业务搭档们的参与，和研发同学的全力以赴" |
| "需要加强测试" | "测试质量和用例不全的问题有所缓解，但在部分技术项目中仍存在用例缺失的问题" |
| "经验值得总结" | "体验治理是长期的事，不奢望'毕其功于一役'...认真细致把'小事'做好" |

## AI 转型评审

### 检查项

- [ ] **三个轴诊断成熟度** — 不是问"大家是否在用 AI 工具"，而是分别评估：
  - **工程 harness 水平**：CLAUDE.md、CI/CD、知识库、测试覆盖等基础设施到了什么等级（无AI水平/初级水平/中级水平/高级水平/顶级水平）
  - **AI 任务接管深度**：AI 在做的事是写代码片段，还是能跑完从需求到测试的完整闭环
  - **人员态度准备度**：团队中激进先行者、积极推动者、务实跟随者、谨慎观察者、有原则的怀疑者各占多少
- [ ] **互动步数作为成熟度指标** — "一个任务，你跟 AI 对话到第几步，开始白盒变黑盒的？十步左右。对话十次左右，他的回应我就开始看不懂了"。能驾驭的对话步数越多，成熟度越高
- [ ] **计算机基础功是门槛** — "恶补的知识百分之九十计算机专业基础课，数据结构、内存管理、编译、进程管理、网络、操作系统...不是恶补概念，是恶补到知识细节"。不补基础功就无法判断 AI 输出的质量
- [ ] **大拆大建阶段认知** — "现在的阶段是棚户区改造，大片大片的大拆大建，本质就是将这些孤立系统开放并连接起来。是致富之前的修路的过程"。不要用建成区的标准评估棚户区的进度
- [ ] **三个飞轮已关注**：
  - **知识闭环**：知识库能否自动更新，AI 能不能用到最新的领域知识
  - **验证闭环**：AI 代码 -> 自动测试 -> 反馈 -> 自修复，这个循环是否跑通
  - **上下游闭环**：PRD 结构化、协作流变化，上下游是否适配 AI 工作流
- [ ] **覆盖率不是唯一指标** — "AI 覆盖率 80%"不等于成功。还要看：首个 PR 时间、代码评审周转时间、缺陷逃逸率、知识新鲜度
- [ ] **区域模型已应用** — 绿区（AI 主导，90%+）、黄区（AI+人工，60-80%）、红区（人工主导，40-60%）；不要把红区硬推到 60% 以上
- [ ] **转型分阶段** — 基础（消灭零 AI 项目）-> 闭环（验证循环运转）-> 效率（从覆盖率转向周期时间）
- [ ] **专业性不可替代** — "纵使强如 AI，最后拉人垫背的事情也在一而再再而三的发生...不是被延期修理，就是被故障教育"。AI 不能兜底所有事，人的专业性仍然关键
- [ ] **基建先于应用** — "基建、修路、建学校永远比亩产万斤来得靠谱"。不要用 demo 代替落地，不要用 vibe 代替工程化
- [ ] **脱颖而出的人做了什么** — "解决应用间不通的问题，解决各种孤岛问题，推动 AI 向驱动跨机器、跨流程、跨环境、跨上下文的长程任务的方向前进哪怕一小步"

### 危险信号

- "AI 转型"定义为"全员使用 Copilot"——工具采纳但没有流程变革
- "vibe 个 demo 就兴奋的蹦老高"——demo 不等于落地
- "含 AI 量几乎为零的事"占用了大量时间——比如用 GPT 画 PPT
- 100% 覆盖率目标但没有分阶段计划
- 没有在知识库或验证基础设施上的投入
- 忽视态度分布——把所有抵触都当作不愿意
- 模型版本升级后框架立即过时——"无论是 specify 挂靠 opus 4.5 的五步一杀，还是 superpowers 搭配 gpt 5.4 的三步上篮...模型版本升级后，立即过时"

### 反模式

| 反模式 | 真实文档中的好写法 |
|--------|-------------------|
| "全员 AI 覆盖率 100%" | "一个任务，你跟 AI 对话到第几步，开始白盒变黑盒的？" |
| "AI 提效 50%" | "十步左右。对话十次左右，他的回应我就开始看不懂了" |
| "拥抱 AI 时代" | "躬身入局，向 AI 低头、向 AI 学习...老老实实先动手搭一个不被封号的线路" |
| "AI 改变一切" | "大拆大建完工之前，咱们还是得过好社会主义初级阶段" |

## 晋升材料评审

> 晋升评审报告的完整撰写指南见 [promotion-review.md](promotion-review.md)。
> 试用期评语、阶段总结、结项复盘、向下汇报的完整指南见 [work-reviews.md](work-reviews.md)。

### 检查项（自检用）

- [ ] **展现了问题主导权** — 候选人定义了问题，而非仅仅解决了分配的任务
- [ ] **范围匹配下一层级** — 证据显示持续在下一层级水平上运作
- [ ] **展现了结构性贡献** — 建立了超越个人参与的组织能力
- [ ] **证据链完整** — 每个论述都有：基线 -> 行动 -> 结果 -> 解读 -> 局限性
- [ ] **取舍已表达** — 选择了什么、放弃了什么，以及原因
- [ ] **局限性已命名** — 出了什么问题、学到了什么、什么仍未解决
- [ ] **集体工作具体承认** — 点名他人的贡献；承担管理和判断失误
- [ ] **定量结果有方法论支撑** — 数字有来源、基线和解读
- [ ] **成长轨迹可见** — 展现从上一层级到当前的进步，而非仅仅当前表现

### 危险信号

- "接到 X 任务，交付了 Y"——这是当前层级的行为
- 战略词汇但没有可观察的决策
- 成功没有限制性条款
- 基于活动的叙述但没有结果证据
- 声称有影响力但没有他人主动寻求其判断的证据

## 附录：跨评审类型的通用红线

以下标准适用于所有评审类型，出现任何一条都应阻止通过：

| 红线 | 说明 |
|------|------|
| **没有数据** | 全程用形容词（"显著提升"、"较大改善"）而非数字 |
| **没有坏消息** | 全是好事、全是达标、全是感谢，没有遗憾和不足 |
| **没有负责人** | 所有事情都是"团队"做的，没有具名的人 |
| **没有时间线** | "近期"、"目前"、"下一步"，没有具体日期 |
| **没有对比** | 只看当下，不和上期比、不和竞对比、不和目标比 |
| **没有根因** | 问题停在表象层，不追问为什么 |
| **没有取舍** | 好像什么都做了，没有放弃任何东西 |
| **没有请求** | 汇报完就完了，没有说清楚需要受众做什么 |
