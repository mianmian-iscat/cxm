## 问题定义

适用场景：在规划文档或立项材料中，需要先厘清"到底要解决什么问题"时使用。这是所有后续文档（战略规划、立项书、技术方案）的输入。

### 写作结构

```markdown
# {团队/领域} 矛盾与取舍

## 一）现状

{用 1-2 段话描述当前状态，嵌入具体数据。不是"目前存在一些问题"，
而是"DAU 稳中带升（同比 +15%），但 App 成交占比一年内仅增长 7pct"。}

## 二）核心矛盾

{不按"问题列表"罗列，而按"矛盾对"组织——每个矛盾是一对相互拉扯的力量：}

1. {矛盾1}：{力量A} vs {力量B}
   - 具体表现：{数据/案例}
   - 为什么现在必须解决：{时间窗口/外部压力}

2. {矛盾2}：{力量A} vs {力量B}
   - 具体表现：{数据/案例}
   - 为什么现在必须解决：{时间窗口/外部压力}

3. {矛盾3}：{力量A} vs {力量B}
   - 具体表现：{数据/案例}
   - 为什么现在必须解决：{时间窗口/外部压力}

## 三）机遇和挑战（战略 & 外部环境）

{把内部矛盾放入外部上下文中：}
- 行业趋势：{竞品在做什么，市场在往哪走}
- 集团/平台约束：{中台能力、技术选型管控、生态位}
- 时间窗口：{为什么是现在}

## 四）取舍

{明确回答"我们做什么、不做什么"。每个取舍要有理由：}

| 做 | 不做 | 理由 |
|----|------|------|
| {方向1} | {舍弃方向1} | {为什么不} |
| {方向2} | {舍弃方向2} | {为什么不} |

## 五）理想结果

{用可衡量的标准描述"解决之后是什么样"：}
- 指标1：从 {X} 到 {Y}
- 指标2：从 {X} 到 {Y}
- 用户体验：{具象描述}
```

### 写作原则

- **矛盾对而非问题列表**：不是"有 5 个问题要解决"，而是"3 对矛盾要做取舍"。问题的价值在于它的张力
- **数据嵌入叙事**：每个矛盾必须有具体数字（DAU、UV、Crash 率、转化率），不写"存在一定差距"
- **外部对标常态化**：每个矛盾都拉竞品数据做参照，不是为了焦虑，是为了校准取舍的合理性
- **括号补充上下文**：频繁用括号补充（"艰难的转型期""首次打通""疫情前天花板"），让读者快速理解背景
- **取舍是最核心的产出**：问题定义文档的价值不在于"发现了什么问题"，而在于"我们决定不做什么"

### 范例结构（来自飞猪用户技术部 2017 技术规划）

> 一）旅客的原始积累 2014~2016 → 二）猪客端体系雏形 → 三）矛盾与取舍 → 四）机遇和挑战（战略 & 外部环境）→ 五~九）各域演进方向 → 十）人才梯队

> 关键技巧：先讲历史（"从 2007 年淘宝首页有了一个机票的 Tab 伊始"），再讲矛盾（"用支付宝的架构做淘宝的业务"），最后才讲取舍。让读者理解"为什么走到今天这一步"。

## 决策备忘录

适用场景：需要推动特定决策人做出特定决策时。通常以邮件、语雀文档或会议材料形式发出。

### 写作结构

```markdown
# 关于 {决策事项} 的建议

**决策人**：{姓名/角色}
**截止日期**：{日期}
**作者**：{姓名}

## 推荐方案

{2-3 句话直接说推荐什么、为什么。不铺垫，不绕弯。}

例：建议采用方案 A（{方案名}），原因是 {一句话}。

## 方案对比

| 维度 | 方案 A（推荐） | 方案 B | 不作为 |
|------|---------------|--------|--------|
| 描述 | {一句话} | {一句话} | 会发生什么 |
| 人力投入 | {人月} | {人月} | - |
| 时间周期 | {周/月} | {周/月} | - |
| 技术风险 | {高/中/低 + 原因} | {高/中/低 + 原因} | {风险} |
| 业务影响 | {量化} | {量化} | {量化} |

## 关键证据

{用数据说话，不用观点说话：}

1. {数据点1}：{具体数字 + 来源}
2. {数据点2}：{具体数字 + 来源}
3. {数据点3}：{具体数字 + 来源}

## 请求事项

- {具体决策请求1}
- {具体资源请求}
- {具体时间节点}
```

### 写作原则

- **结论先行**：推荐方案放在最前面，不让决策人猜你的立场
- **对比表而非长段落**：方案对比用表格，一眼能看差异
- **证据是数字，不是感受**：不写"团队反馈体验不好"，写"秒开率 44.99%，竞品 80%"
- **不作为方案必须有**：永远列出"不做的后果"，这是决策人最需要知道的

## 战略规划

适用场景：为团队或组织规划下一财年或半年方向。本模板是 **markdown 简要版**，适合内部文档和讨论阶段。

> **与 templates-more 模板 25 的关系**：模板 25 是正式 PPT 结构（含演示文稿的行文风格指南），本模板是 PPT 之前的**思考框架**——先用 markdown 把逻辑理清楚，再翻译成 PPT。

### 写作结构

```markdown
# {团队名} {财年} 技术规划

## 一）{历史阶段名} {年份区间}

{用叙事方式回顾过去 1-3 年的历程。不是罗列事件，而是讲清楚
"从哪来、为什么走到今天"。}

例：从 2013 年以来，飞猪开始了轰轰烈烈的行业垂直化的深耕，
并形成了今天成熟的行业体验...同时也不经意间构建了相对封闭的生态。

## 二）{当前体系名}

{描述当前体系的形态，用一张边界图或架构图说清楚"现在是什么样子"。}

{关键句式："一方面要...另外又要..."——把矛盾可视化。}

## 三）矛盾与取舍

{见"问题定义"模板的输出。}

## 四）机遇和挑战（战略 & 外部环境）

{从外部视角审视：}
- 端技术多样化带来的三个挑战：{1、2、3}
- 集团/平台层面的约束和机会
- 竞品动态

## 五~八）各域演进方向

{每个域一个章节，结构统一：}

### {域名}

- 当前状态：{一段话 + 数据}
- 演进目标：{一句话}
- 关键动作：{3-5 条，每条带时间节点}
- 里程碑：{S1 / S2 标注}

## 九）共建领域 & 创新

{跨域共建的方向，明确"谁提供什么、谁消费什么"。}

## 十）人才梯队

{组织结构、headcount、关键岗位、梯队设计。}
```

### 写作原则

- **历史叙事是必须的**：不是从"现状"开始，而是从"从哪来"开始。让读者理解演进的逻辑
- **四字格动词短语**：战略方向用四字短语（"提升留存""拓宽流量""塑造差异""沉淀能力"），增加节奏感
- **三件套分组**：默认用三个一组组织信息（"三大挑战""三个方向""三期演进"）
- **每个域有独立章节**：不按技术层切（前端/后端/算法），按业务域切（交通/酒店/度假/用户）
- **人才梯队单独成章**：技术规划不只是技术，团队规划是最后一章

### 范例结构（来自飞猪用户技术部 2017 技术规划）

> 一）旅客的原始积累 → 二）猪客端体系雏形 → 三）矛盾与取舍 → 四）机遇和挑战 → 五）猪客端架构演进（3.0）→ 六）Web & Native 的再融合 → 七）猪客服务端体系 → 八）内容互动技术体系 → 九）共建领域 & 创新 → 十）人才梯队

## 立项书

适用场景：启动一个战役型或集中整治型项目时的正式立项文档。区别于 templates-extended 模板 13（项目 KO 文档，偏 Kickoff 会议材料）和 templates-more 模板 22（跨团队大项目 KO PPT 结构），本模板聚焦于**立项前的对焦文档**——在 KO 之前用来说服和拉齐。

### 写作结构

```markdown
# {项目名称}

{一句话使命："面对{什么}带来的{什么}，我们集体决定发起{项目名}，
对{什么}做一轮集中整治。"}

## 一）使命

"**{一句话使命概括}**"

{2-3 段话展开：}
- 当前阵痛是什么（用数据）
- 为什么是现在
- 这次集中整治的双重使命：
  - 使命1：{面向用户/业务的}——将那些一直以来各种原因搁置的重要问题集中改进
  - 使命2：{面向技术/基建的}——给那些极其核心的系统创造极好的重塑时机

## 二）子域划分

{经过紧张的对焦梳理后成立 N 个子项目：}

| # | 子项目 | 技术 PM | 关键交付 | 说明 |
|---|--------|---------|----------|------|
| 1 | {名称} | {姓名} | {核心交付} | {一句话} |
| 2 | {名称} | {姓名} | {核心交付} | {一句话} |
| ... | | | | |

{这些项目立项的出发点只有一个，就是"{核心出发点}"——
一方面需要{做什么}，另一方面{做什么}。}

## 三）项目推进方式

- **项目管理**：基于 Aone，项目集：{链接}
- **大 PD**：@{姓名}
- **大 PM**：@{姓名}（@{姓名} 是 Backup）
- **集中办公**：{时间} 在 {地点} 集中，持续到 {结束时间}
- **参与规模**：预计超过 {N} 名研发同学（包括 QA/UED 等角色）

## 四）沟通节奏

| 频率 | 形式 | 参与人 | 内容 |
|------|------|--------|------|
| 每日 | 站会 | 各子项目 PM | 进展、阻塞、依赖 |
| 每周 | 周报 | 全组 | 运营报告 |
| 里程碑 | 汇报 | 管理层 | 阶段性成果 |

## 五）战略意义

{2-3 句话，将项目从"任务"提升为"使命"。}

例：航旅从来没有像今日这样重视无线体验，把"**用户体感**"放在
如此重要的位子上。期待这轮大战能为航旅赢得新年后的开门红，
将大家带入激动人心的"{愿景}"。
```

### 写作原则

- **使命先行**：开篇一句话概括"为什么要打这一仗"，用粗体标出
- **双重使命**：每个战役都有业务使命和技术使命，不能只说一个
- **子项目表是核心**：PM 名单、交付物、时间节点——这是立项对焦的核心产出
- **语气是"集结号"不是"任务书"**：用"期待""一起加油"这种语气，不是"要求各团队"
- **结尾要有仪式感**："大家加油""年后见"——让读到的人感到被召唤

### 范例结构（来自飞猪无线体验百天大战 Kickoff）

> 使命："提升消费者体验，强化互动" → 十个子项目拆解（蜘蛛图）→ 项目管理（Aone 项目集 + 集中办公）→ 战略意义："将大家带入激动人心的 2017 飞猪用户体验年"

## 项目作战地图

适用场景：向团队和利益相关方可视化展示复杂项目的全貌。通常是一页图或一页 PPT，不是长文档。

### 写作结构

```
作战地图：{项目名称}
====================

目标：{一句话，带量化指标}
时间线：{开始} → {里程碑1} → {里程碑2} → {收尾}

工作流总览：
┌──────────┬────────┬──────────────┬──────────────┐
│ 工作流    │ PM     │ 状态          │ 下一里程碑    │
├──────────┼────────┼──────────────┼──────────────┤
│ {流量}   │ {姓名} │ 🟢 正常       │ {日期：内容}  │
│ {体验}   │ {姓名} │ 🟡 有风险     │ {日期：内容}  │
│ {架构}   │ {姓名} │ 🟢 正常       │ {日期：内容}  │
│ {稳定性} │ {姓名} │ 🔴 受阻       │ {日期：内容}  │
└──────────┴────────┴──────────────┴──────────────┘

关键路径：
{阶段1} → {阶段2} → {阶段3} → {上线}
  ↓           ↓          ↓
{交付物1}  {交付物2}  {交付物3}

依赖关系（蜘蛛图）：
{用图或表展示各子项目之间的技术依赖和关键节点。
参照百天大战 Kickoff 中的蜘蛛图模式：
每个子项目的关键点辐射状连接。}

主要风险：
1. {风险}：{影响} —— {缓解措施}
2. {风险}：{影响} —— {缓解措施}

数据看板：
| 指标 | 当前 | 目标 | 趋势 |
|------|------|------|------|
| {指标1} | {值} | {值} | {↑/→/↓} |
```

### 写作原则

- **一页纸原则**：作战地图不是文档，是一页能看完的全貌图
- **红黄绿灯**：状态用 🟢🟡🔴 标记，让读者一眼看到哪里需要关注
- **蜘蛛图展示依赖**：子项目之间的技术依赖用辐射状图展示，比表格更直观
- **数据看板嵌入**：核心指标直接嵌在地图中，不用另外翻数据

## 里程碑报告

适用场景：在里程碑节点（如 615、830）汇报阶段进展。本模板是 **markdown 简要版**。

> **与 templates-more 模板 23 的关系**：模板 23 是正式 PPT 结构（每域一页、标杆案例页），本模板适合在**周报、邮件或语雀**中做里程碑同步。

### 写作结构

```markdown
# {项目名} {里程碑名} 里程碑同步

**日期**：{日期}
**整体状态**：{一句话 + 红黄绿灯}

## 一）整体进展概览

{3-5 句话：本里程碑完成了什么，关键数字变化。}

例：L3 及以上系统占比从 X% → Y%（目标 Z%）。

## 二）分域进展

### {域名}（@{负责人}）

- 本域系统数量：{N} 个
- 目标完成率：{X}%
- 亮点：
  1. {项目名}：效率提升 {X}%，{具体数据}
  2. {项目名}：{具体成果}
- 风险/问题：
  1. {问题}：{影响} —— {行动}

### {域名}（@{负责人}）

{同上结构}

## 三）标杆案例（1-2 个）

### {案例名}

- 背景：{一句话}
- 做了什么：{3-5 条}
- 效率数据：{优化前 → 优化后}
- 可复制性：{同层级团队可以怎么复用}

## 四）下一里程碑计划

- 目标日期：{日期}
- 目标数字：{具体指标}
- 需要决策：{列表}
- 需要协调：{列表}
```

### 写作原则

- **数字先行**：每个域先报数字，再讲故事。"38 个系统，66% L2，34% L1"先于"我们做了很多工作"
- **直面差距**：与目标的差距明说，不藏在细节里。"目标 76% L3，实际 34% L1"——直接呈现
- **标杆案例要有可复制性**：不是"某某团队很厉害"，而是"同层级的人可以复制这个方法"
- **下一里程碑要有请求**：不是"继续努力"，而是"需要 XX 团队在 830 之前完成 XX"

## 风险与依赖评审

适用场景：项目执行过程中的定期风险评审，或大型战役前的风险排查。

### 写作结构

```markdown
# {项目/团队} 风险盘点

**日期**：{日期}
**评审范围**：{哪些子项目/域}

## 一）风险登记

| # | 风险 | 概率 | 影响 | 缓解措施 | 负责人 | 状态 |
|---|------|------|------|----------|--------|------|
| R1 | {具体描述} | 高/中/低 | 高/中/低 | {行动} | {姓名} | {已处理/进行中/待启动} |

## 二）依赖关系

| # | 依赖项 | 提供方 | 消费方 | 当前状态 | 风险 |
|---|--------|--------|--------|----------|------|
| D1 | {什么} | {谁} | {谁} | {已交付/进行中/未启动} | {高/中/低 + 原因} |

## 三）需要升级处理

{需要管理层介入的事项：}

1. {事项}：{为什么需要升级} —— {建议向谁}
2. {事项}：{为什么需要升级} —— {建议向谁}

## 四）历史风险回顾

| 上期风险 | 本期状态 | 结果 |
|----------|----------|------|
| {风险1} | {已消除/仍在/升级} | {结果} |
```

### 写作原则

- **风险要具体到可行动**：不写"存在一定风险"，写"浙江电信接入下单失败率很高，浙电侧尚未给出具体答复"
- **依赖关系要双端可见**：提供方和消费方都列出来，避免"我以为你在做"
- **需要升级的要直说**：不是所有风险都能项目组内解决，需要明确"这件事需要老板出面"
- **回顾上期风险**：每次评审都要回顾上期的风险状态，形成闭环

## 技术方案

适用场景：提出技术决策或架构变更。本模板适合在语雀/Lark 文档中使用，保留技术深度。

### 写作结构

```markdown
# {技术方案标题}

**作者**：{姓名}
**日期**：{日期}
**状态**：{草稿 / 评审中 / 已批准 / 已实施}

## 一）背景

{当前状况是什么，为什么需要变更。嵌入架构演进的历史脉络。}

例：猪客架构从 2012 年的简单功能集合（1.0），到基于 MPass
的框架级方案（2.0），再到 2017 年开始的淘系迁移（3.0 Mashup
App），当前面临的核心挑战是 {具体矛盾}。

## 二）架构现状

{用图或结构化描述展示当前架构。明确边界：哪些是自建、
哪些是集团中台、哪些是二方/三方 SDK。}

{关键句式："猪客作为一个构造复杂的小 App，一方面要保持
行业体验独立性，另外又要深度嫁接集团移动端体系。"}

## 三）方案选项

### 方案 A：{方案名}

- 描述：{一段话}
- 优点：{列表}
- 缺点：{列表}
- 迁移成本：{人月/周期}
- 运维成本：{长期开销}

### 方案 B：{方案名}

{同上结构}

### 不作为

- 会发生什么：{技术债务累积的后果}

## 四）决策

- **选定方案**：{方案}
- **决策理由**：{为什么}
- **放弃的收益**：{其他方案能提供什么，我们选择不追求}

## 五）实施计划

| 阶段 | 内容 | 时间 | 负责人 | 验证标准 |
|------|------|------|--------|----------|
| 第一阶段 | {内容} | {时间} | {姓名} | {如何验证} |
| 第二阶段 | {内容} | {时间} | {姓名} | {如何验证} |

## 六）风险与回滚

| 风险 | 缓解措施 | 回滚方案 |
|------|----------|----------|
| {什么} | {如何} | {如何回退} |

## 七）验证计划

- 监控：{关注哪些指标}
- 灰度策略：{百分比 → 全量}
- 线上验证：{怎么判断成功}
```

### 写作原则

- **架构演进脉络是必须的**：不是从"问题"开始，而是从"从哪来"开始。展示 1.0 → 2.0 → 3.0 的旅程
- **边界设计可视化**：用图说清楚"哪些是我们的、哪些是集团的、哪些是三方的"
- **技术选型要有上下文**：不是"我推荐 React"，而是"在飞猪这样一个低频小 App、外接集团大量 SDK 的场景下..."
- **Quick and dirty 也是一种决策**：探索阶段的技术选型"尽可能的弱化"，不需要过度设计

### 范例结构（来自面向未来的飞猪用户技术体系）

> 一）大浪淘沙（历史叙事）→ 二）旧貌新颜（当前体系 + 三个核心问题）→ 三）本土生存（四个域的 Local 解决方案）→ 每个问题都有架构图 + 演进时间线 + 技术选型的理由

## 复盘

适用场景：战役或项目结项时的总结。本模板提炼自 M4（Milestone 4 = 结项标志）报告格式，适合用结构化表格呈现。

> **与 templates-more 模板 24 的关系**：模板 24 是完整的 M4 结项报告（含详细表格和达标判断标准），本模板是**轻量复盘版**，适合项目级而非战役级的复盘。

### 写作结构

```markdown
# {项目/战役名} 小结

**周期**：{开始} —— {结束}
**参与团队**：{列表}

## 一）数据结果

{用 2-3 段话 + 数据图开篇，先说结果。}

例：经过两个月的奋战，历经两个客户端版本发布，从 3 月 21 日
春促开始到 4 月 7 日清明假期结束，日均 DAU 为 410 万，相比
去年同时段的 147 万日均 DAU 翻倍不止。其中峰值高达 491 万。

{如有未达标，坦诚说明："尽管未能达到预定的日均 500 万的业务
目标。但是从数据回落上看，整体的流量依然呈现着健康的向上的态势。"}

## 二）本次冲刺的过程

{按"做到了什么"组织，不是按"做了什么"组织：}

1. {方向1}：{做到了什么 + 数据}
2. {方向2}：{做到了什么 + 数据}
3. {方向3}：{做到了什么 + 数据}

## 三）背后的磨砺

{技术保障方面的功课，那些用户没有明显感知但团队付出了巨大努力的：}

1. {技术方向1}：{做了什么 + 效果数据}
2. {技术方向2}：{做了什么 + 效果数据}
3. {技术方向3}：{做了什么 + 效果数据}

## 四）小结

{坦诚的回顾：}

- **遗憾**：{哪些事没赶上/没做好，为什么}
- **收获**：{回顾整个历程，最大的收获是什么}
- **展望**：{未来会在哪些方向持续投入}

## 五）致谢

{感谢具体的 PM、PD、团队成员、支援方。点名感谢，
不要泛泛的"感谢大家"。}

例：最后感谢我们各个项目的 PM：{名单}。还有产品大 PD {姓名}。
感谢 {领导/搭档} 给予的大力支持！感谢飞猪大团队所有提名字的
和没提名字的兄弟姐妹们！
```

### 写作原则

- **先说结果，再说过程**：开篇就是数据和结论，不是"项目背景"
- **遗憾是必须的**：不掩饰未达标的部分，"这些点都是可以持续提升的"
- **回顾整个历程**：不只回顾本期，而是连接到历史（"回顾 2018 财年里我们经历的百天大战、场景化战役、王者荣耀一期..."）
- **致谢要具体**：点名感谢 PM、PD、支援方，特别是幕后英雄
- **控制在一页以内**：项目小结不是技术报告，是给团队看的总结

### 达标判断标准（战役级复盘适用）

| 判断 | 条件 |
|------|------|
| **达标** | 核心指标全部达成，无遗留技术问题 |
| **基本达标** | 核心指标达成，但有非关键遗留项 |
| **部分达标** | 部分核心指标达成，部分未达成 |
| **未达标** | 核心指标多数未达成，或项目被取消 |

### 范例结构（来自王者归来项目小结 + 体验战役二期 M4）

> 王者归来：数据结果（DAU 410 万 vs 目标 500 万）→ 过程（三个方向做到了什么）→ 背后的磨砺（Push 优化、端技术升级、泰坦）→ 小结（遗憾 + 收获 + 展望）→ 致谢

> M4 结项：表格明细（6 个大项目，20+ 子项目）→ 汇总数据（311 需求/251 交付/57% 达标率/113 人月）→ "总的来看"五段总结 → "两期战役带来的变化"三段跨期对比 → 四个不足

## 管理共创会

适用场景：组织中高层管理者（TL/P8+）的管理共创会，聚焦于人、组织、领导力。

> **与 templates-extended 模板 14 的关系**：模板 14 是**技术共创会纪要**（聚焦技术方案讨论），本模板是**管理共创会**（聚焦人的管理和组织建设）。
>
> **与 templates-more 模板 27 的关系**：模板 27 是管理共创会的**完整框架**（含案例研讨、工具箱、管理锦囊等全部环节），本模板是**轻量设计版**——适合首次组织共创会或半天时长的简化版。

### 写作结构

```markdown
# {主题} — 管理共创会

**日期**：{日期}
**参与人**：{D 级管理者 + 核心 TL}
**时长**：{半天/全天}

## 一）我们在哪里

{把参与者放入更大的上下文中：}
- 宏观：{行业/公司层面的变化}
- 微观：{团队层面的具体挑战}
- 核心矛盾：{用一句话概括}

## 二）核心议题

### 议题 1：{议题名称}

**背景**：{为什么讨论这个}

**信息输入**：{TL 简报或数据}

**讨论问题**：
1. {问题1}
2. {问题2}

### 议题 2：{议题名称}

{同上结构}

## 三）案例研讨（1-2 个）

### 案例：{脱敏标题}

- **当事人诉求**：{TA 想要什么}
- **实际达成情况**：{理想与现实的差距}
- **管理者的评估**：{多维度评估}
- **管理盲区**：{管理者忽略了什么}
- **管理反思**：{如果重来，可以怎么做不同}

## 四）总结与行动

### 管理锦囊

{将讨论浓缩为 N 条，每条一句话：}

1. {锦囊1}
2. {锦囊2}

### 课后作业

| # | 行动 | 负责人 | 完成时间 |
|---|------|--------|----------|
| 1 | {具体管理动作} | {姓名} | {日期} |
```

### 写作原则

- **从真实案例出发，不从理论出发**：每个讨论议题必须紧跟真实案例
- **管理盲区比管理动作更重要**：重点不是"该怎么做"，而是"我忽略了什么"
- **作业要有回报机制**：布置的作业必须有检查和反馈环节
- **参与者先分享感受**：开场让每个人分享自己的观察，"站在技术本位思考，对问题不作回应，只作感受同步"

### 范例结构（来自无线技术共创会）

> 四趴结构：① 分享过去一年团队现状/业务支撑体感认知 → ② TL 信息输入 → ③ 汇总四个核心痛点，分组讨论 → ④ 总结

> 第一趴中每个参与者的发言忠实记录（"仲凡：技术现状：既背靠手淘/支付宝，又个性化发展..."），形成集体感知的输入。

## 向上汇报

适用场景：半年度（S1/S2）向 D 级管理者做述职汇报。本模板是 **markdown 简要版**，适合内部对焦和材料准备阶段。

> **与 templates-more 模板 26/28 的关系**：模板 26 是年度述职 PPT 结构，模板 28 是半年度述职 PPT 结构（含行文风格指南），本模板是 PPT 之前的**思考框架**——先把逻辑理清楚。

### 写作结构

```markdown
# {团队名} FY{X}S{1/2} 述职

## 一、做业务：FY{X}S{1/2} OKR 进展同步

### 一）{重点专项1}

{每个专项结构：}

1. **项目定位**：{一句话}
2. **做了什么**：{3-5 条，引词 + 短句格式}
   - {引词}：{具体行动 + 量化结果}
   - {引词}：{具体行动 + 量化结果}
3. **结果**：{量化数据，优化前 → 优化后}
4. **难点**：{坦诚说明}
5. **不足**：{没做好的地方 + 根因}

### 二）{重点专项2}

{同上结构}

### 三）{重点专项3}

{同上结构}

## 二、建团队：FY{X}S{1/2} 组织稳定性

1. **基本概况**：{规模变化 + 结构数据}
2. **组织设计**：{关键决策 + 理由}
3. **梯队建设**：{培养动作}
4. **组织挑战**：{待解决的问题}
5. **招聘和补员**：{缺位和计划}

## 三、S{2/1} 规划

### O1：【{方向标签}】{一句话目标}

1. **{引词}：**{具体交付 + 量化目标 + 时间节点}
2. **{引词}：**{具体交付 + 量化目标 + 时间节点}

### O2：【{方向标签}】{一句话目标}

{同上结构}

### O3：【{方向标签}】{一句话目标}

{同上结构}

### O4：【{方向标签}】{一句话目标}

{同上结构}
```

### 写作原则

- **三段式结构**：做业务 → 建团队 → 下期规划。这是 D 级述职的标准框架
- **引词 + 短句格式**：每条 KR 用"**引词：**描述"格式。引词是 2-4 个字的方向标签（"行业交付""体验治理""AI 专项""团队建设"）
- **数字密度极高**：几乎每条都有数字——百分比、天数、人月、版本号、日期。"秒开率从 65% 提升到 80%"比"显著提升"好 10 倍
- **成就 + 反思双栏**：每个专项都要有"不足"部分，不是"还有提升空间"这种废话，而是具体的根因分析
- **量化目标用"从 X 到 Y"**：不说"提升"，说"从 65% 提升到 80%"。不说"降低"，说"降 50M"
- **时间节点具体**：不用"尽快完成"，用"截止 730 完成"。不用"下半年"，用"S2 结束前"
- **承上启下**：S1 述职的后半部分就是 S2 规划，形成闭环
- **竞品对标常态化**：频繁使用"不输携程""追评同程""行业第一梯队"等竞品对标表述
- **AI 作为独立板块**：2025 年后，AI 转型必须作为独立板块汇报，不混在日常交付里

### 范例结构（来自 FY26S1 述职）

> Slide 2 总览（4 大板块：行业交付/体验架构/AI 转型/组织建设）→ 一）超级对齐专项（一期&二期）→ 二）入淘及性能保障 → 三）问一问交付及架构升级 → 四）端架构治理 → 建团队（组织稳定性）→ S2 规划（O1 行业&大促 / O2 体验&入淘 / O3 架构&基建 / O4 团队建设）

| 类别 | 常见引词 |
|------|----------|
| 交付类 | C 端交付、B 端交付、行业交付、关键交付、出海支持 |
| 体验类 | 体验治理、性能保障、搜推体验、体验专项 |
