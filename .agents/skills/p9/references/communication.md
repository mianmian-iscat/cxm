## 核心沟通原则

### 通用法则

1. **结论先行** — 第一句话就亮出核心观点。不是"背景、分析、结论"，而是"结论、证据、下一步"。写周报时开篇就是稳定性数据，写汇报时开篇就是"三个一句话"总结，写技术文章时开篇就是缘起故事。读者在前 30 秒就要建立基线认知。
2. **证据优于断言** — 每个论断都需要数据或具体案例支撑。不说"性能有提升"，说"秒开率从 83% 提升到 91.6%"；不说"团队做了大量工作"，说"P0 需求 59 个，其中 53% 已发布"。
3. **区分事实与判断** — 标明哪些是已知事实、哪些是假设、哪些是建议。"本周 Push 打开率稳定在 2.6 左右"是事实；"这类 Push 对日活和体验都是有很好的帮助的"是判断。二者不混。
4. **明确诉求** — 如果需要听众采取行动，说清楚要什么、谁来给、什么时候要。"@张三 在推进中，下周继续追进度"比"此事在推进中"有力得多。
5. **篇幅适度** — 文档该多长就多长，不要冗余。周报可以长（因为覆盖多个项目线），但每段内部紧凑；向上汇报必须精炼。
6. **一文档一目的** — 不要把决策请求和状态更新混在一起。周报是状态同步，决策备忘录是推动决策，规划报告是获取对齐和批准。

### 三种结论先行模式

- **数据结论前置** — 开篇即呈现稳定性指标和核心 KPI，再展开细节。周报以"日活均值稳定在 360W""Crash 率万二以内"开头，读者第一秒就知道基本面是否健康。
- **战略结论前置** — 面向未来的文档以宏观行业或业务判断开篇，为后续技术讨论定调。"从 2007 年淘宝首页上有了一个'机票'的 Tab 伊始，'旅行'这件小事在阿里就一发不可收"——先给出时代定位，再展开技术叙事。
- **问题-方案-收益三段式** — 每个主题遵循紧凑序列：(1) 用 1-2 句话定义问题，(2) 描述方案，(3) 用数据展示结果。"安装包控制难度加大 -> @李四 牵头明确了两件事 -> 启动非活跃 Native Page 的梳理工作"。

### 通用文档模板

```
[一句话结论或核心指标]
  [背景与现状 — 2-3 句话]
    [重点事项展开，按优先级排序]
      [风险与挑战 — 不回避，带感叹号也不丢人]
        [下一步或明确诉求 — 有人名、有时间点]
```

## 周报写法

周报是技术管理者最核心的周期性输出。它不只是状态同步，更是管理节奏的锚点、团队文化的载体、向上汇报的原始素材。

### 周报结构

周报采用中文序号分层，稳定性数据永远排在第一位：

```
## [团队名]周报 [日期]

### 一）线上稳定性情况（或"线上稳定性概况"）
- 核心运行指标：日活、Crash 率、秒开率、接口达标率
  - 每个指标：具体数值 + 环比变化 + 归因 + 负责人
- 本周线上问题：问题描述 + 根因 + 已采取的措施 + 制度性改进

### 二）本周重点项目进展情况（或"本周重点事项"）
1. [最重要的项目/战役]：进展 + 数据 + 风险
   - 子项目 A：状态 + @负责人 + 时间节点
   - 子项目 B：状态 + @负责人 + 时间节点
2. [第二重要的项目]
3. ...

### 三）团队建设（或"团建 & 技术方面"）
- 招聘进展、组织变动
- 技术基建和工具更新
- 方向性思考（务虚脑暴的结论）

### 四）团队心声
- [管理者自己的思考]
- [精选团队成员心得，每人一段]
```

### 稳定性数据写法

稳定性数据是周报的"血压计"，每一项都要做到：具体数值 + 变化归因 + 风险评估 + 人名。

**格式范例**：

```
- 猪客本周运行概况：本周日活均值稳定在 [X]W，受[原因]的影响，
  日新增日活有[方向]变化。客户端稳定性外在表现本周[状态]。
  - Crash 率：IOS 和 Android 端最新版本 Crash 率为万分之[X]，
    [具体归因]。本周 [版本号] 发布，[功能简述]，稳定性方面，
    [问题修复情况]，再次回归正常水位。本周总体表现平稳。
  - 包大小方面，[版本号] 控制在 [X]M 以内。
    [矛盾描述]。@[负责人] 牵头明确了[几件事]，
    [具体行动]。
  - Push 稳定性情况：本周 Push 打开量 [X] 万，
    Push 打开率稳定在 [X] 左右。[新动作进展]。
```

**关键原则**：

1. **数据要精确到版本号** — "8.5.8 控制在 93M 以内"而非"包大小控制良好"
2. **矛盾要直接命名** — "我们费了九牛二虎之力降下来的 Buffer 很快被新增的外部包占满，安装包控制难度加大"
3. **风险要敢于感叹** — "稳定性的机制保障依然是我们将长期面对的巨大挑战！！"
4. **每个 action 有人名** — "@李四 牵头明确了两件事"、"@张三 在推进中"

### 重点项目写法

项目进展不是活动日志，而是"里程碑 + 数据 + 风险 + 人名"的组合。

**格式范例**：

```
1. [项目名]（[别名]）研发进展顺利，作为[背景定位]，
   目前进入[阶段]。整体思路仍是[策略简述]，
   从[几]个方面来做：第一[方向A]，第二[方向B]，
   第三[方向C]。比较期待[下一个节点]，简述下各子项目进展：
   - [子项目A]：[完成状态]，[具体数据]。
   - [子项目B]：[状态]，@[负责人]在推进中，下周继续追进度。
   - [子项目C]：[状态]，[时间节点]之前[交付目标]。
```

**长项目可以穿插叙事**——在进展描述中嵌入方向性思考：

```
- 本周和[人名]一起明确了[方向]的[计划]，目标是[目标]。
  早在 [年份] 年我刚 Base 到杭州时成立了[小组名]，
  搭档[人名]和[人名]寻求[方向]在飞猪的落地，
  当时借了[背景]的一阵小高潮，但很快我也被调去做[其他方向]了，
  这个方向上我做了短暂的尝试就搁浅了。
  但[方向]的探索不应当终止。在新的财年，
  我们需要在技术投入上更具决心……
```

这种叙事的价值在于：让读者（尤其是上级和跨团队伙伴）理解一个技术方向的来龙去脉，而不只是知道"本周在推进"。

### 风险与挑战写法

风险不是附录，而是周报的核心价值之一。写法要求：

1. **直接命名问题** — "浙江电信接入本周受阻，下单失败率很高"
2. **给出影响判断** — "至于具体失败的概率有多大以及影响，浙电侧尚未给出具体的答复"
3. **嵌入反思** — "尽管 App 在 Crash 率上控制有方，但在更多维度的'不可用'定义、监控和测试效率上仍然短板巨大"
4. **标明跟进人** — "@张三 在推进中，下周继续追进度"

### "团队心声"板块

"团队心声"不是社交公告栏——它服务于四个管理目的：

1. **向上展示团队文化** — 让领导层看到团队的活力和深度
2. **传递技术理念** — 管理者自己的心得潜移默化地强化方向
3. **暴露真实关切** — 团队成员的洞察常常编码了真实的痛点
4. **建立技术品牌** — 对外展示团队的思考深度

**管理者自己的心声格式**：

```
- 拔赤：
  - [个人成长/反思]：本周第一次[事件]，[感悟]。
  - [管理思考]：Q4 给自己定的小目标，[目标]，[进展]。
    最大的体会，[核心观点]。最大的遗憾，[坦诚的不足]。继续加油！
  - [阅读/思考]：重读了《[书名]》，也[让自己怎样一下]，
    [感悟]，何其难。
```

**团队成员心声格式**：

```
- [花名]：[技术观察/行业思考/工作方法论/个人感悟]
  - 精选那些将个人成长与技术方向关联的内容
  - 而非泛泛的状态总结（"本周很忙"没有价值）
```

心声板块是管理者可以"夹带私货"的地方——技术判断、管理理念、对行业的看法，都可以通过自己和成员的声音传递出去。

## 月报写法

月报是综合提炼，不是周报的合集。随着管理范围的扩大（从约 30 人到 150+ 人），报告频率从周报降低到月报，但信息密度提升。

### 月报结构

```
一）核心 OKR 指标进展
   - 关键绩效指标 vs. 目标
   - 用数据说话，不做主观粉饰

二）本月重点事项（3-5 个）：
   - 每个事项的进展 + 数据 + 关键突破
   - 按业务领域分组，不按时间线罗列
   - 每个领域有"做了什么 → 效果如何 → 还差什么"的完整弧

三）团队建设
   - 招聘、晋升、组织变动
   - 关键人才盘点结论

四）思考与声音
   - 对战略或组织的方向性思考
   - 团队成长观察
```

### 周报 vs 月报

| 维度 | 周报 | 月报 |
|------|------|------|
| 频率 | 每周 | 每月 |
| 粒度 | 项目级、子项目级 | 领域级、战役级 |
| 稳定性数据 | 逐指标展开 | 趋势性总结 |
| 叙事 | 穿插方向性思考 | 提炼方向性结论 |
| 团队心声 | 多人多条 | 管理者核心观点 |
| 适用阶段 | 团队 30-60 人 | 团队 60-150+ 人 |

### 月报的提炼方法

月报不是"把四周的周报订在一起"，而是从月度视角重新组织信息：

1. **提炼主线** — 这个月最重要的三件事是什么？不是二十件。
2. **呈现趋势** — 不是"本周 Crash 率万二"，而是"过去四周 Crash 率从万二下降到万一，创了新低"。
3. **暴露结构性问题** — 周报中可以追踪单个 bug，月报应该看到"架构稳定性靠人肉"这类结构性问题。

## 向上汇报

### 目的

以高层领导需要的格式，提供他们需要的信息。向上汇报的核心不是"展示我做了多少事"，而是"让领导有信息做出决策"。

### "三个一句话"开场

D 级述职的开场用三句话概括整个周期：

```
一句话总结业务结果：[核心指标达成情况]
一句话总结技术建设：[最重要的基建成果]
一句话总结团队状态：[组织能力的关键变化]
```

这三句话的作用是让领导在 30 秒内建立对全局的认知框架，后面的内容都是展开和补充。

### 四段式汇报框架

```
1. 现状如何 — 本周期的关键稳定性指标和业务指标
   数据表格化，一眼可见达成/未达成
2. 做了什么 — 3-5 个优先事项及里程碑进展
   标记为 M1/M2/M3，每个事项有"达成 + 反思"双视角
3. 建了什么 — 基础设施演进和团队建设
   技术能力沉淀、人才梯队变化
4. 需要什么 — 资源缺口、跨团队协调、方向性决策
   用数据暴露缺口，让听众自己得出结论
```

### 成就 + 反思双视角

每个板块的汇报都采用双视角——不只是"做了什么"，还有"还有什么不够"：

```
[达成的结果] — 具体数据
[反思/不足] — "尽管...但在更多维度的...仍然短板巨大"
[下一步] — 基于反思的行动计划
```

这种模式的典型案例：
- "尽管 App 在 Crash 率上控制有方，但在更多维度的'不可用'定义、监控和测试效率上仍然短板巨大"
- "尽管未能达到预定的日均 500 万的业务目标，但从数据回落上看，整体的流量依然呈现着健康的向上的态势"

**关键**：反思不是自谦的修辞，是对真实差距的命名。"最大的遗憾，高 P 养成计划，苗子少，难度高！继续加油！"

### 将工作打包为战役

复杂的多项目工作以"战役"形式汇报，而非零散的状态条目：

```
[战役名称]：[一句话定位]
- 整体思路：[策略简述]
- 子项目 A：[负责人] + [里程碑] + [数据]
- 子项目 B：[负责人] + [里程碑] + [数据]
- 子项目 C：[负责人] + [里程碑] + [数据]
- 风险项：[具体风险 + 兜底方案]
- 诉求：[需要什么支持]
```

案例："王者归来项目"作为财年结束前最后一波猪客日活冲刺项目，整体思路是延续王者荣耀二期，从三个方面来做——第一强化客户端产品和基础服务体验，第二借助流量冲锋为抓手优化流量流转和留存，第三技术侧兜底。

### 汇报中的诉求艺术

不要直接要资源。相反，用数据暴露缺口，让听众自己得出结论：

1. **如实陈述招聘进展** — "本周加速招聘，终面通过的不多，下周继续"
2. **用产能数据对比承诺范围** — 展示缺口，不加主观评价
3. **将方向性诉求嵌入"下一步重点"** — 暗示本周期不应再给团队加什么
4. **在对齐会中直接决策请求** — 将领导的原话反馈记录为行动项

**关键原则**：明确的资源请求留给已对齐的沟通；永远不要在正式汇报中首次提出资源诉求。

### 向前看的桥接

每个板块的结尾用前瞻性桥接送尾——不是"汇报完毕"，而是指向下一个周期的方向：

```
"回顾 [周期] 里我们经历的 [战役A]、[战役B]、[战役C]，
我们用了一整年的时间来专注于[方向]，
[核心收获]，是我们这一年来经历的这些项目后最大的收获！
未来一年我们仍然会聚焦[方向]，
在[具体领域]等方面更加聚焦的来打，
和各位合作伙伴一起把[目标]推向新的水平。一起加油！"
```

### 向上汇报原则

1. **他们很忙** — 简洁。"三个一句话"开场不是装饰，是必需品。
2. **他们需要决策，不是信息** — 将问题框定为需要他们做出的决策。
3. **坏消息要早** — "稳定性的机制保障依然是我们将长期面对的巨大挑战！！"——感叹号不丢人，隐瞒问题才丢人。
4. **数字优于叙述** — "延迟降低 30%"比"我们取得了很好的进展"有力得多。
5. **与他们的目标关联** — 展示你的工作如何支撑他们的优先级。技术项目的价值要换算成钱——投入多少、收益多少、回本周期多长（[roi-thinking](roi-thinking.md)）。

### 向上汇报的反模式

- **状态堆砌** — 罗列团队做的所有事情，没有优先级。
- **只报喜** — "尽管未能达到预定的日均 500 万"——如果省略这句话，汇报就失去了可信度。
- **没有诉求** — 汇报不提任何请求，错失获得帮助的机会。
- **过于细节** — 受众不需要知道每个 Bundle 的名字。

## 规划报告

### 目的

获取对计划的对齐和批准。规划报告不是"我打算做什么"的独白，而是"我打算这样做，你们同意吗"的对话发起。

### 叙事弧线型规划

面向未来的技术规划不应该是干巴巴的列表，而应该有叙事弧线——从时代背景到技术演进到具体打法到展望未来：

```
一）[时代定位] — 站在什么十字路口
   "从 2007 年淘宝首页上有了一个'机票'的 Tab 伊始..."
   先建立"为什么是现在"的紧迫感

二）[问题定义] — 旧貌和新颜之间的矛盾
   用叙事方式展开技术挑战的来龙去脉：
   "早在 [年份] 年...但很快...这个方向上做了短暂的尝试就搁浅了"
   让读者理解问题的历史纵深

三）[本土生存] — 聚焦矛盾、修炼内功
   飞猪独有的难题 + 解法，逐个展开
   每个域有"问题 -> 方案 -> 证据 -> 还差什么"的完整弧

四）[工程实战] — 中台/平台建设的实战
   从技术网关到业务网关的蜕变
   具体工具、具体数字、具体人

五）[展望未来] — 脚踏实地、即是面向未来
   "KPI 非常重要，但 KPI 背后的用户价值更加重要"
   回归初心，给出方向性判断
```

### 章节标题的文学性

规划报告的章节标题不应该是"一、背景 二、方案 三、总结"。用对仗或比喻给章节命名，让读者记住结构：

- "大浪淘沙——站在时代的十字路口"
- "旧貌新颜——旅行电商的荆棘之路"
- "本土生存——聚焦矛盾、修炼内功"
- "遇山开山——新零售端侧中台实战"
- "从心开始——构建多彩的旅行生态"
- "脚踏实地、即是面向未来"

### 规划报告的结构要素

```
[计划概要] — 我们打算做什么，2-3 句话
[为什么] — 驱动这个计划的问题或机会
[做什么] — 关键交付物和里程碑
[怎么做] — 方法、技术选型、资源计划
[谁来做] — 团队和职责分工，有人名
[时间线] — 关键里程碑时间表
[风险] — 可能出什么问题及如何缓解
[依赖] — 需要他人提供什么
[指标] — 如何衡量成功
```

### 规划中嵌入"我们为什么要自建"

飞猪的技术规划经常需要回答"为什么不直接用集团中台"。写法是：

1. **先承认集团能力的价值** — "飞猪是集团基建非常大的受益方"
2. **再精确命名差异** — "但大导购域在飞猪的落地面临很多实际的困难，最大的困难就是诸多业务纵深内的商品模型、内容模型和容器模型的统一"
3. **给出具体案例** — "酒店日历房是宝贝吗？内容详情和商品详情有什么本质区别？"
4. **结论** — "这种情况下，如何在端侧技术找准方向，助力业务突破，并找到一条适合飞猪自己的旅行电商之路，将是对我们极大的考验"

## 技术分享与演讲

### 技术叙事的起源模式

技术文章/演讲不是从"问题"开始的，而是从"我"开始的——个人经历赋予技术叙事以合法性：

```
"2013 年我来到阿里旅行（那时还叫'淘宝旅行'），
到现在也快三年，很庆幸自己跟随业务一起快速成长，
更幸运的是亲身经历了旅行垂直行业和整个阿里电商的
无线 All In 大潮……"
```

这种"缘起"模式的作用：
1. 建立"为什么听我讲"的合法性——不是因为职位，而是因为经历
2. 让技术演进有了时间轴——读者可以跟着你从 2013 走到现在
3. 为后续的自嘲和反思提供了情感基础

### 技术演进作为叙事弧

不是"我们做了 A、B、C"，而是"我们从 A 走到了 B，中间经历了什么"：

```
[起源] — "2013 年'淘宝旅行'还是一个规规矩矩的 PC 站点"
[转折] — "但变化来的如此之快，超过所有人的想象，
         似乎几乎一夜之间 PC 就成了过去时"
[困境] — "体验上简直天上地下"（自嘲）
[突破] — "H5 页面带动了流量，流量的拉动又对 H5 提出更苛刻的诉求"
[沉淀] — "现在回头看，2014 年真的是忙碌的一年..."
```

每个阶段都有：
- 具体的工具名（Clam、KISSY MINI、html-proxy）
- 具体的人名（@王五、@钱六、@周八）
- 具体的数字（"日活从万很快增长到十万，并一度逼近百万"）
- 具体的情感（"简直天上地下"、"让人很不痛快"、"想想就觉得棒棒哒"）

### 五段式技术演讲框架

适用于 ATA 文章、QCon 分享、技术峰会等场景：

```
1. 缘起（为什么是我来讲）— 个人经历 + 时代背景，建立合法性
2. 问题定义（难在哪里）— 从"我"的经历放入行业共性问题
3. 技术演进（怎么走过来的）— 每个阶段有工具、有人、有数据
4. 实战（展示给我看）— 架构图（必须有）、前后对比、性能数据
5. 反思与展望（现在回头看）— 坦诚评估 + 有据可依的下一步
```

> 五段式框架与"论文格式解题"（序论 → 选型 → 解法 → 结果 → 展望）结构一致，详见 [management-tips](management-tips.md) 第二锦囊。

### 短时演讲结构

适用于 15-20 分钟的演讲：

1. **钩子** — 听众为什么要关心？（1 分钟）
2. **背景** — 现状是什么？（2 分钟）
3. **核心信息** — 你希望他们记住的那一件事（1 分钟）
4. **证据** — 3 个有数据支撑的论点（10 分钟）
5. **启示** — 这对听众意味着什么（3 分钟）
6. **行动号召** — 他们接下来该做什么（1 分钟）

### 演讲中的"自嘲"与"自嘲的度"

自嘲是建立亲和力的工具，但不能变成自我贬低：

- **好的自嘲**："体验上简直天上地下"——让听众会心一笑，然后理解 H5 初期的粗糙
- **好的自嘲**："想想就觉得棒棒哒"——让技术工作有了人情味
- **好的自嘲**："尼玛他发版了，而且没告诉我"——让协作痛点变得生动
- **不好的自嘲**：对自己团队能力的否定——这会动摇领导对团队的信心

### 架构图的作用

技术分享中架构图是必须的——它不只是信息载体，更是叙事的锚点：

1. **先给出全局图景** — "这也是绝大多数同学所熟悉的一张图"
2. **再逐层展开** — 每一层都有故事和细节
3. **用颜色区分归属** — "橙色的模块和非橙色的模块组成了一个完整的混搭体"

### 演讲原则

1. **一个核心信息** — 如果他们只记住一件事，那是什么？
2. **证据优于观点** — 数据、案例、对比。
3. **故事优于统计** — 人们记住故事；用统计来支撑故事。
4. **用类比降低认知门槛** — "物理组合需要演进到化学组合"
5. **架构图先行** — 先建立全局图景，再深入细节。
6. **练好第一分钟** — 开场决定了人们是否会继续听。

## 数据驱动论证

### 四层证据

用四层递进的数据来构建有说服力的论证：

1. **基线** — 每周期报告的指标（Crash 率、秒开率、日活），建立基本面健康的信任。"猪客本周运行概况：本周日活均值稳定在 360W"
2. **趋势** — 展示随时间推移是改善还是恶化的方向性变化。"IOS 端 Crash 率控制在万 1 左右，创了新低"
3. **对比** — 前后对比或 A/B 指标，展示特定变更的效果。"交叉营销推送打开率较之前提升了 30% 以上"
4. **业务影响** — 将技术结果与商业价值关联。"火车票随机立减带来日拉新峰值过万，均值超过六千"

### 数据呈现原则

1. **数据 + 判断** — 永远不要只给数字不给解读。"2% 的打开率，这个打开率是极低的"——数字后面紧跟判断。
2. **数据 + 归因** — 解释数据为什么是这样。"Push 打开率交上周（4.3%）上升到超过 7%，也是因为全量 Push 和圈人营销类 Push 数量（分母）下降导致"
3. **数据 + 基线** — 通过行业对比或历史基线建立参考点。给出行业排名图、历史走势线。
4. **数据 + 行动** — 每个数据点都应指向下一步行动。"目前我们的位移消息完全依赖于地动仪的输血...技术上我们需要自己把这个短板补全...这方面进展缓慢，需要加速（@郑十一）"

### 数据归因的诚实性

数据驱动不等于数据粉饰。当数据不好时，直接说：

- "至于具体失败的概率有多大以及影响，浙电侧尚未给出具体的答复"——承认信息不足
- "实际上 Crash 率略高于万一，已经修复"——发现数据偏差时立即修正
- "我们能看到端稳定性数据实际存在大量幸存者偏差"——命名方法论的局限

### 证据链公式

```
基线数据 -> 采取的行动 -> 结果数据 -> 归因 -> 局限性 -> 下一步
```

案例：

```
基线：Push 打开率稳定在 2.6 左右
行动：参与了 Oppo Push 通道的公测 + 交叉营销推送 + 酒店行程提醒推送
结果：交叉营销打开率超过 4%，酒店行程提醒打开率超过 5%
归因：交叉营销推送打开率较之前提升了 30% 以上，特别赞吴十算法团队的支持
局限：在没有其他任何运营工具接入的情况下达到的效果，但传播的量逐日下滑
下一步：运营手段要跟上；传播物料除了流量之外，还可以是某类商品和内容
```

### 线上问题的数据化复盘

线上问题的汇报格式：

```
[问题描述] — 本周发生[几]起典型线上问题，[简述]
[严重性判断] — 从严重性上看[大/不大]
[反映的本质] — 但反映出的问题很典型，都是[根因类别]
[具体措施] — 已[修复/优化/增加监控]
[制度性改进] — 借此[建立了什么制度/流程]
```

案例："这两个问题从严重性上看并不大，但反映出的问题很典型，都是前端业务触发了端架构底层的 bug...架构改造的稳定性有相当的隐患，架构稳定性靠人肉"

> 接手外部系统或技术遗产时的故障定责复盘，有更完整的功课清单和复盘姿势，见 [system-handover-and-ownership](system-handover-and-ownership.md)。

## 明确诉求

### 核心原则

让听众知道你需要什么，但永远不要让他们觉得你在抱怨。

### 四种诉求策略

1. **通过暴露风险间接诉求** — 如实陈述风险，资源含义不言自明。"50% 需求处于草稿状态，PD 需加大投入"——不说"PD 不够"，说数据，让读者自己得出"PD 需要加人"的结论。

2. **数据缺口引出资源需求** — 呈现招聘进展或产能数据，不做主观评价。"本周加速招聘，终面通过的不多，下周继续"——缺口自己会说话。

3. **方向性思考作为隐性诉求** — 在技术讨论中嵌入资源诉求。"我们认为这类 Push 对日活和体验都是有很好的帮助的...目前这方面技术的投入非常薄弱"——不直接说"给我算法工程师"，但意思到了。

4. **在对齐会中直接决策请求** — 在结构化的共创会中，将领导的原话反馈记录为行动项。这是唯一适合直接提出资源诉求的场合。

### 项目小结中的诉求

项目小结（如"王者归来项目小结"）的结尾是天然的诉求窗口——通过"遗憾"来暴露缺口：

```
"本次日活冲刺还是有不少遗憾，
比如[项目A]和[项目B]等没赶上春促，
[方向C]的流量挖掘的还不透彻，
[方向D]的技术策略还需优化。
尽管我们做了最大努力，
最终日活表现和我们的目标周日均 [X]W 相差还有一定距离。
这些点都是可以持续提升的。"
```

### 致谢即政治

项目小结的致谢不是客套，而是对协作关系的确认和投资：

```
"最后感谢我们各个项目的 PM：[花名列表]。
还有产品大 PD [花名]。
感谢整个项目组里所有成员，
感谢你们的努力和相互理解与支持！
感谢 [上级/兄弟团队花名列表] 给予的大力支持！
感谢飞猪大团队所有提名字的和没提名字的兄弟姐妹们，
让我们一起继续努力冲击更高的目标！"
```

**原则**：致谢要具体到人名，"提名字的和没提名字的"这种表达既覆盖了所有人，又暗示了你确实想了该感谢谁。

### 诉求的反模式

- **抱怨** — 只陈述事实不带情绪；永远不说"太难了"。
- **推责** — 当问题涉及其他团队时，说"需要跨团队协调"而非"他们没有交付"。"至于具体失败的概率有多大以及影响，浙电侧尚未给出具体的答复"——陈述事实，不评价对方。
- **模糊** — 不是"我们需要支持"，而是"我们需要两个产品设计师，为期三周"。
- **错误的场合** — 在合适的层级和场合提出诉求；永远不要在正式汇报中首次提出资源请求而不提前对齐。

## 写作风格

### 结构标记

- **中文序号分层** — 一级用"一）二）三）"，二级用"1. 2. 3."，三级用"-" bullet points
- **关键结论加粗** — 在段落中加粗关键结论，使其在快速浏览时脱颖而出
- **链接嵌入正文** — 包含支持文档的链接，供想深入了解的读者使用，格式为 `[链接文字](URL)`
- **人名用 @ 前缀** — "@李四 牵头明确了两件事"、"@张三 在推进中"
- **版本号精确** — "8.5.8"、"8.6.7"，不说"最新版"

### 语言特征

- **客观、克制，但关键时刻敢于感叹** — "稳定性的机制保障依然是我们将长期面对的巨大挑战！！"
- **自嘲和幽默穿插在技术叙述中** — "体验上简直天上地下"、"想想就觉得棒棒哒"、"尼玛他发版了"
- **叙事性过渡** — 不是"下面讲第二点"，而是用叙事衔接："但变化来的如此之快，超过所有人的想象"
- **技术细节和业务上下文混合** — 同一个段落里既有 Crash 率数据，也有对业务策略的思考
- **个人反思嵌入工作汇报** — "最大的体会，技术上的追求卓越是对自己彻底的不设边界，警惕'PM'，沦为 PM 是一件很悲哀的事"
- **一起加油** — 每个板块的结尾用"一起加油！"收尾，这是团队凝聚力的语言信号

### 技术文章的语体

技术文章（ATA、公众号、演讲文稿）采用"讲故事 + 讲技术"的混合体：

1. **从个人经历切入** — "2013 年我来到阿里旅行..."
2. **技术演化作为叙事主线** — 不是功能列表，而是"从 A 到 B 到 C"的时间线
3. **具体的工具和人** — 每个阶段命名具体的工具（Clam、KISSY MINI、Bridge 适配器）和具体的人（@王五、@钱六）
4. **自嘲作为节奏调节** — "简直天上地下"、"让人很不痛快"
5. **回顾性框架** — "现在回头看..."、"现在回过头来看..."
6. **技术判断嵌入叙事** — "这个动作非常非常必要"、"这段时期对航旅来说是极其痛苦的一段时光"

### 周报的语体

周报更加紧凑和结构化，但仍然保持个人色彩：

1. **数据开头** — 每一项都是数据先行
2. **项目有"简述下各子项目进展"的过渡** — 先讲整体思路，再分述
3. **风险直言不讳** — "有一定风险"、"短板巨大"、"巨大挑战！！"
4. **期待和鼓励** — "比较期待本期冲刺，下周春促开启，一起加油！"、"期待效果"、"值得期待"
5. **技术洞察穿插在项目进展中** — 不是独立板块，而是在项目描述中嵌入对技术方向的思考

### 项目小结的语体

项目小结介于周报和技术文章之间——有数据总结，有过程回顾，有技术深度，有情感表达：

1. **数据结果先行** — "日均 DAU 为 410 万，相比去年同时段的 147 万日均 DAU 翻倍不止。其中峰值高达 491 万。"
2. **诚实的差距** — "尽管未能达到预定的日均 500 万的业务目标"
3. **过程回顾有结构** — "我们做到了以下 3 点："
4. **技术磨砺单独成段** — "除了这些用户有明显感知的部分的明显进步，在技术保障方面我们也做足了功课"
5. **回顾性升华** — "回顾 2018 财年里我们经历的百天大战、场景化战役、王者荣耀一期、王者荣耀二期、王者归来项目"
6. **致谢收尾** — 具体到人名

### 沟通的反模式

- **活动日志** — 罗列任务或时间线，没有结论。
- **没有上下文的术语** — 技术词汇不解释为什么重要。
- **装饰性指标** — 数字好看但对决策没有影响。
- **埋没的实施细节** — 在决策场景中，以选择而非构建过程开头。
- **无主的架构图** — 没有明确归属和采纳状态的图表。
- **用战略词汇包装日常工作** — 用宏大语言膨胀常规任务。
- **没有证据的绝对结论** — 缺少支撑数据或不确定性标记的断言。
- **"最新"、"目前"代替版本号** — 读者三个月后回看时不知道"最新"是哪个版本。
