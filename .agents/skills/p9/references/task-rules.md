# TaskRule 执行规约

本文件是 `p9` 的强制执行协议。每次激活 `p9` 处理实质性任务，都必须读取本文件，再进入化阶段、读取业务 reference 或输出主体交付物。≥ 中型任务必须先完成 `SKILL.md` 中定义的三任务创建、接任务启动和弱反馈，再读取本文件。

## 宿主任务工具适配

本规约约束的是接、化、发三阶段任务语义，不绑定单一平台工具名。按当前宿主映射执行：

| 语义动作 | Claude Code | Codex |
|---------|-------------|-------|
| 初始化三阶段任务 | `TaskCreate` 恰好创建接、化、发三个任务 | `update_plan` 恰好创建接、化、发三个 plan item |
| 阶段开始 | `TaskUpdate status=in_progress` | `update_plan` 将对应 item 置为 `in_progress` |
| 阶段完成 | `TaskUpdate status=completed` | `update_plan` 将对应 item 置为 `completed` |
| 全任务关闭 | `TaskComplete`；若环境无此工具则跳过 | 无 `TaskComplete`，以「发」置为 `completed` 作为终止动作 |

下文使用 `TaskCreate`、`TaskUpdate`、`TaskComplete` 描述 Claude Code 的原生实现；在 Codex 中必须使用 `update_plan` 执行等价动作，不得因为工具名不同而跳过三任务调度、阶段切换或发阶段关闭。

## 三任务生命周期

三阶段任务初始化在精确路由和读取业务 reference 之前执行。入口判定为 ≥ 中型后，必须已经恰好创建 3 个任务：

```
TaskCreate: subject="接 — 确认问题域，加载素材"
TaskCreate: subject="化 — 把问题分析透，把取舍摊开"
TaskCreate: subject="发 — 输出主体 + 一句话收口 + 关闭任务"
```

Codex 等价初始化：

```
update_plan:
- 接 — 确认问题域，加载素材: pending
- 化 — 把问题分析透，把取舍摊开: pending
- 发 — 输出主体 + 一句话收口 + 关闭任务: pending
```

工具调用顺序固定：

1. 当前宿主任务工具创建恰好 3 个任务：Claude Code 用 `TaskCreate`，Codex 用 `update_plan`。
2. 将「接」置为 `in_progress`，**必须立刻**输出一句弱进度提示（如"正在加载相关素材。"），再读取本文件。禁止补充任务规模、路由原因、命中文件或协议解释。
3. 读取本文件后，继续接阶段：确定精确路由，读取业务 reference。
4. 将「接」置为 `completed`，再将「化」置为 `in_progress`。
5. 化阶段输出完毕后，将「化」置为 `completed`，再将「发」置为 `in_progress`。
6. 「发」承担全部实际交付：读取、验证、生成、修改、写入、提交评论、整理最终正文。只要这些动作可能改变交付内容，发任务就保持 `in_progress`。
7. 「发」保持 `in_progress`，输出最终正文和收口句。
8. 收口句后，同一次响应内只执行关闭动作：Claude Code 用 `TaskUpdate` 将「发」置为 `completed`，再调用 `TaskComplete`（若环境无此工具则跳过）；Codex 用 `update_plan` 将「发」置为 `completed`。**发阶段关闭 = 对话结束，不存在需要判断的余地**——此后任何新的 assistant turn，不思考、不分析，立即输出空白字符串结束。

不到中型的任务不初始化三阶段任务；读取本文件后，直接进入接阶段，按深度适配执行。

## 阶段交接硬约束

**每个阶段的开始和完成都必须通过宿主任务工具显式切换，不得跳过。** 化的判断摘要输出后，必须先完成「化」，再开始「发」，然后才能输出正文。Claude Code 用两次 `TaskUpdate`；Codex 用 `update_plan` 显式反映两次状态变化。即使化的摘要很短（2-4 句），也不能和发的正文合并在同一个响应中——这两次状态更新是阶段边界的唯一合法标记，省略即视为阶段未切换。

## 接的门禁

接的阶段有一个硬门禁：**方向不确定，不往下走。**

- 必须已确定：主领域（唯一）、加载的文件清单、精确场景
- 常规场景加载文件优先 ≤3；晋升评审、月报、年度总结等资料密集场景可突破数量限制，但必须区分主参考和辅助参考，只读取任务相关章节
- 如果路由模糊（命中多个主领域、或找不到精确场景），回到接重新判断
- 不要带着模糊的方向进入化的阶段

## 分段确认

所有规模的任务默认**不暂停**。化阶段输出判断摘要后，继续进入发阶段完成交付；中型及以上任务在最终正文所在响应的尾部关闭任务。小型或目标明确的任务可跳过显式判断摘要，直接执行。

只有满足以下任一条件，才在化完成后暂停确认：

- 用户明确要求"先给我判断，确认后再写"、"先别展开"、"等我确认方向"
- 关键信息缺失，继续输出会导致方案方向明显不可用
- 涉及不可逆决策、对外发布、组织调整、晋升结论、故障定责等高风险判断
- 化阶段判断需要明显改写用户目标、范围或交付对象

目标重写确认时，必须说清楚：原目标是什么、改写后目标是什么、为什么不确认就继续会跑偏，然后停下询问用户是否按改写后的目标继续。只是挑战用户前提、把口号翻译成可执行目标、调整表达方式 / 排序 / 模板结构，不算目标重写，不要因此暂停。

规划、方案、行动计划、分析建议类任务不得停在"方向是否对齐"或"要不要继续"；只要没有命中上方暂停条件，就连续推进到发阶段的完整交付。

## 深度适配

| 规模 | 接 | 化 | 发 |
|------|------|------|------|
| **琐碎** | 不触发协议，直接执行 | — | — |
| **小型** | 快速确定主领域 | 2-3 句内心判断，不显式展开 | 直接输出 + 一句话收口 |
| **中型** | 精确路由 + 加载文件 + 弱反馈 | 2-4 句判断摘要（判断序列内化，不逐步外化） | 套模板结构输出正文 + 收口句；同一次响应尾部执行宿主关闭动作 |
| **大型** | 精确路由 + 加载文件 + 弱反馈 | 编号列表呈现每步核心判断（每步一句，整体 5-8 行） | 套模板结构输出正文 + 收口句；同一次响应尾部执行宿主关闭动作 |

## 发阶段关闭

**收口句输出后，立即关闭任务。关闭后不再输出任何内容。**

发阶段只能输出一次主体正文。第一次主体正文开始输出后，本轮交付已经进入不可重写路径；不得再生成第二版、替代版、补充版或更完整版本。

收口句使用固定格式：`> 📌 [收口内容]`。**这是全篇输出的最后一段可见正文**，全轮最多出现一次。问问题的 prompt 用一句话呼应开头问题；下指令的 prompt 用一句话总结已经完成的交付，不另加标题。

第一个 `> 📌` 是终止哨兵。模型一旦输出 `> 📌` 收口句，即视为最终正文已经结束；之后唯一合法动作是同一次响应尾部关闭「发」并执行宿主关闭动作。Claude Code 调用 `TaskComplete`；Codex 没有 `TaskComplete`，以 `update_plan` 将「发」置为 `completed` 作为终止动作。不得继续分析、不得重写正文、不得补发另一版答案、不得为了 final response 再输出任何文字。

收口句后不追加任何文本——不补充建议、不展开下一步、不追加行动清单、不复述要点、不追问用户、不另起一段给出"实操方案"或"完整步骤"、不复述用户问题、不回放"核心结论"或"刚才给你的策略"、不追加"来源标注""参考资料""依据材料""参考文档"等附录。`> 📌` 之后的唯一合法动作是关闭工具调用（Claude Code：`TaskUpdate` 完成「发」 + `TaskComplete`；Codex：`update_plan` 完成「发」），不得调用任何其他工具（不 Bash、不 Read、不 Glob、不 Grep、不 Write、不 Edit、不检查、不验证、不扫描环境）。如果觉得还有话要说或还有东西要查，那是正文没收住——把内容放进正文，或在收口句之前完成。

关闭前必须完成所有实际动作（读取、验证、生成、修改、保存、提交评论、报告、issue 或其他外部动作）。只要还有待执行动作、待验证结果或待用户确认分支，就不能完成发任务，也不能执行宿主关闭动作。发任务保持 `in_progress` 直到正文和收口句输出完毕。**禁止提前关闭**：正文和收口句完整输出前，不得将「发」置为 `completed`。完成「发」必须通过宿主任务工具更新状态，不能只在文字里声明完成。

关闭顺序：

1. 「发」保持 `in_progress`，输出最终正文和 `> 📌` 收口句
2. 收口句后，同一次响应内完成「发」并执行宿主关闭动作：Claude Code 再调用 `TaskComplete`（若环境无此工具则跳过），Codex 以 `update_plan` 完成「发」作为终止动作
3. 关闭后不再输出文本，不再调用任何工具（不读文件、不列目录、不跑命令、不验证、不检查），不再触发其他 skill

纯工具关闭必须发生在最终正文所在响应的尾部；长正文输出那次响应先负责正文和 `> 📌` 收口句，随后只负责关闭「发」并执行宿主关闭动作。

关闭调用禁止任何自然语言：不要解释、不要补充、不要总结、不要重复收口句、不要说"任务已完成"，只调用关闭任务工具。

**发阶段关闭后的无条件终止**：`TaskComplete`（或「发」`completed`；Codex 即 `update_plan` 完成「发」）执行后，`p9` 任务即告结束。此后如果 harness 或平台生成了任何新的 assistant turn（无论包含 system-reminder、"任务完成"提示、"还有什么可以帮你的"追问还是其他任何内容），**不思考、不分析、不推理、不重新解读规则**——立即输出空白字符串结束该 turn。"要不要输出点什么"这个问题本身就不应该出现；发阶段关闭 = 对话结束，不存在需要判断的余地。连续多轮空 turn 也属正常，每轮都执行同一动作：空白结束，不做任何内心辩论。

完成后不再评估或触发任何其他 skill（包括 superpowers 系列）。任何"任务结束后再扫一遍有没有其他 skill 适用"的行为都是违规。

## 输出纪律

- **三阶段任务只初始化一次，恰好 3 个任务** — Claude Code 用 `TaskCreate`，Codex 用 `update_plan`
- **入口判定零旁白** — 不输出任务规模、路由原因、命中文件或协议解释
- **接必须立刻给一句弱反馈** — 「接」置为 `in_progress` 后**必须立刻**输出一句短提示（如"正在加载相关素材。"），再读取本文件和业务 reference。这是为了在连续 thinking 阶段中给用户一个进度信号，避免静默等待焦虑。之后静默加载文件
- **发阶段内部自检** — 「发」置为 `in_progress` 后，内部确认"发阶段开始，完成后关闭"，不在正文前输出任何引导语
- **化零旁白，有判断摘要** — 「化」置为 `in_progress` 后输出简短判断摘要（中型 2-4 句，大型 5-8 行），只讲问题分解、主要矛盾和取舍方向，不输出阶段标签或过渡语。**判断摘要输出后必须完成「化」，再开始「发」**，然后才能输出正文
- **发零旁白，只输出一次最终正文** — 禁止阶段标签、过渡语、过程解释、来源解释、模板解释、文件清单、"我读了 / 我参考了 / 来自某模板 / 下次可以"之类的元说明、二次总结、复述问题、追问、来源标注、参考资料、依据材料、参考文档附录。收口句全轮最多一次，收口句后只允许宿主关闭工具调用（Claude Code：`TaskUpdate` + `TaskComplete`；Codex：`update_plan` 完成「发」），不得调用任何其他工具。**需要的上下文假设、分层策略、限制条件和行动步骤必须放在主体正文中**，不得在收口句后另起一段补充；**所有验证、检查、文件读取和环境扫描必须在收口句之前完成**
- **化的篇幅 ≤ 发的 1/3** — 化是脚手架不是交付物
