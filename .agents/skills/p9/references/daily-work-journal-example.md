# 工作日常随记范例

> 这是一篇真实的工作日常随记，写于 2017 年 7 月。作者参加支付宝晋升面试后，有感于技术人的坚持与跨栈，写下这篇随笔。
>
> **使用说明**：此文件作为"工作日常随记"的范例模板保留。文中人物均为真实花名，阅读时请忽略具体人名，关注行文结构和表达方式。

---

上个月去参加支付宝的晋升面试，苏千 手下有几个 Node 领域的年轻技术高手 P7 晋升 P8。从他们对 NodeJS 技术领域的布局来看，还是小惊艳了一把。若干个高手晋升成功，苏千 兄今年也晋升到 P9。虽然他依然很胖，在那几个小时的场子里，摆脱业务 KPI 的碎念，还是感受到弄弄的唯技术味道，到底意难平。

我和苏千打交道比较早，追溯到 2010 年，淘宝第一批玩 Node 技术的小圈子就有他，和如今的 Swift 一样，Node 在当时仅是一股理念先锋，挂靠 JavaScript 语言被瞬间"玩"起来，和业务也挂不上钩，整个集团在当时共有三波人在玩 Node，北京的我加上阿里妈妈的李牧，淘系的玉伯、小马，再有就是空无的数据产品。我们把 Node 玩成了工具（Clam），淘宝把 Node 玩成了工程（Midway），只有空无的数据领域把 Node 玩出了产品，向上衔接工程，向下衔接物理数据。做出了最佳实践。苏千 就是在这个领域里持续坚持下来，一直到今天。

技术人总是情愿忠于某样东西。有些人忠于这个业务，有些人忠于团队的兄弟，有些人忠于一门技术。尽管这种工程师的体验很难被精确诠释，至少有一股无形的技术美感驱动，支撑着某些人坚持忠于一个方向，克服万难，一条道走到黑，直到拨云见月。这其中最含金量的亮点品质"坚持"和"技术跨栈"：

一）坚持、死寂一般孤独的坚持

在今年之前，Node 在阿里技术体系内的位置一直非常微妙，在工程效率层面始终受到 PHP 社区的挑战，在技术运维和性能层面收到传统 Java 社区的质疑，在其特有的对高并发支持的优势方面，也被看成语法糖式的 Hack，而不受正统技术流派的待见。在技术委员会内部的争议也非常大。但还是硬着头皮拧成了几个里程碑，第一，淘宝首页 Node 化，第二，TMS 工具 Node 化，第三，Midway 的开源，第四，工程外围体系补全，形成最佳实践。

至今我完全可以体会到淘宝首页第一期切 Node 时，工程师面临的忐忑，以及当时小马承担的压力。第一，技术上完全出力不讨好，所谓性能上的提升也只停留在理论上。第二，稳定性和可运维能力是否能优于之前的版本（PHP）。所以上线一个被广泛质疑的、（大流量面前的）稳定性没有经过实战考验的、而且和 KPI 没什么关系的 技术，是多么让人焦心的一件事情。

TMS 第二次大改版的全面 Node 化，外加 Midway 的开源，Node 才勉强在阿里技术大图里占据一个小方块。后来空无的数据魔方也走完他的历史使命，作为第一批的 Node 践行者@空无 @清笃 @朋春 也都燕飞各处，Node 必须要寻找新的生存空间。

Node 领域的艰难前行，所依靠的只有以苏千、朴灵、玉伯、汤尧 为首的几颗独苗，在压力和技术围堵下冒着被随时 HC 冗余掉的风险，死寂一般的坚持！

二）把局盘活，必须要跨栈

Node 本身是不错的技术，但 Node 如此薄的一层要被盘活，只靠 Node 自己是不够的，必须要跨栈。用 Node 把所有复杂度封装成工具，把零碎的工程领域（大前端）里各个碎片链接起来，不知疲倦的封装再封装，在鲁肃护盘之下星星之火开始燎原，走上一个快车道。

燎原之初的第一推力是"布局"，在玉伯的坚持之下，Node 领域细分成了 TWA、AntDesign、Basement 等应用层产品，同时也包括 tnpm、chair、egg、antd、dva 等基础性或脚手架级的产品。形成了一张大图：

这是一张若干年前的图，我们在很多晋升 PPT 里都能看到类似的图（我们是不是记得，很多P5升P6的同学都恨不得用这种图讲出四个现代化来，^_^），很幸运的，几个产品都有了不错的输出，已经在集团内部（包括我们）大量受益了。

第二推力是"组织保障"，我们都曾做过规划，所谓组织保障有三层意思，①首先是靠技术 Leader 个人的坚持。②再者是执行工程师需要在业绩 KPI 和技术坚持之间艰难的平衡。事实上只有少数一线工程师能破茧杀出走到底，大部分人走出第一步估计就被 KPI 压垮，随后迷失掉了。人的心力在这种情况下是需要经受住极大的煎熬，老板会换，业务会换，产品也是一茬一茬的换，过山车一般。③最后是技术高手的卡位，到底是因为人带起了技术产品，还是技术产品带起了人，似乎也傻傻分不清楚了。

第三推力，爬雪山过草地的勇气

如果没有老板的催逼，没有身边伙伴的鼓励，收不到甲方持续的反馈，缺少社区的技术认同，只靠一张务虚的"技术大图"就能支撑起自己坚持搞定，也算人中龙凤了。更何况大多时候需要动员，需要拉平认知，需要技术卡位，需要高姿态的护盘！！涉及到团队协作，落地难度更大。我从支付宝学到的最有价值的东西就是不断的动员，不断的给予正面反馈，不断的宣讲大图，一而再再而三的"刷存在感"，从弱弱的影响感染开始，用一个Q，用半年的时间去扩充阵营，扩大影响力。支付宝提倡的架构师精神的源泉始于此。上得了厅堂，画的图的确很高大上，下得了厨房，不厌其烦的宣讲，下基层，榜样带动，一行行的码出架构师的影响力！说实话，我到现在都做不到这种务实的高标准，拿爬雪山过草地的勇气来落这张图，我表示继续加强修炼。

第四推力，愿赌服输

Node 领域是一个很典型的因为某些人的坚持慢慢做出来的领域，从 2010 年清笃站到 QCon 第一个宣讲基于 Node 技术的淘宝数据产品开始，到今天 Node 技术栈的完善，在企业级 Node 应用破局道路上，一晃七年过去，苏千 兄也成功卡位。同样，阿里内部仍然存在大量不为人所知，迷失在半路上的技术域，比如在前端领域 Kissy 时代的结束（想想承玉兄当年），再比如 PHP 在阿里工程级研发领域的消亡（看看云谦兄），没办法，时代在进步，坚持很重要，格局很重要，技术的风向标同样重要。

技术跨栈不是口号，靠这四点来践行，我只能说"知易行难"。

---

很高兴看到苏千兄的晋升，我也一时想不出合适的语言来总结这段经历。作为个体，有些方面值得我们学习和反思的。

**第一，规划长远，以修正当下**。很多年前，我对这些漂亮的 PPT 不屑一顾（特别是支付宝的兄弟们的抽象和技术领悟力又特别强），但今年有点读懂他们，事情的执行落地需要组织、需要策略、那个大图就是组织和策略，执行过程迷失途中，用它把偏路掰正。So，我们 6 月初做了一版规划，尽管这个规划过于保守，过于阶段性，但一定要有！而几个子领域里的规划性我们还做的不够，也赖我太懒没顾得上及时 Review。

**第二，情商、智商、技商**。当技术高 P 是某个领域的 Owner，需要拉动一票人一块干一件事时，最好的方式就是体察这些（哪怕是不直接相关）人的诉求，不厌其烦的互动，"给你讲两遍了你怎么还不明白，那我再给你讲一遍！"，"还有哪里不清楚的？是否需要我提供文档？"，"你时间上有什么压力，需不需要我找你的主管帮你减减压？"这些话术"很阿里"，"很政工干部"，但在琐碎事务噪音面前是最简单有效的方式。

**第三，目标设定很重要**

最近在跟敏刚一起设定圣训的 KPI 目标，我相信敏刚会有一些体会。目标具体、可衡量、有策略、适度增强、容易把握住度，对技术同学来说，目标想清楚，路径基本清楚，路径清楚。一线的同学才可能顺杆上爬。这一点支付宝的兄弟们做的非常好（同时也羡慕他们真舍得给技术投资），我表示继续虚心学习。目标设定不仅是 TL 的事情，对于高 P 的技术卡位同样重要。没办法，阿里的风格就是这样。

我想我收获最大的就是这三个"味道"，很"阿里味"。但愿我能像他们一样，把大图落好地，和大家一起共勉。
