# 架构图绘制风格

> 本文件用于“画架构图 / 技术体系图 / 架构演进图 / 中台架构图 / 系统调用链路图”等场景。核心不是复刻某种视觉皮肤，而是保留画图逻辑：先讲清问题、边界、分层、依赖和取舍，再选择合适版式。

---

## 核心原则

架构图不是组件清单。合格的架构图必须回答四个问题：

1. **这张图要证明什么**：演进合理性、分层边界、调用链路、治理机制、生态关系，还是投入产出。
2. **系统边界在哪里**：哪些是自建，哪些是集团/外部能力，哪些是业务域，哪些是平台域。
3. **控制点在哪里**：网关、容器、Bridge、SDK、协议、数据源、发布系统、监控系统等，哪些决定架构成败。
4. **取舍是什么**：要什么、舍什么、风险在哪里，为什么不选择另一条路。

画之前先定图的主线。主线不清楚时，不要直接画组件盒子。

---

## 先选图型

| 图型 | 适用场景 | 画法重点 |
|------|----------|----------|
| 架构演进图 | 讲 1.0 → 2.0 → 3.0 的变化 | 左侧放产品/业务形态证据，右侧放对应架构抽象；每代只突出关键差异 |
| 分层体系图 | 讲端技术中台、平台架构、技术栈 | 自上而下：业务代码 → 适配/容器 → 公共能力 → 框架/SDK → 服务端/网关 → 行业/集团中台 |
| 生态关系图 | 讲自建体系与集团生态如何耦合 | 中间画标准交集和共享层，左右区分自建、集团、外部 App 或其他 BU |
| Before / After 对照图 | 讲升级、改造、迁移收益 | 左边旧结构，右边新结构，中间箭头；灰掉被替换部分，强调新增控制点 |
| 调用链路图 | 讲一次请求、一次发布、一次资源下载如何流动 | 按真实路径画，不为对称补节点；用箭头标出主路径、备用路径和黑白名单 |
| 治理流程图 | 讲发布治理、质量治理、版本管控 | 上半部画原流程问题，下半部或右侧画改造后机制；用红/绿状态点表达治理效果 |
| 工具链全景图 | 讲运行时、构建、发布、资源管理、监控之间关系 | 按生命周期分区：运行时、构建期、发布期、监控期，标出资源和配置流向 |
| 业务漏斗/流量体系图 | 讲用户、流量、转化、沉淀 | 从用户心智或流量来源出发，横向经过转化通道，最后到业务结果和用户沉淀 |
| 成果时间轴图 | 讲阶段成果和技术产品沉淀 | 时间轴承载 Release 节点，节点上放能力或产品，节点下写归属和阶段收益 |

如果一个需求同时命中多种图型，优先选择最能支撑结论的图型。不要把所有信息塞进一张图。

---

## 信息组织

### 1. 用“业务形态 → 技术抽象”组织演进

演进图不要只写版本号。每个阶段至少包含：

- 业务形态：用户端、App、H5、Weex、小程序、外部渠道等。
- 技术形态：Native Only、Hybrid、Container、Mashup、动态模板等。
- 研发规模：10 人、50 人、100 人这类规模变化可作为架构复杂度证据。
- 核心挑战：稳定、性能、研发效率、集团生态复用、业务差异化。

### 2. 用“层”表达稳定关系

分层体系图按稳定程度从上到下：

1. **业务代码 / 业务 Bundle**：变化最快，放最上层。
2. **适配层 / Bridge / Container**：连接业务与平台，是差异化控制点。
3. **公共代码 / UI Common / 工具共享**：沉淀复用能力。
4. **Framework / SDK / Fusion Service / OS**：架构级研发能力。
5. **网关 / 服务端基础设施**：连接端和服务端。
6. **行业技术 / 集团中台 / 外部生态**：更底层或更外部的依赖。

不要为了好看把依赖倒置。变化快的在上，稳定支撑在下。

### 3. 用“虚线框”表达边界

边界比连线重要。常见边界：

- 自建能力 vs 集团能力
- 业务研发 vs 架构研发
- 运行时 vs 构建期 / 发布期
- 端侧能力 vs 服务端能力
- 标准交集 vs 各自实现
- 主链路 vs 备用链路

边界必须命名。不要只画一个没有标题的框。

### 4. 用“右侧关系”补足组织和生态

这类架构图经常不只解释技术，还解释协作关系。可以在右侧放：

- 端研发、架构团队、行业技术研发、服务端团队
- 集团标准、集团 App 容器、自有业务生态、其他阿里系 App
- Scrum 迭代、平台化运作、PMO 治理、发布审核

技术图如果不说明谁负责、谁依赖谁，容易变成静态堆栈。

### 5. 用“底部文字”写取舍和收益

图下方保留 2-4 条说明，结构固定：

- **要**：这次架构选择要获得什么能力。
- **舍**：接受什么短板、依赖或成本。
- **收益**：体验、效率、生态、稳定性、复用上的具体变化。
- **风险**：成熟度、依赖、包大小、监控、运维、组织协同上的风险。

不要写空泛总结。每条都要能对应图中的某个控制点或边界。

## 视觉约定

样式可以按实际输出工具调整，但信息角色要稳定：

| 角色 | 建议表现 |
|------|----------|
| 业务 / Bundle | 紫色块，放在上层或入口侧 |
| 公共能力 / UI / 适配 | 蓝色块 |
| Framework / 基础能力 | 绿色块 |
| 网关 / SDK / 关键控制点 | 橙色或红色块 |
| 外部生态 / 不可控依赖 | 灰色块 |
| 当前重点 / 风险提醒 | 红字或橙红气泡，少量使用 |
| 边界 | 灰色虚线框 |
| 主路径 | 实线箭头 |
| 弱依赖 / 参考 / 对齐 | 虚线箭头 |
| 双向协作 | 双向箭头 |

保持白底、高留白、少装饰。不要使用复杂渐变、3D 图标、云厂商图标堆砌或无意义的彩色连线。

## 常用版式

### 左文右图

适合“讲一个架构方案”。左侧写 2-3 个关键判断，右侧画小而完整的分层图。文字不要复述组件名，要解释为什么这么分。

### 左图右责

适合“体系建设 / 中台建设”。左侧画技术分层，右侧画组织、生态或协作关系。中间用虚线或箭头说明标准交集和共享能力。

### 双图对照

适合“升级前后”。左边旧架构，右边新架构，中间箭头。旧架构中被淘汰或弱化的部分可灰掉，新架构只突出新增控制点。

### 上流程下数据

适合“治理改造”。上半部画流程变化，下半部放饼图、柱状图、指标变化或问题说明，证明治理动作有效。

### 左链路右价值

适合“系统调用链路 / 技术商用价值”。左侧画真实调用链路，右侧写进展、价值和风险。调用链路必须有主路径、备用路径和关键限制。

### 上漏斗下产品

适合“流量体系 / 工具产品化”。上半部画用户分层和流量去向，下半部画产品组合或工具矩阵，再说明每个产品解决哪类不确定性。

## 样板库

样板用于迁移拓扑结构，不用于照搬历史业务名、团队名和产品名。使用时先选最接近的样板，再替换为当前系统的真实组件。

### 样板 1：架构演进三段式

来源：无线架构演进类 PPT。适合讲一个系统从轻客户端、混合架构到平台化/生态化的演进。

```text
画布：横向 3 行，每行表示一代架构

左侧：业务形态证据
  第 1 代：早期产品截图 / 单一入口 / 功能少
  第 2 代：业务功能变多 / H5 或 Hybrid 引入
  第 3 代：多端入口 / 外部渠道 / 业务形态复杂

中间：时代和判断
  Tool/App Age
    Native Only
    研发规模小
  Platform Age
    Hybrid
    研发规模扩大
  Mashup / Container Age
    多技术栈混合
    自建 + 共建 + 外部生态

右侧：架构抽象
  [biz]
  [Native]

  [Hybrid] [biz]
  [Libs / Utils] [Framework]
  [Native]

  [biz bundle] [外部业务模块]
  [Libs / Utils] [外部 SDK]
  [Container / Bridge]
  [Framework / SDK]
  [Gateway]
  [业务系统] [外部生态]

底部说明：
  每一代只写关键变化、主要矛盾和下一代出现的原因。
```

使用要点：
- 不要把版本号当主线，主线是业务复杂度和研发规模逼出架构升级。
- 每代只保留 3-5 个模块，避免演进图变成全量架构图。

### 样板 2：左图右责的中台体系图

来源：端技术中台体系图。适合讲技术中台、平台架构、跨团队协作。

```text
画布：左 65% 技术分层，右 35% 组织/生态关系，底部写收益和取舍

左侧技术分层：
  [业务代码]
    App Bundle | H5 Bundle | Weex/Rx Bundle | Dynamic Bundle

  [容器适配层]
    Adaptor / Hybrid API / Polyfill

  [业务适配器 / Bridge / 标准交集]
    自建 Container
    集团 App 容器实现
    标准交集：协议、API、页面容器、事件通道

  [公共代码 / 基础能力 / 工具共享]
    UI Common | Framework | SDK
    Fusion Service / Libraries / OS

  [服务端支撑]
    服务端基础设施 | 网关层

  [行业技术 / 集团中台]
    行业平台 | 集团能力 | 其他生态

右侧关系：
  端研发
    ↓
  平台/中台架构
    ↓
  架构研发 / Scrum 迭代
    ↓
  行业技术研发

中间连接：
  自建能力 ↔ 集团标准
  基建共享 ↔ 功能级共享
  App 自有生态 ↔ 其他 App / BU

底部说明：
  要：标准一致、能力复用、研发效率
  舍：接受集团技术短期不成熟、一同采坑
  收益：体验一致、技术生态、平台化、业务容器标准
```

使用要点：
- 这张图必须画“谁和谁耦合”，不是只画技术层。
- 右侧责任关系要服务于技术边界，不要变成组织架构图。

### 样板 3：Before / After 改造图

来源：端架构 2.0 → 3.0、值机改造、Native 化改造等页面。适合讲升级、迁移、重构收益。

```text
画布：左旧结构，右新结构，中间粗箭头

左侧旧结构：
  [旧入口 / 旧 SDK / 旧容器]
        ↓
  [旧服务 / 旧通道]
        ↓
  [外部系统]

右侧新结构：
  [多入口 / 多渠道]
    App | H5 | 外部渠道
        ↓
  [新控制点]
    新容器 / 新 Bridge / 新协议 / 新服务
        ↓
  [核心服务]
        ↓
  [外部系统 / 集团能力]

视觉处理：
  旧结构中被替换部分用灰色或浅色弱化
  新增控制点用橙色或红色强调
  关键收益用短标签贴在新控制点旁边

底部说明：
  改造前：成功率、体验、覆盖率、成本问题
  改造后：成功率提升、体验可控、覆盖范围扩大、成本下降
  S2 / 下一步：还没解决的问题
```

使用要点：
- Before/After 不是两张完整架构图并排，而是突出“变化点”。
- 必须说清旧结构为什么不够，新结构靠哪个控制点解决。

### 样板 4：系统调用链路图

来源：直连技术、手机墙、外部系统调用链路类页面。适合讲真实请求路径、兜底路径、黑白名单、代理池。

```text
画布：左侧链路图，右侧价值说明

链路顶部：用户端和渠道占比
  [渠道 A] [渠道 B] [自有 App]
        ↓ 非直连 / 直连请求

链路主体：服务端和控制点
  [业务服务端]
    [核心业务模块 A] [核心业务模块 B]
        ↓
  [调度层 / 代理调度 / 网关]
    [代理池] [普通池] [黑名单/白名单]

侧边能力：
  [手机墙 / 设备池 / 开发板]
    ↔ 真机资源
    ↔ 加密 / 风控 / 调试

链路底部：外部系统
  [PC 通道备份]   [Mobile 通道主力]
        ↓             ↓
      [外部系统 / 铁总 / 第三方]

右侧说明：
  进展：哪些链路已打通，哪些仍在调试
  价值：省资源、提体验、提高成功率
  风险：稳定性、合法合规、容量、互备关系
```

使用要点：
- 真实路径优先，不要为了版面对称补链路。
- 主路径、备用路径、限制条件必须分清。

### 样板 5：治理流程对比图

来源：客户端质量和研发过程治理页。适合讲发布治理、版本治理、质量治理、流程改造。

```text
画布：上半部流程对比，下半部数据证明

左上：治理前流程
  用户产品    O → M2 → M3 → M4 → 发布
  类目产品    O → M2 → M3 → M4 → 发布
  平台产品    O → M2 → M3 → M4 → 发布
  问题标注：流程点较多、PM 流程意识不强、版本成本高

右上：治理后流程
  各战线 Kickoff
      ↓
  迭代归一 / 版本计划
      ↓
  集成灰度 / 发布审核
      ↓
  发布

控制点：
  PMO 提前规划
  需求系统迭代归一
  架构组值班 / 版本审核
  集成 Diff 评估
  发布红线

下半部数据：
  紧急集成占比变化
  包大小水位
  质量问题类型占比
  关键指标用红/绿强调

底部说明：
  成效、仍未解决的问题、下一步治理抓手
```

使用要点：
- 流程图必须有控制点，不是节点串联。
- 数据是用来证明治理有效，不是装饰。

### 样板 6：工具链全景图

来源：容器基建、离线包管理、研发环境等页面。适合讲运行时、构建期、发布期、资源管理、监控联动。

```text
画布：按生命周期横向分区

左侧：运行时 Runtime
  [URL]
    ↓
  [Container Router]
    [URL 解析] [白名单] [短链展开] [预取]
    ↓
  [Render 层]
    小程序 / Weex / Native / WKWebView
    ↓
  [离线缓存]
    命中规则 | 下载通道 | 资源池

中间：离线包加载器 / 配置更新
  [消息监听]
  [更新拉取]
  [本地总控更新]
        ↓ 触发资源更新

右侧：管理平台
  [容器总控]
  [接口服务 / 资源配置]
  [研发环境]
    云构建 | 云打包 | 规范检查

底部：依赖和开放
  [基础服务] [集团依赖] [多资源部署] [商家开放]

连接：
  配置推送 → 加载器
  资源下载 → 缓存池
  发布平台 → 多资源部署
  监控 → 总控管理
```

使用要点：
- 按生命周期分区，比按系统归属分区更容易看懂。
- 每条箭头标注流动对象：配置、资源、事件、监控数据。

### 样板 7：业务漏斗 / 流量体系图

来源：端侧引流工具产品化页。适合讲用户心智、流量通道、工具产品组合、业务结果。

```text
画布：上半部用户和流量漏斗，下半部工具产品矩阵

上半部：
  [老用户 / 确定性心智]
      金刚 + 搜索 → 找货架 → 标品 / GMV

  [新老用户 / 相对确定性心智]
      推荐 + 场景 → 匹配场景 → 内容 / 服务 / 转化

  [新新用户 / 弱心智]
      营销触达 / Landing → 注意力占领 → IPVUV → 用户沉淀

  横向阶段：
    用户运营/拉新 → 流量转化+种草 → 流量沉淀+收割 → 用户沉淀

下半部：
  [工具 A] 外部流量引导
  [工具 B] 内部投放管理
  两个圆或两个框重叠，表示共同解决不确定性流量

右侧说明：
  三类流量通道的定义
  两个工具产品分别解决什么问题
  S1/S2 进展和数据
```

使用要点：
- 先按用户心智分层，再放工具；不要先介绍工具。
- 工具价值要对应“不确定性如何变成确定性”。

### 样板 8：成果时间轴图

来源：端技术中台挑战和收获页。适合讲一个周期内技术产品和能力沉淀。

```text
画布：上半部 3-4 条关键判断，下半部时间轴

上半部：
  1. 工程研发效率保障
  2. 集团体系打通
  3. 自建体系和创新

下半部时间轴：
  ─────────────────────────→
  2019 FY.Q2          双十一前          双十一后          S1 Release

  节点 1：
    [圆形能力块]
    能力名称
    收获：解决什么问题
    归属：自建 / 集团打通 / 业务创新

  节点 2：
    [圆形能力块]
    ...

底部说明：
  从单点能力到体系能力的变化
  哪些能力已商用，哪些只是试探
```

使用要点：
- 时间轴节点要有“能力 + 收获 + 归属”，不能只是项目名。
- 用颜色区分自建、集团复用、业务创新。

## 输出流程

1. **确认目标**：用户要的是解释现状、设计未来、说服决策、复盘演进，还是沉淀技术体系。
2. **选择图型和样板**：从上面的图型中选一个主图型，并从样板库中选最接近的拓扑；必要时拆成多张图。
3. **列组件清单**：只列真实存在或用户明确假设的组件；缺失时询问或标注假设。
4. **找控制点**：识别网关、容器、协议、SDK、数据源、发布、监控、标准交集等关键点。
5. **画边界**：先画边界，再放组件，再连线。
6. **补取舍**：图下写要、舍、收益、风险。
7. **检查可读性**：一眼能看出主线；三眼能看出边界；读完说明能理解为什么这样设计。

---

## 反模式

- **组件堆叠**：只有一堆盒子，没有边界、控制点和取舍。
- **网状连线**：所有组件互相连，看起来复杂但没有主路径。
- **云厂商图标化**：图标很多，但技术判断很少。
- **为了对称编造层级**：实际没有的层被硬补出来。
- **只画技术不画组织**：跨团队/中台/生态场景缺少责任和依赖。
- **只讲收益不讲舍**：看不出架构选择的代价。
- **一张图塞所有内容**：演进、调用链、治理、收益混在一起，谁也讲不清。

## 生成格式建议

根据用户要求选择输出格式：

- **Mermaid**：适合快速表达关系，但不适合精细还原版式。
- **Excalidraw / SVG / HTML**：适合保留分区、颜色、留白和对照布局。
- **PPT 绘制说明**：适合用户要手工做 Keynote/PPT。
- **Markdown + 图形代码**：适合需要同时解释逻辑和给出可编辑图稿。

无论格式如何，最终输出都必须包含：图、关键图例、取舍说明。
