# 自愈策略执行手册

## 🔴 环境隔离红线（执行前必检）

**所有自愈策略执行前必须先确认目标记录的 `env` 字段。**

| 环境 | 允许操作 | 禁止操作 |
|---|---|---|
| **env=staging（预发）** | S1 重试、S2 重启、S3 审核推送、S4 队列调配建议、S5 阶段补偿、数据修复、状态推进 | — |
| **env=production（生产）** | 查询、监控、告警通知、诊断报告 | **一切写操作**：重试/重启/状态变更/审核任务操作/数据修复 |
| **env 未知 / 无 env 字段** | 同 production 处理（保守策略） | 同 production |

### 执行流程

```
收到判定信封 → 检查 env →
  if env == staging → 按 recommendedAction 执行自愈
  if env == production → 跳过自愈，仅发告警通知 + 标记"需人工处理"
  if env 未知 → 同 production 处理
```

### 判定信封中的 env 字段

```json
{
  "verdict": "P0_CRITICAL",
  "ruleHit": "R001",
  "env": "staging | production | unknown",
  "selfHealable": true,
  "recommendedAction": "S1_RETRY",
  ...
}
```

**`selfHealable` 的最终判定必须叠加 env 检查：**
```
实际可自愈 = selfHealable == true AND env == "staging"
```

### SQL 查询强制 env 过滤

所有巡检 SQL 必须包含 `env` 过滤条件，防止跨环境数据混淆：
```sql
WHERE ... AND env = 'staging'   -- 预发巡检
WHERE ... AND env = 'production' -- 生产监控（只读）
```

## S1: 429 智能重试

**触发条件**: R004 告警 — LLM 429 Quota 耗尽

**执行步骤**:
1. 统计当前 429 错误的数量和分布节点
2. 确认是否为全局性 quota 耗尽（多策略、多节点同时出现）还是单策略触发
3. 如果偶发（<10 条）：
   - 等待 60 秒后，通过 `taobao-cloth-afd-mcp` 的 `retryWorkflowRecord` 重试失败记录
   - 重试间隔采用指数退避：60s → 120s → 240s
4. 如果批量（>10 条）：
   - 先暂停重试，通知用户确认 quota 恢复情况
   - 检查是否有其他批次在抢占 quota
5. 重试后验证：重新查询这些记录的状态是否变为 SUCCESS

**MCP 工具**:
```
retryWorkflowRecord(recordId)  — 单条重试
```

**注意事项**:
- 不要连续重试超过 3 次，避免加剧 quota 消耗
- 如果连续 3 次仍 429，升级告警级别并通知用户人工介入

## S2: 停滞任务重启

**触发条件**: R003 告警 — HANDLING 停滞超过 30 分钟

**执行步骤**:
1. 查询停滞记录列表（按停滞时间排序）
2. 对每条停滞记录：
   - 检查停滞时间：30-60 分钟 → 标记 WARNING，继续观察
   - 60 分钟以上 → 执行重启
3. 重启方式：调用 `retryWorkflowRecord` 重新触发处理
4. 重启后 5 分钟内验证状态是否从 HANDLING 变为 SUCCESS/FAIL

**MCP 工具**:
```
retryWorkflowRecord(recordId)  — 重新触发处理
```

**注意事项**:
- 同一记录重启超过 2 次仍停滞，停止重试并通知用户
- 可能是底层服务故障，非重试能解决

## S3: 审核推送提醒

**触发条件**: R005 告警 — 审核等待超过 2 小时

**执行步骤**:
1. 查询待审核记录，确认审核状态
2. 如果等待 2-6 小时：
   - 通过 QoderWork IM 发送审核提醒，包含批次信息和待审核数量
3. 如果等待超过 6 小时：
   - 升级为 WARNING 级别
   - 发送包含紧急标记的提醒
4. 如果等待超过 18 小时（参考 BT_5621 案例）：
   - 升级为 CRITICAL
   - 明确标注"审核延迟已阻塞后续阶段"

**通知内容模板**:
```
【审核提醒】批次 {batch_id} 有 {cnt} 条素材待审核，
已等待 {hours} 小时。请及时处理以避免阻塞后续阶段。
```

## S4: 队列积压智能调配

**触发条件**: D4 维度告警 — 队列积压

**执行步骤**:
1. 统计各节点的 HANDLING 队列长度
2. 识别积压最严重的节点
3. 分析积压原因：
   - 如果是上游产出过快（短时间内大量 SUCCESS → 下一阶段 HANDLING 激增）：
     建议限流，降低提交速率
   - 如果是下游处理能力不足（HANDLING 长时间不消化）：
     检查是否有节点异常，考虑扩容或分流
4. 目前 F88 平台不支持动态调整并发数，此策略主要为诊断和建议

**注意事项**:
- 此策略为分析型，不自动执行修复操作
- 输出诊断报告供用户决策

## S5: 阶段补偿触发

**触发条件**: R002 告警 — 阶段未触发

**执行步骤**:
1. 确认缺失的阶段（对比链路配置 vs 实际执行的 strategy_id）
2. 检查缺失原因：
   - 如果前一阶段的输出参数异常（如 passedImg = [null, null]）：
     报告参数丢失问题，需要人工修复数据后重新触发
   - 如果前一阶段尚未完成（仍有大量 HANDLING）：
     等待前一阶段完成，非异常
   - 如果链路配置中该阶段的策略 ID 不存在或已禁用：
     报告配置问题
3. 如果确认是暂时性问题且前序阶段已完成：
   - 通知用户手动触发缺失阶段
   - 提供缺失阶段的 strategy_id 和建议操作

**注意事项**:
- 阶段补偿涉及数据一致性，不建议全自动执行
- 必须通知用户确认后操作
- 参考案例：BT_5621 的 approve 输出参数丢失导致套图阶段未触发

## 通用执行原则

1. **安全第一**: 涉及数据修改的操作（重试、重启）必须通知用户确认，除非用户明确授权自动执行
2. **幂等性**: 重试操作应确认记录当前状态仍为 FAIL/HANDLING，避免重复处理已恢复的记录
3. **升级机制**: 任何自愈策略连续执行 3 次未成功，自动升级为 P0 告警通知用户
4. **日志记录**: 所有自愈操作记录执行时间、目标记录 ID、执行结果，便于事后审计
