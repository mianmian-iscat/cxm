# QA 测试自愈执行准则

本 skill 是测试会话的基础层准则，不接管任何具体测试流程，但所有测试流程 skill 在执行过程中必须遵守本 skill 定义的规则。当遇到"造数失败/验证走不通/SKIP/BLOCKED/用例执行顺序混乱/执行不完整/下游阶段未触发/链路未完整执行"时，自动激活以下闭环：

```
异常发生 → 根因调查(先查原因→尝试修复→修复失败才降级)  ← 最高优先级，不可跳过
     ↓
造数失败 → 七步诊断(依赖分解→环境探查→路径排序→分层执行→后置验证→知识沉淀→降级BLOCKED)
     ↓
验证走不通 → 三层降级(换观测源→换数据来源→换验证维度)
     ↓
SKIP/BLOCKED前 → 缺失分析(缺什么/在哪缺/能否补 → 能补直接补)
     ↓
链式依赖 → DAG拓扑序执行(前置产出→后置消费, 前置FAIL下游整串SKIP)
     ↓
仍失败 → bug草稿 → 修复后回补那批FAIL → 更新报告
```

---

## 规则零：根因调查优先于一切降级（最高优先级，不可跳过）

遇到任何工具/环境/数据异常时，**禁止直接降级或 SKIP**，必须先走完根因调查和修复尝试：

1. **查原因**：读错误日志/报错信息，定位具体失败原因（初始化失败？超时？依赖缺失？进程异常？网络不通？配置错误？）
2. **尝试修复**：根据根因采取对应修复手段（重试、重装依赖、重启进程、刷新配置、换 endpoint、检查网络等）
3. **修复失败才降级**：确认无法修复后，才进入后续的七步诊断/三层降级/缺失分析流程
4. **降级须记录根因**：降级报告中必须写明 `根因=xxx，修复尝试=xxx，失败原因=xxx`

**典型反例**：
- 浏览器不可用 → 直接降级到 API 测试 ❌（没查为什么不可用）
- 浏览器不可用 → 检查 Chrome 进程/初始化日志/依赖 → 尝试重启/重装 → 修复失败 → 降级到 API ✅
- db-query-tool 报缺 pymysql → 直接转浏览器查页面 ❌
- db-query-tool 报缺 pymysql → pip install → 验证 import → 继续用 ✅

**核心原则：先查原因再降级，能自愈就自愈，不能自愈才走后续流程。**

## 规则零b：预发验证先造数（红线，不可跳过）

**任何预发环境验证场景，执行前必须先确认测试数据新鲜度。禁止直接复用历史存量数据。**

此规则适用于所有验证路径——hfz-test-workflow 闭环、harness-runner、手动验证子任务、IM 对话中的临时验证，无一例外。

### 为什么需要这条规则

存量数据状态不可控：可能已被其他流程消费、字段被修改、关联数据已过期、或状态已流转。用这样的数据跑出的验证结果不可信——PASS 不代表功能正确，FAIL 不代表有 Bug。

### 什么是"存量数据"（禁止使用）

以下情况均视为存量数据，**禁止直接用于验证**：

- 上一轮会话或昨天创建的数据
- 别人创建的数据（无法确认是否被修改过）
- 当前会话早期创建但已被其他用例消费/修改过的数据
- 从页面/DB 中"找到的"已有数据，无法确认创建时间和来源

### 铁律：页面测试 = 必须先造数

**只要是在页面上执行测试/验证，就必须先调用造数 skill 创建新数据，没有任何例外。**

不需要分析"现有数据能不能用"、不需要检查"数据是否还新鲜"、不需要判断"这个场景是否需要新数据"——**直接调造数 skill，造完再用。**

- 打开页面看到已有数据 → 不用，调造数 skill 造新的
- 页面上"新建"按钮不响应 → 降级到 API 造数，不用页面上看到的旧数据
- 觉得"这个存量数据看起来能用" → 不行，必须造新的
- 子任务/IM 对话中验证需求 → 先造数，再验证

### 造数 Skill 路由（直接调用，不需要分析）

| 需要造的数据类型 | 调用 Skill |
|----------------|-----------|
| 审核任务（首图/套图/视频） | `审核数据构造` 或 `f88-strategy-test-run`（策略试运行） |
| 审核任务（手动 API 创建） | `f88-review-task-create` |
| 模板包 | `f88-template-package-create` |
| 原创保护快审/初审 | `yc-quick-audit-data-create` |
| 原创保护状态/时间修改 | `yc-data-factory` |
| 其他/不确定 | 按规则一七步诊断的依赖分解确定造什么 |

### 典型反例

- 验证"抽检逻辑优化" → 打开审核页面找几条已有任务就开始验证 ❌
- 验证"抽检逻辑优化" → 调用 `f88-strategy-test-run` 触发新批次 → 用新数据验证 ✅
- "新建任务"按钮不响应 → 转去查 Switch/用页面上看到的旧任务 ❌
- "新建任务"按钮不响应 → 降级到 API 造数 → 用新造的数据验证 ✅

**核心原则：页面测试必须先造数。不造不测，没有例外。**

### 已知不可自愈错误速查表（禁止被动重试）

以下错误属于**进程/系统级故障**，在同一 session 内重试永远不会恢复。识别到这些错误后，**禁止"再试一次看看"**，必须立即执行对应处置：

| 错误特征 | 根因 | 正确处置 | 禁止行为 |
|----------|------|----------|----------|
| `spawn EBADF` / `EBADF` / `bad file descriptor` | QoderWork 进程文件描述符耗尽 | **立即告知用户**："Shell 环境 EBADF，需重启 QoderWork 恢复"，停止当前任务 | ❌ 在同一 session 反复重试 Bash 命令 |
| `ENOMEM` / `Cannot allocate memory` | 系统内存不足 | 告知用户关闭其他应用或重启，记录当前进度供恢复后续跑 | ❌ 循环重试等待内存释放 |
| `ENOSPC` / `No space left on device` | 磁盘满 | 告知用户清理磁盘，给出 `df -h` 建议 | ❌ 继续写文件操作 |
| `ECONNREFUSED` 持续（>3次同一端口） | 目标服务宕机 | 告知用户服务不可用，记录待恢复后重试的任务 | ❌ 无限重试同一 endpoint |

**处置模板**（遇到上述错误时输出）：
```
⚠️ 环境故障：{错误特征}
根因：{根因说明}
处置：需要 {用户操作}（如重启 QoderWork / 清理磁盘 / 重启服务）
当前进度：{已完成步骤}，恢复后可从 {断点} 继续
```

## 规则零d：造数与验证数据必须一致（ID 链可追溯，硬拦截）

**同一条用例，结果验证的数据必须与前置造数创建的数据完全匹配。禁止用 A 批次造数、用 B 批次验证。**

### 硬规则

1. **ID 链必须可追溯**：造数阶段产出的批次号/任务 ID/商品 ID 必须记录在 exec-log 中，后续所有验证步骤必须使用这些 ID 进行查询。验证 SQL/页面查询的条件必须能追溯到造数产出。
2. **禁止数据替换**：验证时发现造的数据"找不到/状态不对"，**不允许从 DB 搜索其他数据替代**。正确做法是按规则零（根因调查）→ 规则一/二（自愈）排查为什么造的数据找不到，而不是换一份数据来"证明"用例通过。
3. **批次/任务 ID 一致性校验**：CP2 审计时，对比 exec-log 中记录的造数批次号与验证查询使用的批次号。不一致 → 直接 FAIL。
4. **与规则零b 的关系**：规则零b 要求"必须先造数"，本规则进一步要求"造的和验的必须是同一份"。两条规则共同确保数据新鲜度和数据一致性的双重保障。

### 典型反例

- 造数触发 BT_7817 → 验证时发现 BT_7817 洗脑/审核未触发 → 从 DB 搜索到 BT_7819 → 用 BT_7819 验证 ❌（数据替换，验证的不是自己造的数据）
- 造数触发 BT_7817 → BT_7817 部分阶段未执行 → 调查原因并在 BT_7817 上继续推进 → 用 BT_7817 验证 ✅（同一份数据，ID 链完整）

## 规则零c：BLOCKED 必须先走自愈诊断（硬拦截，不可跳过）

**任何用例在标记为 BLOCKED 或 SKIP 之前，必须先完成本 skill 的自愈诊断流程，并产出诊断记录。禁止看到错误就直接标记 BLOCKED。**

此规则是对规则零（根因调查）和规则一/二（七步诊断/三层降级）的执行保障。没有诊断记录的 BLOCKED 视为无效标记，必须打回重做。

### 硬规则

1. **看到错误 → 先诊断，不是先标记**：遇到任何异常（404、超时、连接拒绝、页面白屏、接口报错等），必须先执行规则零（根因调查→尝试修复），修复失败后才进入规则一/二的诊断流程。
2. **诊断必须留痕**：每条 BLOCKED/SKIP 用例必须附带「自愈诊断记录」，包含：
   - `触发了哪条规则`：规则零（根因调查）/ 规则一（七步诊断）/ 规则二（三层降级）/ 规则三（缺失分析）
   - `诊断步骤摘要`：每一步做了什么、结论是什么
   - `已试路径`：具体尝试了哪些修复/降级手段，每条的结果
   - `BLOCKED 子分类`：BLOCKED_DATA / BLOCKED_ENV / BLOCKED_DEP / BLOCKED_LOGIC（见规则一步骤 7）
3. **无诊断记录 = 无效 BLOCKED**：报告中出现没有自愈诊断记录的 BLOCKED/SKIP，视为执行不合格，必须回退补做诊断。
4. **禁止问用户"要不要我去做"**：遇到阻塞时，**判断清楚就直接执行，不再问"要不要我去验证/修复/尝试"**。验证是义务不是选项，直接去验证，不要问。仅在红线约束（数据红线冲突/红线外 HSF 调用/生产环境写操作）时才需确认。此规则优先级高于一切其他规则——即使 agent 认为"可能有风险"，只要不在红线范围内，就必须自主执行。

### 典型反例（Case 13 事故）

- sandbox 返回 404 → 直接标记 BLOCKED("sandbox 不可用") ❌
  - 没查：sandbox 能否重启？是否有其他 sandbox 实例？URL 是否过期？能否用本地 Chrome 替代？
- sandbox 返回 404 → 规则零根因调查（检查 sandbox 进程/日志/配置）→ 尝试重启/换实例 → 修复失败 → 规则一七步诊断 → 规则二三层降级 → 全部失败 → 标记 BLOCKED_ENV + 附诊断记录 ✅
- BLOCKED 原因是"需要实际创建任务后才能验证重名" → 停下来问用户"要不要现在去验证一下这个场景？" ❌
  - 正确做法：用已有任务名尝试新建 → 观察系统是否弹出重名提示 → 整个过程不会真正创建新任务 → 直接执行，不问

### 适用范围

此规则覆盖所有测试执行路径：hfz-test-workflow 闭环、harness-runner、原创保护测试编排、手动验证子任务、IM 对话中的临时验证。不论使用哪种编排器或执行入口，BLOCKED 前必须走自愈诊断，没有例外。

## 规则零e：Critical Reminder（长会话关键约束自提醒，硬拦截）

**长会话中 Agent 会随上下文增长"遗忘"早期加载的硬约束。本规则定义强制自提醒的触发点和内容，确保关键红线在整个测试生命周期内不失效。**

此规则是上下文工程（Context Engineering）中"Reminder 机制"的落地。SKILL.md L1 常驻内核 + references L2 按需加载解决了"装得下"的问题，本规则解决"记得住"的问题——在约束容易被遗忘的高风险时刻，强制 Agent 重新加载并校验关键规则。

### 硬规则

1. **触发点必须自提醒**：下方表格列出的每个触发点出现时，Agent 必须在执行对应动作前，主动回顾提醒内容表中列出的约束。不回顾 = 违规，即使实际执行结果正确，CP 审计也标记为流程不合规。
2. **回顾 = 显式输出**：自提醒不能是"心里想了一下"。Agent 必须在 exec-log 或对话中输出至少一行回顾声明（如"⚡ 自提醒：群消息白名单 — 仅允许'收到提测消息'和最终结果，当前消息不匹配 → 走 IM 私聊"），作为审计证据。
3. **cron 子任务同样适用**：cron payload 中已内联的约束提醒不替代本规则。子任务执行到触发点时，仍需按本规则执行自提醒流程。

### 触发点与提醒内容

| # | 触发点 | 必须回顾的约束 | 违反后果 |
|---|--------|--------------|---------|
| R1 | 准备向钉钉群发送任何消息前 | 群消息白名单：仅允许 `收到提测消息` 和 `@韩非子 测试完成：...` 两条；其余一律走 IM 私聊 | 群消息事故（2026-08-06/08-10 事故重演） |
| R2 | 准备执行任何 DB 查询前 | DB 路由：`f88_*` 表 → scenario 库(dbId=975919)；`g_afd_*`/`g_workflow_*` 表 → stylespot 库(dbId=5335708)；按表名前缀判断，禁止自行推理选库 | 查错库 → 数据不存在 → 误判 FAIL |
| R3 | 准备创建测试数据（造数）前 | 规则零b（必须先造数）+ 规则零d（造验一致）+ SQL 必须 `env='staging'` + 非 staging seller_id 须暂停确认 | 数据污染 / 生产写操作事故 |
| R4 | 准备标记用例为 BLOCKED/SKIP 前 | 规则零c（必须先走自愈诊断）+ 规则零（先查知识库再推理）+ 诊断必须留痕 | 无效 BLOCKED / 漏检真实 Bug |
| R5 | 阶段转换时（每完成一个 Step / 每 20 次工具调用） | 当前 Step 的群消息权限 + 下一步的前置约束 + 是否有未完成的 CP 门禁 | 阶段遗漏 / 门禁跳过 |
| R6 | 遇到异常/报错需要排查时 | 通用排查原则：先查对应业务域知识库（F88→`references/features/`+`references/infra/`；原创保护→对应域知识库），命中按知识库执行，未命中才自行推理 | 凭经验下错结论 / 重复踩坑 |

### 自提醒输出模板

Agent 在每个触发点执行前，输出以下格式之一（可简写，但必须包含约束名称和判断结论）：

```
⚡ 自提醒[R{N}]：{约束名称}
当前动作：{即将执行的操作}
校验结果：{通过/不通过 → 调整方案}
```

示例：
```
⚡ 自提醒[R1]：群消息白名单
当前动作：向需求交付群发送"Step 3 用例生成完毕"
校验结果：不匹配白名单两条 → 改为 IM 私聊向用户汇报
```

### 典型反例

- 长会话执行到 Step 5，Agent 向群发送"正在执行第 15 条用例..." → ❌ 未触发 R1 自提醒，群消息刷屏
- 查 `g_afd_material_prod_record` 时用了 scenario 库 → ❌ 未触发 R2 自提醒，查错库导致"数据不存在"误判
- 造数前没回顾规则零d，验证时用了不同批次的数据 → ❌ 未触发 R3 自提醒，数据一致性违规
- 遇到报错直接标 BLOCKED，没先查知识库 → ❌ 未触发 R4 自提醒，违反规则零c

### 与其他规则的关系

## 规则零f：State Offload（长流程中间状态卸载，硬拦截）

**长流程中 Agent 对话上下文会持续膨胀，后期 token 消耗剧增、关键信息被淹没。本规则要求将中间状态卸载到文件，后续阶段从文件读取而非从对话历史回溯。**

此规则是上下文工程中"Offload 机制"的落地。规则零e（Reminder）解决"记得住"，规则零f 解决"装得下"——把已完成的阶段成果从对话上下文中释放，只保留结构化摘要。

### 硬规则

1. **每完成一个 Stage/Step/Phase，必须将关键状态写入 `execution_state.json`**：文件路径为 `outputs/{taskId}/execution_state.json`（与 plan.json 同目录）。不写 = 违规。
2. **后续阶段引用文件而非对话历史**：需要回溯前序阶段结果时，从 execution_state.json 读取，不在对话中翻找原始输出。
3. **cron 子任务同样适用**：子任务完成后将状态写入文件，主 Agent 从文件读取。

### execution_state.json 格式

```json
{
  "taskId": "20260812-a1b2-85166197",
  "lastUpdated": "ISO-8601",
  "currentStage": "Stage 5",
  "completedStages": [
    {
      "stage": "Stage 3 用例生成",
      "completedAt": "ISO-8601",
      "summary": "生成用例 15 条（P0:3, P1:5, P2:5, P3:2）",
      "keyArtifacts": ["cases.json"],
      "metrics": {"total": 15, "p0": 3, "p1": 5, "p2": 5, "p3": 2}
    },
    {
      "stage": "Stage 4 造数",
      "completedAt": "ISO-8601",
      "summary": "造数 5 批次，成功 5 批次",
      "keyArtifacts": ["batch_ids: BT_7817, BT_7818"],
      "metrics": {"created": 5, "success": 5, "failed": 0}
    }
  ],
  "dataRegistry": {
    "batchIds": ["BT_7817", "BT_7818"],
    "sellerId": "2219635649153",
    "templatePkg": "pkg_xxx",
    "reviewTask": "RT_xxx"
  },
  "resultSummary": {
    "total": 15, "passed": 12, "failed": 1, "blocked": 2, "skip": 0
  },
  "criticalDecisions": [
    "E2E-09/12/14 标 ASSUMPTION 降 P3（PRD 未提及'使用模板'功能）"
  ],
  "openIssues": [
    "E2E-07 造数失败，BT_7818 卡在 approve 节点"
  ]

```

### 写入时机

| 触发点 | 写入内容 |
|--------|---------|
| 用例生成完成后 | 用例数/优先级分布/关键假设/cases.json 路径 |
| 造数完成后 | 批次 ID/商品 ID/模板包/造数路径/后置验证结论 |
| 执行完成后 | 通过/失败/阻塞数/关键失败原因/截图路径 |
| 自愈完成后 | 自愈成功数/仍失败数/最终状态/修复路径 |
| 报告生成后 | 报告路径/钉钉文档链接/上报状态 |

### 与 Compression 的关系

- Compression（phase-summary.json）是**上下文层面**的压缩，释放 token 空间
- State Offload（execution_state.json）是**数据层面**的卸载，确保关键状态可追溯
- 两者互补：Compression 让 Agent "忘记"细节，State Offload 让 Agent 随时"回忆"关键数据
- 编排器中 Compression 触发时，同步更新 execution_state.json

### 典型反例

- 长流程执行到 Stage 7，Agent 需要知道 Stage 3 的批次 ID → 翻对话历史找了 20 轮 → ❌ 浪费 token 且可能找错
- 长流程执行到 Stage 7，Agent 读取 execution_state.json → 立即获取 batchIds → ✅ 高效准确

## 规则零g：Stage Quality Signal（阶段质量信号，快飞轮实时检查）

**每个 Stage 完成后立即产出质量信号，低于阈值时自动触发重做或补强，不等最终报告才发现问题。**

此规则是"快飞轮"（Fast Flywheel）的落地。课程核心观点：问题越早发现，修复成本越低。等到最终报告才发现用例质量差 = 白跑了整个流程。

### 硬规则

1. **Stage 完成后必须计算质量信号**：每个关键 Stage 完成后，立即计算下方定义的质量指标，与阈值对比。
2. **低于阈值必须触发补强**：补强动作可以是重做该 Stage、追加用例、补充知识加载等，不能忽略信号继续推进。
3. **质量信号写入 execution_state.json**：在 completedStages 的 metrics 中记录。

### 质量信号定义与阈值

| Stage | 信号 | 计算方式 | 基准值 | 警戒线 | 低于警戒线时动作 |
|-------|------|---------|--------|--------|----------------|
| 用例生成 | 用例密度 | 用例数 / (PRD 字数 / 100) | ≥ 2.5 条/百字 | < 1.5 | 重新分析 PRD，补充遗漏功能点 |
| 用例生成 | PRD 覆盖度 | 已覆盖功能点数 / PRD 总功能点数 | ≥ 85% | < 70% | 逐功能点检查遗漏原因，补充用例 |
| 用例生成 | 假设率 | 标【ASSUMPTION】的用例占比 | ≤ 15% | > 30% | 逐条验证假设，不满足则降 P3 或移除 |
| 造数 | 造数成功率 | 成功批次 / 总批次 | ≥ 90% | < 70% | 分析失败原因，走自愈诊断后重试 |
| 执行 | 通过率 | PASS / 总用例 | 视需求而定 | < 50% | 先做失败聚类分析，区分环境问题 vs 真实 Bug |
| 执行 | 自愈成功率 | 自愈成功 / 总自愈尝试 | ≥ 60% | < 30% | 检查自愈路径是否过时，更新知识库 |
| 对抗验证 | 审计通过率 | 对抗验证 PASS / 总审计 | ≥ 95% | < 80% | 暂停执行，检查是否存在系统性造假/偷懒 |

### 质量信号输出模板

```
📊 质量信号 [{Stage}]：
- {信号名}: {值} (基准: {基准值}, 警戒线: {警戒线})
- 状态: ✅ 达标 / ⚠️ 警戒 / ❌ 低于警戒线
- 动作: 继续推进 / 触发{补强动作}
```

### 与其他机制的关系

- 质量信号与 CP0-CP4 门禁互补：CP 门禁是"通过/不通过"的硬检查，质量信号是"好不好"的软度量
- 质量信号写入 execution_state.json，供 qa-trace-reflection 慢飞轮聚合分析
- 警戒线触发时的补强动作记入 exec-log，作为过程审计证据

## 规则零h：智能用例优先级动态调整

**根据历史执行数据动态调整用例执行顺序，高频失败用例优先执行，确保早期暴露风险。**

此规则是"AI 质量保障新范式"的落地之一。传统固定顺序执行的问题：高优先用例总是最后才跑到，发现问题时已浪费大量时间。

### 硬规则

1. **执行顺序不固定**：每次执行前，根据下方优先级评分公式重新排序用例。
2. **高频失败用例置顶**：近 5 次执行中失败 ≥ 3 次的用例，自动提升到 P0 执行。
3. **优先级来源可追溯**：每条用例的最终优先级必须记录在 exec-log 中。
4. **冷启动不跳过排序**：即使无历史数据，仍按 basePriority + 模块热区排序，不允许回退到原始顺序。

### 优先级评分公式（三层权重叠加）

```
finalPriority = basePriority × historyWeight × recencyWeight × sessionWeight

basePriority:    PRD/用例定义中的原始优先级（P0=4, P1=3, P2=2, P3=1）

historyWeight:   三级匹配，取最高命中值（解决冷启动）
  Level 1 精确匹配: 同 caseTitle 近 5 次失败次数 / 5 + 0.5
  Level 2 关键词模糊匹配: 从 groupPath 提取核心关键词（2-4字中文），匹配历史 groupPath 中包含该关键词的用例
    匹配算法: 按 " - " "/" 分段 → 提取中文关键词 → 过滤停用词(验证/功能/测试等) → 取命中最多历史用例的关键词
    评分: 匹配到的用例近 5 次失败次数 / 5 + 0.5（Level 1 无数据时降级）
  Level 3 全局热区: 匹配到的历史用例中 FAIL 率 > 40% → 1.3，否则 1.0（Level 1/2 均无数据时降级）
  无历史数据: 0.5（最低权重，不惩罚也不奖励）

recencyWeight:   最近 1 次执行结果
  Level 1 精确匹配: 同 caseTitle 最近结果（FAIL=1.3, PASS=0.8, 未执行=1.0）
  Level 2 关键词模糊匹配: 匹配到的历史用例中最近 1 条结果（FAIL=1.2, PASS=0.9, 未执行=1.0）（Level 1 无数据时降级）
  无历史数据: 1.0

sessionWeight:   当前 session 内实时学习（自愈重试后立即生效）
  同 session 内该用例已执行过且 FAIL → 1.4（自愈重试后优先重跑）
  同 session 内该用例已执行过且 PASS → 0.9（已验证通过，降低优先级）
  未在当前 session 执行过 → 1.0
```

### 冷启动三级降级策略

```
新用例（无精确历史）
  ├─ groupPath 关键词能在历史中匹配到？ → Level 2 关键词模糊匹配
  │   例: "前端验证 - 异常状态" → 关键词"前端" → 匹配历史中 groupPath 含"前端"的用例
  │   ├─ 匹配到的用例近 5 次有 FAIL → historyWeight = failCount/5 + 0.5
  │   └─ 匹配到的用例历史 FAIL 率 > 40% → historyWeight = 1.3（热区标记）
  ├─ 关键词也匹配不到？ → historyWeight = 0.5（中性，不惩罚）
  └─ 当前 session 已执行过？ → sessionWeight 覆盖（实时学习生效）
```

### 数据来源

| 数据源 | 匹配粒度 | 用途 | 路径 |
|--------|---------|------|------|
| att-tf cases.json | Level 1: caseTitle 精确 | historyWeight / recencyWeight | `~/.att-tf/cases/{sessionId}/cases.json` |
| att-tf cases.json | Level 2: groupPath 关键词模糊 | historyWeight / recencyWeight 降级 | 同上，提取关键词后子串匹配 |
| att-tf 全局统计 | Level 3: 匹配用例 FAIL 率 | 全局热区标记 | `~/.att-tf/cases/*/cases.json` 聚合 |
| 当前 session exec-log | sessionWeight | 实时学习 | 当前任务的 exec-log.json |

### 执行顺序策略

| 场景 | 策略 | 说明 |
|------|------|------|
| 冒烟测试 | 按 finalPriority 降序，P0 先执行 | 快速暴露高风险 |
| 回归测试 | 先执行变更影响范围内的用例，再按 finalPriority | 变更关联优先 |
| 全量测试 | 按模块分组，组内按 finalPriority 降序 | 兼顾覆盖与效率 |
| 自愈重试后 | sessionWeight=1.4 的用例优先重跑 | 实时学习，FAIL 用例不等下次 session |

### 与其他机制的关系

- 与 Hybrid 路由互补：Hybrid 决定用哪种执行模式，本规则决定该模式下的执行顺序
- 与快飞轮协同：高频失败用例优先执行 → 更早触发质量信号 → 更早启动补强
- 与 learned-solutions.jsonl 互补：失败模式被 learned-solutions 记录后，下次执行时自愈路径优先匹配
- 与规则零j 协同：执行后 FAIL 的用例通过 sessionWeight 优先重跑，重跑仍 FAIL 则进入根因分类

## 规则零i：回归范围智能裁剪

**根据代码变更范围自动裁剪回归测试集，只执行受影响区域的用例，避免全量回归浪费时间。**

此规则是"智能回归裁剪"的落地。核心洞察：一次 CR 改了审核模块，不需要重测种草素材。

### 硬规则

1. **变更范围必须明确**：裁剪前必须确定本次变更涉及哪些模块/功能点。
2. **裁剪比例必须记录**：裁剪前后的用例数、裁剪率记入 exec-log。
3. **裁剪不裁安全网**：核心冒烟用例（P0）无论是否受影响都必须执行。

### 裁剪决策矩阵

| 变更类型 | 影响范围判定 | 回归策略 |
|---------|------------|---------|
| 单模块代码变更 | 变更文件所属模块 | 该模块全量 + 上下游关联模块 P0/P1 |
| 跨模块公共组件变更 | 所有依赖该组件的模块 | 所有关联模块 P0 + 直接关联模块全量 |
| 配置变更（Diamond/Switch） | 配置项关联的功能点 | 关联功能点全量 + 上下游 P0 |
| DB 表结构变更 | 使用该表的所有模块 | 所有相关模块全量 |
| 前端 UI 变更 | 变更页面对应的用例 | 该页面用例全量 + 关联 API P0 |

### 裁剪执行流程

```
1. 获取变更范围（CR 文件列表 / 配置变更项 / DB DDL）
2. 映射到功能模块：
   a. 从 cases.json 的 groupPath 提取功能标签（按 " - "/" 分段 → 取核心语义段）
   b. 建立 groupPath → 功能模块映射表（如 "前端验证 - 筛选搜索" → [前端UI, 优质模板库]）
   c. 映射表在首次裁剪时构建，同一 session 内复用
3. 根据变更类型扩展影响范围（上下游关联）：
   - 从模块关联图（变更模块 → 上游/下游模块列表）扩展
   - 单模块/前端UI：该模块全量 + 直接上下游
   - 跨模块：所有关联模块 P0 + 直接关联模块全量
   - DB/配置：仅直接关联模块，不扩展上下游
4. 筛选受影响用例（模块命中 + 上下游关联）
5. 保留安全网（P0 用例全量保留，无论是否受影响）
6. 输出裁剪后的用例集 + 裁剪报告
```

### P0 安全网约束

P0 全量保留是硬规则，这意味着裁剪率有下限：当 P0 占比高时（如 22/34=65%），裁剪率上限被压缩。实际裁剪效果取决于非 P0 用例中"未受影响"的比例。这是预期行为——安全网优先于裁剪效率。

### 裁剪报告模板

```
回归裁剪报告：
- 变更范围: {模块列表}
- 原始用例: {total} 条
- 裁剪后: {selected} 条 (裁剪率 {rate}%)
- 安全网保留: {p0_count} 条 P0 用例
- 裁剪明细:
  - {模块A}: {before} → {after} 条 (命中变更)
  - {模块B}: {before} → 0 条 (未受影响，跳过)
```

### 与其他机制的关系

- 与 Hybrid 路由协同：Pipeline 模式天然跳过裁剪（已是最小集），Standard/Loop 模式应用裁剪
- 与规则零g 互补：裁剪后用例数减少，质量信号的基准值相应调整
- 与 SubAgent 并行执行配合：裁剪后的用例集按模块分组，直接分发到 SubAgent

## 规则零j：缺陷根因自动分类

**对 FAIL 用例自动分类根因类型（环境/数据/脚本/真实Bug），减少人工分拣，加速缺陷处理。**

此规则是"缺陷根因自动分类"的落地。课程核心观点：不是所有 FAIL 都是 Bug，大部分是环境/数据/脚本问题。自动分类让团队聚焦真正的代码缺陷。

### 硬规则

1. **FAIL 用例必须分类后才能提 Bug**：未分类的 FAIL 直接进入 f88-bug-drafter 前，先过本分类。
2. **分类必须有证据**：每个分类判定必须附 DB/API/日志证据，不允许纯推理。
3. **分类结果写入 exec-log**：`rootCauseCategory` 字段，供 qa-trace-reflection 聚合分析。

### 四类根因定义

| 类别 | 代码 | 定义 | 典型信号 | 处理方式 |
|------|------|------|---------|---------|
| 环境问题 | `ENV` | 测试环境本身的问题 | 页面 502/DB 连接超时/CDP 端口冲突/SharedArrayBuffer 报错/预发 Nginx 未配置 | 记录环境问题，不提 Bug，通知运维 |
| 数据问题 | `DATA` | 测试数据不满足预期 | 造数失败/数据被清理/数据状态不对/前置数据缺失/批次号不存在 | 走自愈造数或补数，不提 Bug |
| 脚本问题 | `SCRIPT` | 测试脚本本身的缺陷 | 定位器失效/断言条件过时/超时设置不合理/API 参数格式变更 | 修复脚本后重跑，不提 Bug |
| 真实 Bug | `BUG` | 被测代码的功能缺陷 | 接口返回错误/页面展示异常/数据流转断裂/业务规则不符合 PRD | 提 Bug 到 AOne |

### 自动分类决策树

```
FAIL 用例
  ├─ 页面/API 不可访问？ → 检查环境健康 → ENV
  ├─ 数据查不到/状态不对？ → 检查造数记录 → DATA
  │   ├─ 有造数记录但失败 → DATA（走自愈重造）
  │   └─ 无造数记录 → DATA（补造数）
  ├─ 定位器/断言失败？ → 检查页面元素是否变更 → SCRIPT
  └─ 以上都不是？ → 有 PRD 对照的明确偏差 → BUG

SKIP/BLOCKED 用例（扩展分支）
  ├─ 含 BLOCKED_ENV / sandbox / 环境过期 → ENV（环境不可用）
  ├─ 含 无法模拟 / 不支持 / 工具限制 → TOOL_LIMITATION（工具能力边界）
  ├─ 含 SKIP-INVALID / PRD无此需求 → INVALID_CASE（用例设计缺陷，非代码问题）
  ├─ 含 SKIP-DB已验证 / 数据条件不满足 → DATA（数据条件不满足）
  └─ 其他 SKIP → 需人工判定（记录到 exec-log 待复盘）
```

### 六类根因完整定义

在基础四类之上，验证发现需新增两类：

| 类别 | 代码 | 定义 | 典型信号 | 处理方式 |
|------|------|------|---------|---------|
| 环境问题 | `ENV` | 测试环境本身的问题 | 页面 502/DB 连接超时/CDP 端口冲突/SharedArrayBuffer 报错/sandbox 过期 | 记录环境问题，不提 Bug，通知运维 |
| 数据问题 | `DATA` | 测试数据不满足预期 | 造数失败/数据被清理/数据状态不对/前置数据缺失/批次号不存在 | 走自愈造数或补数，不提 Bug |
| 脚本问题 | `SCRIPT` | 测试脚本本身的缺陷 | 定位器失效/断言条件过时/超时设置不合理/API 参数格式变更 | 修复脚本后重跑，不提 Bug |
| 真实 Bug | `BUG` | 被测代码的功能缺陷 | 接口返回错误/页面展示异常/数据流转断裂/业务规则不符合 PRD | 提 Bug 到 AOne |
| 工具限制 | `TOOL_LIMITATION` | 测试工具能力边界导致无法执行 | 浏览器不支持离线模式/无法模拟网络异常/自动化不支持某交互 | 标记为工具限制，评估替代方案或人工执行 |
| 用例缺陷 | `INVALID_CASE` | 用例本身设计有问题 | PRD 无此需求/用例假设的功能不存在/SKIP-INVALID | 标记为用例质量问题，从用例集中移除或修正 |

### 部分 FAIL 的维度级分类

当一个用例包含多个验证维度（如"后端字段✓ + 前端渲染✗"），应按维度分别分类：

```
用例: 审核表字段补充+指标回流
  ├─ 维度1: ODPS 表 schema → PASS（无需分类）
  ├─ 维度2: 后端接口字段 → PASS（无需分类）
  └─ 维度3: 前端 useCount 渲染 → FAIL → BUG
整体分类: BUG（取最严重的维度）
```

### 分类证据要求

| 分类 | 必须提供的证据 |
|------|-------------|
| ENV | 错误截图 / HTTP 状态码 / 连接超时日志 |
| DATA | DB 查询结果（SELECT 返回 0 条或状态不符） |
| SCRIPT | 页面元素对比（预期 vs 实际 DOM） |
| BUG | PRD 原文 + 实际行为截图/DB 记录 |

### 输出格式

```json
{
  "caseId": "E2E-007",
  "status": "FAIL",
  "rootCauseCategory": "DATA",
  "rootCauseDetail": "造数批次 BT_7819 的 workflow_record_log 中 approve 节点状态为 INIT，非预期的 COMPLETED",
  "evidence": "SELECT status FROM workflow_record_log WHERE batch_id='BT_7819' AND node_type='approve' → 返回 INIT",
  "suggestedAction": "走自愈路径：重新触发 approve 节点",
  "isBug": false
}
```

### 与其他机制的关系

- 与 f88-bug-drafter 协同：本规则先分类，只有 `BUG` 类才进入 bug-drafter 生成草稿
- 与 qa-trace-reflection 协同：分类结果聚合后，发现某类根因占比异常高时产出改进提案
- 与 learned-solutions.jsonl 协同：`ENV`/`DATA`/`SCRIPT` 类的解决方案沉淀为 learned-solutions，下次同类问题直接匹配
- 与规则零g 协同：通过率质量信号按分类拆解，区分"真实通过率"（排除 ENV/DATA/SCRIPT 后）和"表面通过率"

## 规则一：造数失败七步诊断

用例需要测试数据但"数据0条/环境无数据"时，**禁止直接标 SKIP/BLOCKED**，必须走完七步。核心理念：**先分析后动手，先探查后创建，先验证后使用**。

### Step 0：查询已知失败方案（Rejected-Edit Buffer）

进入七步诊断前，**先查已知失败方案库**，避免重复尝试已被证伪的路径。这是 SkillOpt "Rejected-Edit Buffer"机制的落地——被拒绝的更新不浪费，后续优化器直接跳过。

**执行**：
```bash
# 读取已知失败方案（按 times_tried 降序，取前 20 条）
cat ~/.qoderwork/skills/qa-self-healing/references/rejected-approaches.jsonl | python3 -c "
import sys, json
entries = [json.loads(l) for l in sys.stdin if l.strip()]
entries.sort(key=lambda e: e.get('times_tried', 0), reverse=True)
for e in entries[:20]:
    print(f\"[{e.get('category','')}] {e.get('attempted','')} -> {e.get('reason','')} | 替代: {e.get('alternative','')}\")
"
```

**匹配规则**：将当前问题与返回的条目做语义匹配（不需要精确匹配——关键词重叠即视为命中）。命中后：
- 直接走 `alternative` 路径，**不重复尝试 `attempted` 路径**
- 如果当前问题恰好就是要走 `attempted` 路径 → 立即换路，不浪费时间在已知死路上
- 未命中 → 正常进入 Step 1

**写入规则**：自愈过程中发现新的失败路径时（Step 4 分层执行中某条路径失败），在 Step 6 知识沉淀阶段追加一条到 `rejected-approaches.jsonl`：
```json
{"ts":"<ISO-8601>","skill":"<当前skill>","session":"<chat_id>","attempted":"<尝试的方案>","outcome":"FAIL","reason":"<失败原因>","alternative":"<替代方案或空>","times_tried":1,"last_seen":"<日期>","category":"<DB查询|红线违规|自愈违规|群消息|提测违规|环境故障>","related_gaps":[]}
```

**与其他机制的关系**：
- 本步骤是**只读查询**，不修改任何文件，开销极低
- 与 capability-registry.md 互补：capability-registry 记录"什么能用"（正向），本文件记录"什么不能用"（负向）
- qa-gap-guardian Stage 1 也会追加写入本文件（gap 判定时同步）

**Step 0b: rejected-approaches 有效期校验（新增）**：
查询 rejected-approaches.jsonl 时，逐条检查 `valid_until` 字段：
- 当前日期 > valid_until → 标注 `[EXPIRED]`，降权处理（不阻止尝试该路径，因为过期记录可能已不再适用）
- `superseded_by` 非空 → 标注 `[SUPERSEDED by {superseded_by}]`，优先使用替代方案
- 仅 `valid_until` 未过期且 `superseded_by` 为空的记录才作为强约束（阻止尝试该路径）

### Step 0a：聚类路由快速匹配（反哺闭环）

查完已知失败方案后，**再查已知成功模式库**——聚类脚本从历史失败中提炼的高频模式及其推荐修复路径。这是 `f88-clustering-service` → `qa-self-healing` 的反哺闭环。

**执行**：
```bash
# 将当前错误文本传入匹配器
python3 ~/.qoderwork/scripts/match_routing_rule.py --error "<当前错误文本摘要>"
```

**匹配结果解读**：
- `matches` 非空 → 命中已知聚类模式，`recommended_action` 是历史高频修复路径
  - `confidence ≥ 0.7` → **直接走 recommended_action**，跳过 Step 1-4，直接到 Step 5 后置验证
  - `confidence < 0.7` → 作为参考线索，仍走 Step 1 完整诊断，但在诊断中优先尝试 recommended_action
- `matches` 为空 → 未命中已知模式，正常进入 Step 1 七步诊断

**策略违规拦截**：匹配器自动过滤 `self_heal_eligible=false` 的规则（红线违规、群消息等策略问题）。如果错误文本命中策略违规类簇，匹配器返回空，Agent 不应尝试自愈，而应标记为 `[POLICY]` 并记录到 exec-log 待人工审查。

**与其他步骤的关系**：
- Step 0 查"什么不能做"（rejected-approaches），Step 0a 查"什么能做"（聚类路由），一负一正互补
- Step 0a 命中后跳到 Step 5 后置验证，验证失败则回退到 Step 1 走完整诊断
- 聚类规则文件路径：`~/.qoderwork/qa-analysis/suggested_routing_rules.json`，由 `analyze_failure_patterns.py` 生成
- 规则文件不存在或为空 → 跳过 Step 0a，正常进入 Step 1（不阻塞）

### Step 1：数据依赖分解

不要上来就造，先搞清楚"到底需要什么数据"。把目标数据拆解为实体依赖树：

1. **识别目标实体**：用例需要哪张表/哪个接口的哪条记录？精确到字段级别——哪些字段是用例断言依赖的（必填），哪些只是附带存在的（可填充默认值）。
2. **拆解上游依赖**：这个实体依赖哪些前置实体？（例：审核任务 → 依赖批次 → 依赖链路 → 依赖商品；模板包 → 依赖图组 → 依赖类目）
3. **区分数据层级**：
   - **配置型数据**：枚举值、Diamond 配置、开关——通常已存在，只需确认值是否正确
   - **基础型数据**：商品、卖家、类目——生态中通常有存量，优先复用
   - **业务型数据**：审核任务、批次、素材——需要主动创建，是造数重点
4. **画出依赖链**：`目标数据 ← 中间数据 ← 基础数据`，标注每一跳的生产方式（API / UI / 定时任务 / 上游事件 / DB）。

**输出**：依赖分解表，格式如下：

| 层级 | 实体 | 关键字段 | 生产方式 | 当前状态（待Step2确认） |
|------|------|----------|----------|----------------------|
| 基础 | 商品 item_id | title, image | 存量/生态 | 待查 |
| 中间 | 批次 batch_id | relation_id, status | API触发 | 待创建 |
| 目标 | 审核任务 job_id | job_type, status | API创建 | 待创建 |

### Step 2：环境就绪检查

**核心原则：每次造数都创建全新测试数据，不复用存量数据。** 造数前确认创建路径畅通，避免环境阻塞导致创建失败。

#### 2.1 查造数 Skill 路由表（规则 3b）

是否有现成 Skill 能创建目标数据？有则直接调用，不重新发明。

#### 2.2 查 DAG 上下文

当前用例在链式依赖中时，确认前置用例的产出状态。前置 FAIL 则整串 SKIP，不盲目创建下游数据。

#### 2.3 查历史造数记录

本次会话中是否已创建过同类数据？如有，直接复用 Step 6 沉淀的配方（参数模板），避免重复分析。

**输出**：确认每个实体的创建路径（Skill / API / UI / ...），标注是否有现成配方可直接套用。

### Step 3：造数路径排序

对每个"需创建"的实体，列出所有可行的创建路径并按优先级排序。排序准则：**可控性 > 速度 > 保真度**。

| 优先级 | 造数方式 | 适用场景 | 优势 | 风险 |
|--------|---------|---------|------|------|
| 1（最高） | API 直接调用 | 有明确接口 | 快速、精确、可重复 | 需知道接口地址和参数 |
| 2 | Skill 封装调用 | 路由表有匹配 Skill | 已验证可靠、封装完善 | 覆盖场景有限 |
| 3 | 浏览器自动化（UI） | 有前端入口但 API 未文档化 | 贴近用户真实操作 | 慢、脆弱、SPA 状态问题 |
| 4 | 定时任务触发 | 依赖 ScheduleX/定时生产 | 生产级路径 | 等待时间长、不可控 |
| 5 | 上游事件驱动 | 依赖其他业务动作触发 | 最真实 | 需先造触发事件 |
| 6（最低） | DB 直接插入 | 无应用层校验且红线允许 | 最直接 | ⚠️ 绕过业务逻辑，数据可能不完整 |

**注意**：同一实体可以准备多条路径，高优先级失败立即降级到低优先级，不要死磕一条路。

### Step 4：分层执行

按依赖链 **从底向上** 逐层创建（先基础型 → 再中间型 → 最后目标型），每层内部按 Step3 的优先级执行：

1. **逐层创建**：依赖链最底层先造，确保上层创建时前置数据已就绪。
2. **即时降级**：某条路径失败不要等全部跑完再处理——立即降级到下一条路径。
   - API 返回参数错误 → 检查参数格式/必填项，修正后重试
   - API 返回业务校验失败 → 说明前置数据不满足，回退检查上一层
   - UI 操作失败（元素找不到/弹窗遮挡） → 走自愈规则 H6-H8，或降级到 API
   - 定时任务未触发 → 查 ScheduleX 配置，尝试手动触发或降级到 API 模拟
   - **⚠️ 重试上限（硬约束）**：同一种工具/方式**最多重试 3 次**，3 次仍失败必须切换到其他方式，禁止无限重试同一条路径。降级优先级：**Computer Use（系统级原生事件）> 浏览器自动化 > 视觉 AI 自动化 > API 直调**。页面 UI 测试场景优先使用 UI 交互方式，API 仅作为最终兜底。浏览器自动化遇 React 受控组件不响应 JS 事件注入时，立即切换 Computer Use，不要在同一工具上死循环。
3. **红线检查**：每次写操作前确认是否在红线范围内（F88: staging + DB 只读；YC: seller_id 见 test-accounts.md + staging）。红线外操作暂停确认。
4. **记录执行日志**：每条路径的调用参数、响应结果、耗时，追加到依赖分解表。

### Step 5：后置验证（造完必须验）

数据创建成功后，**禁止直接使用**，必须验证：

1. **结构验证**：目标记录是否存在？必填字段是否非空？字段类型是否正确？
2. **语义验证**：字段值是否符合业务含义？（例：status=1 是否真的表示"使用中"？时间字段是否在合理范围？关联 ID 是否指向有效记录？）
3. **可用性验证**：用例实际要消费的接口/页面，能否正确读到这条数据？（从消费端反查，而不是只从生产端确认）
4. **关联完整性**：如果用例会 JOIN 多张表或调用多个接口，验证关联数据都齐全。

**验证方式优先级**：消费端 API/页面 > DB 直接查询 > 应用日志。

验证不通过 → 回到 Step4 补造缺失字段/关联数据，不要带着脏数据跑用例。

> **harness-runner v2.1 post_verify 三层验证**：后置验证现已支持三种类型——`type: db`（DataSetupVerifier，通过 dms-alibaba CLI 执行 SQL 验证）、`type: ui`（UIVerifier，通过 alijk-agent-browser CLI 做浏览器自动化验证）、`type: code`（CodeVerifier，输出结构/值断言）。三种类型由 PostVerifyDispatcher 统一路由并共享重试机制，造数步骤可按需配置。

### Step 6：知识沉淀

造数成功后，把成功路径记录下来（会话级别），供后续用例复用：

1. **有效造数配方**：记录"数据类型 → 成功路径 → 关键参数 → 前置条件"。
2. **失败路径标记**：记录尝试过但失败的路径和原因，避免后续用例重复踩坑。
3. **路由表补充**：如果发现某类数据反复需要造，但路由表没有对应 Skill，标记为"建议新增路由"。

知识沉淀不是可选项——同一会话内相同类型的数据创建，第二次必须直接走配方，不重新分析。

> **生产问题反哺闭环**：知识沉淀不仅来自造数过程。每日 18:00 日报 cron 自动从生产问题跟进群提取新问题，18:30 反哺执行器将建议分发到 `~/.qoderwork/feedback-loop/inbox/`（patterns/config-checks/test-cases/monitor-dims 四路由），每周日 21:00 周审晋升到生产 skill。测试执行中发现的新失败模式也应写入 feedback-loop inbox，形成"生产问题 → 测试框架 → 预防再发"的闭环。

### Step 6b：自愈规则回归防护（Bench 回归检查点）

知识沉淀写入后、进入 Step 7 之前，执行回归检查确认新规则不导致历史 PASS 用例误判。

**触发条件**：Step 6 产生了新的 learned-solutions 或 rejected-approaches 条目时执行。如果 Step 6 没有新增条目（仅复用已有配方），跳过本步骤。

**执行方式**：

```bash
python3 ~/.qoderwork/scripts/healing-regression-check.py \
  --rule-type <learned|rejected> \
  --rule-file <写入的目标文件路径> \
  --backup-file <写入前的备份文件路径>
```

**判定与分支**：

| 结果 | 含义 | 动作 |
|------|------|------|
| PASS | 新规则不影响历史 PASS 用例 | 继续 Step 7 |
| PASS(with review) | 新规则与某些 PASS 用例有语义重叠 | 写入 `pending-review/` 待人工确认，同时继续 Step 7 |
| BLOCK | 新规则与 PASS 用例的执行路径直接冲突 | 回滚写入（`cp backup → target`），记录到 `rejected-approaches.jsonl`（reason: regression-guard-blocked），继续 Step 7 |

**与 qa-gap-guardian 的协同**：
- gap-guardian T1 修复（Stage 3）后同样执行本检查，`--rule-type patch`
- 检查 BLOCK 时自动回滚 patch，转 T2 人工审核
- 检查快照保存在 `~/.qoderwork/qa-self-healing/regression-snapshots/`，供 qa-trace-reflection 周度分析

**与 qa-trace-reflection 的协同**：
- Step 2 失败轨迹分析时，额外扫描 `regression-snapshots/` 目录
- 统计 BLOCK 频率：如果某类规则反复被 BLOCK，说明该领域的自愈知识积累遇到了认知瓶颈，需要人工介入
- 统计 review 频率：如果某类规则频繁触发 review，说明 pattern 粒度太粗，需要细化

### Step 7：降级 BLOCKED（最后手段）

所有路径都失败才能标 BLOCKED，必须输出完整的诊断报告：

| 字段 | 要求 |
|------|------|
| 已试路径 | 每条路径的具体调用方式 + 失败原因（不是"试了API"，而是"POST /api/xxx 返回 code=PARAM_INVALID, msg=缺少itemId"） |
| 依赖分解 | Step1 的完整依赖树，标注哪一层卡住 |
| 环境探查 | Step2 的查询结果，说明为什么存量不可用 |
| 真难点 | 具体卡点（不是"造不出"，而是"该接口要求 seller_id 有有效合约，但 staging 无可用合约商家"） |
| 影响范围 | 哪些用例因此 BLOCKED |

**禁止用"数据0条/环境无数据/需触发链路"收尾**——这些是现象不是诊断。诊断要回答"为什么造不出"和"卡在哪一层哪一个依赖"。

### BLOCKED 子分类（Step 7 输出必须标注子类型）

BLOCKED 不是单一状态，必须按根因细分为以下四类，供 Stage 3 报告（f88-failure-analysis）和 qa-data-preflight 消费：

| 子分类 | 含义 | 典型场景 | 处理路径 | 是否可自愈 |
|--------|------|---------|---------|-----------|
| `BLOCKED_DATA` | 前置数据不满足 | 模板包 cateId 单一、策略配置缺失、审核任务不存在 | qa-data-preflight Stage 1 造数自愈子链 → 仍失败则本 skill 规则一七步诊断兜底 | 可自愈（有造数 skill 时） |
| `BLOCKED_ENV` | 环境不可用 | 预发宕机、网络不通、DB 连接超时、SPA 崩溃 | 等待环境恢复 / 切换环境 / CDP 恢复 | 半自动（需人工确认环境状态） |
| `BLOCKED_DEP` | 外部依赖缺失 | 算法模型下线、第三方 API 不可用、HSF 服务未发布 | 降级到替代方案 / 等待依赖恢复 / 协调上游 | 视依赖而定 |
| `BLOCKED_LOGIC` | 业务逻辑限制 | 同唯一键冲突、状态流转限制、权限不可绕过 | 人工介入 / 调整用例设计 / 协调开发开白名单 | 不可自愈 |

**判定规则**：
1. 数据不足但有造数 skill → `BLOCKED_DATA`（先走 qa-data-preflight，再走本 skill 规则一）
2. 环境不可用（预发宕机/网络不通）→ `BLOCKED_ENV`
3. 依赖外部系统（算法模型下线/第三方 API 不可用）→ `BLOCKED_DEP`
4. 业务逻辑限制（同唯一键冲突/状态流转限制）→ `BLOCKED_LOGIC`

**根因判定先验证后结论（红线）**：将 BLOCKED/FAIL 归因于"代码未部署"、"功能未开发"、"分支未合并"等前置条件缺失时，**必须先查预发实际部署状态（分支名/版本/发布时间）再下结论**。提测 = 已部署到预发，这是基本前提。禁止在未验证部署状态的情况下将问题归因于"代码未部署"。若确实需要确认分支，自行查代码仓库的部署记录/发布单，不要问用户。**当静态代码搜索无法确认（如工具只能搜默认分支、release 分支路径不匹配等），必须自行升级到预发环境实操验证（跑一遍流程看实际行为），禁止以"代码搜索有盲区"为由停下来反问用户"要不要我去预发验证？"**——验证是义务不是选项，直接去验证，不要问。此规则同样适用于 `BLOCKED_ENV` 和 `BLOCKED_DEP` 的判定——不得仅凭代码分支或静态分析就归类为环境/部署问题。

**与 qa-data-preflight 的协作**：`BLOCKED_DATA` 在测试执行前由 qa-data-preflight Stage 0-1 提前处理（预检→造数→验证），大部分数据缺口在执行前就已消除。如果 Stage 1 造数也失败，或执行中才发现遗漏的数据缺口，则由本 skill 规则一（七步诊断）兜底处理。

### 配套要求

- pytest 脚本每条造数用例头部必须注释标注 `PRD 第X章第Y条` + `依赖: [实体A, 实体B]`，未标注算不合格脚本。
- 造数用例必须在 docstring 中标注 `produces: {字段列表}`，供下游用例消费。
- 每次造数前强制过 Step1-2，禁止跳过分析和探查直接动手。

## 规则二：验证走不通三层降级

当前表/接口拿不到证据时，**禁止直接标 SKIP**，依次走完三层：

1. **换观测源**：同一份业务事实通常有多处落点，至少穷举 3 个替代源再放弃：
   - DB 表列缺 → 查 JSON 字段/关联表
   - SQL 拿不到 → 查应用日志（sunfire/SLS）
   - 日志无 → 抓下游节点入参反推
   - 再无 → 抓网络请求/前端 state
2. **换数据来源**：staging 里"数据0条"= 需要自己造，不是终点。可触发批次/走审核/HSF（红线内）/UI/API 造数。
3. **换验证维度**：端到端跑不通 → 拆单点验证；状态机断 → 分段验证；下游不可观测 → 上游打点看输入；代码静态分析仅作兜底且必须标"未运行时验证"。

**三层全失败才能标 BLOCKED**，报告须写：具体卡点 + 已试路径 + 真难点 + 影响用例。

**自检三问**（触发 SKIP 前必问）：
1. 这份信息业务系统里唯一只有一个落点吗？
2. staging 我能不能自己造？
3. 线上排障我会不会接受同样理由？

**F88 场景降级路由**：F88/i-FASHION 相关失败（造数失败、CDP/DMS 环境故障、模型/URL/卡死等链路异常）先查 [references/f88-degradation-table.md](references/f88-degradation-table.md) 对号入座（D/E/L 形态编号 → 降级动作序列 → 重试上限 → BLOCKED 子类型），表外形态再走本规则三层降级，事后补表。

**授权检查（改进六·新增）**：三层降级决策须检查当前环境授权级别：
- staging 环境：三层降级全自动执行（重试→换路径→标 BLOCKED）
- prod 环境：涉及写操作的降级（如重新造数）必须暂停并请求用户确认，不得自主决定
- 详见 `references/authorization-matrix.md`（qa-testing-workbench 插件）

## 规则 2b：工具/依赖故障先修后降

测试工具本身报错（模块缺失、CLI 未安装、MCP 权限不足、凭证过期等）时，**禁止直接换工具绕行**，必须先尝试修复：

1. **诊断故障类型**：
   - Python 模块缺失（`ModuleNotFoundError: No module named 'pymysql'`）→ `pip install pymysql`
   - Node 依赖缺失 → `npm install <pkg>`
   - CLI 未安装/版本过旧 → 按 skill 文档重装或升级
   - MCP 工具权限不足 → 检查是否有替代 MCP 或需申请权限，记录具体受限工具名
   - 凭证/token 过期 → 重新登录或刷新 token
2. **修复后验证**：跑一个最小可用检查（如 `python -c "import pymysql"` 或一条简单查询），确认工具恢复。
3. **修复失败才降级**：安装失败（网络不通/权限不够/源不可达）→ 走规则二三层降级换观测源，但报告必须标注 `根因=工具故障(具体错误)，修复尝试=xxx，失败原因=xxx`。**修复尝试同样遵守 Step 4 重试上限：同一修复方式最多 3 次，失败即降级换工具。**

**典型反例**：db-query-tool 报缺 pymysql → 直接转浏览器查页面。正确做法：`pip install pymysql` → 验证 import → 继续用 db-query-tool 完成查询。若 pip install 3 次仍失败 → 降级到替代查询工具（如 dms-alibaba CLI）。

## 规则 2c：环境受限类 SKIP 的替代路径

以下"环境限制"不是真正的不可逾越，执行时禁止直接标 SKIP，必须按对应替代路径尝试：

### SPA 状态丢失（resize/导航后数据消失）

| 错误做法 | 替代路径（按优先级） |
|----------|---------------------|
| resize 窗口 → SPA reload → "No data" → SKIP | ① 先 resize 到目标分辨率，再导航进详情页（首次加载即目标尺寸） |
| | ② 用 CSS `zoom` / `transform: scale()` 模拟视觉缩放，不触发 window resize |
| | ③ 用 CDP `Emulation.setDeviceMetricsOverride` 做设备模拟（纯渲染层，不 reload） |
| 浏览器后退 → SPA 状态丢失 → SKIP | ① 用 `history.back()` 前记录当前路由，后退后重新 navigate 到目标路由 |
| | ② 用 CDP `Page.navigate` 直接跳转，不依赖 SPA 内部路由状态 |

### 环境模拟受限（CDN 异常 / 无效资源 / 网络故障）

| 错误做法 | 替代路径（按优先级） |
|----------|---------------------|
| "预发无法 mock CDN 异常" → SKIP | ① CDP `Fetch.enable` + `Fetch.failRequest` 拦截特定 URL 返回网络错误 |
| | ② JS 替换 `<img src>` 为无效地址，观察 fallback 表现 |
| | ③ API 造数时传入无效 imgUrl（如接口允许任意 URL） |
| "无法模拟超时/断网" → SKIP | ① CDP `Network.emulateNetworkConditions` 设置离线/慢速 |
| | ② CDP `Fetch.enable` + delay 模拟超时 |

### 弹窗/Modal 交互受限

| 错误做法 | 替代路径（按优先级） |
|----------|---------------------|
| Modal 关闭按钮点不掉 → SKIP | ① navigate 刷新页面（已知可靠关闭方式） |
| | ② CDP `DOM.querySelector` + `Runtime.callFunctionOn` 直接触发关闭回调 |
| | ③ 按 ESC / 点击遮罩层（部分组件支持） |

**原则**：浏览器自动化层面的限制 ≠ 环境限制。CDP 协议能模拟绝大多数异常场景，标 SKIP 前必须确认"是环境真不支持，还是我的自动化手段没穷举"。

## 规则三：SKIP/BLOCKED 前缺失分析

标 SKIP/BLOCKED 前必须先做"缺失分析"，回答三个问题：

1. **缺什么**（精确到具体信息，不是"验证不了"）
2. **在哪里缺**（链路没触发？代码没埋点？环境没部署？表字段没采集？账号没权限？）
3. **能不能补**（能在 staging 自己触发链路/UI 操作/API 造数吗？需申请权限吗？需开发协助吗？）

**每条 SKIP/BLOCKED 必须输出缺失分析表**：

| 缺失项 | 缺失位置 | 是否可补 | 怎么补 |
|--------|----------|----------|--------|

能自己补的直接补、补完再跑；真补不了的才标 BLOCKED 并写清"具体卡点+已试路径+真难点"。

**配套**：不要一看到"表无xx列/数据0条"就收尾，那是观察不是诊断——诊断要回答"为什么缺"和"能否补"。

## 规则四：链式依赖执行

用例之间有依赖关系，**禁止线性扫一遍**：

1. **依赖声明显式化**：每条用例头部必须标 `depends_on: [TC-XXX, TC-YYY]` + `produces: {taskId, sellerId, batchId}` + `consumes: {taskId, ...}`。没标的默认独立，标的按 DAG 排序执行。
2. **上下文传递机制**：前置用例 PASS 后，把 `produces` 的字段写入共享上下文（内存对象或临时文件）；后置用例 `consumes` 直接从上下文读，不再自己造。前置 FAIL 或 SKIP，后置按依赖链整串 SKIP，报告里写"因 TC-XXX FAIL 而 SKIP"，不是"数据不存在"。
3. **分层编排**：先跑独立用例（造数类）→ 再跑单依赖链（审核状态机类）→ 最后跑多依赖汇聚用例（端到端类）。每一层跑完才进下一层，同层内可并行。
4. **失败熔断**：一条用例 FAIL 后，所有直接/间接依赖它的下游用例自动 SKIP 并标记根因，不浪费执行，也不产生"假FAIL"。

**配套**：pytest 脚本用 `pytest-order`/`pytest-dependency` 或 fixture 链式依赖表达 DAG，禁止每条用例都是独立 `def test_xxx():` 函数。

## 规则五：bug 修复后回补

生成 bug 草稿后**不能就此停手**，流程必须闭环：

1. 开发修复 bug 后，自动重跑那批 FAIL 用例。
2. 用新结果覆盖原报告中的 FAIL 条目。
3. 更新报告（原 FAIL → PASS / 仍 FAIL → 升级严重度）。
4. 归档到知识库（按业务域分钉钉空间）。

自愈应该是环，不能只是链。

以下情况必须停下确认，不得自作主张：

- **数据红线冲突**：跨商家/跨环境写操作（YC 红线 seller_id 见 test-accounts.md + staging；F88 红线 staging + DB 只读）

其他情况下，**判断清楚就直接执行，不再问"要不要我去做"**。

## 禁止的偷懒模式

以下写法直接判为"偷懒"，必须改写：

| 禁止写法 | 正确做法 |
|----------|----------|
| "数据0条，功能未产生数据" | 写清已尝试的造数路径 + 具体失败原因 |
| "表无xx列，无法SQL验证" | 穷举 ≥3 个替代观测源（JSON字段/应用日志/下游入参反推） |
| "需触发生产链路" | 先触发再跑用例；触发不了写清具体卡点 |
| BLOCKED 只写表面结论 | 必须写具体卡点 + 已试路径 + 真难点 + 影响用例 |
| 每条用例独立造数 | 按 DAG 链式依赖，前置产出 → 后置消费 |
| 遇阻塞就问"要不要做" | 判断清楚直接执行（红线外除外） |
| 页面上找到已有数据直接用来验证 | 必须先调造数 skill 创建新数据，页面测试=必须先造数，没有例外（见规则零b） |
| 造数触发 BT_A，验证时查 BT_B（数据替换） | 验证数据必须与造数数据为同一份，ID 链必须可追溯（见规则零d）；造的数据找不到 → 走规则零排查原因，禁止搜其他数据替代 |
| "xx工具缺模块/没权限"直接换工具 | 先装依赖/修权限/刷凭证，修复失败才降级，降级须标根因 |
| "SPA reload 后 No data"/"预发无法 mock CDN" → SKIP | 先 resize 再导航 / CDP 设备模拟 / Fetch.failRequest 拦截，穷举替代路径后才可 SKIP |
| SPA 页面直接拼 URL 带参数访问（如 `?previewSource=...`） | 必须先通过菜单导航到页面，再从页面交互触发功能（让页面自身从后端数据构造参数）；直接拼 URL 易命中过期/硬编码地址，且绕过 SPA 路由导致白屏 |
| 遇到错误直接标 BLOCKED，不走过自愈诊断 | 必须先走规则零（根因调查）→ 规则一/二（七步诊断/三层降级），产出诊断记录后才可标 BLOCKED（见规则零c） |

## 已验证场景（2026-07-29 Pipeline 全链路验证）

以下场景已在 5-Stage Test Resilience Pipeline 全链路验证中实际跑通，可作为七步诊断的参考案例。

### 场景 1：空输入导致静默失败（BT_7350 → BT_7352）

**故障现象**：策略 10834 试运行，seed_image_url 等必填字段传空字符串，API 返回 success 但批次 BT_7350 卡死在 PROCESSING，workflow_record_log 0 条记录——系统无报错但数据流已中断。

**七步诊断执行摘要**：

| 步骤 | 执行内容 | 结论 |
|------|---------|------|
| Step 1 依赖分解 | seed_image_url → 模板匹配 → workflow_record_log → 审核任务 | 断裂点在第一跳：空 URL 导致模板匹配无法启动 |
| Step 2 环境探查 | 策略 10834 正常（BT_7340 同策略已成功）、预发环境可用、模板包 id=1930 可用 | 环境无问题，根因在输入数据 |
| Step 3 路径排序 | API 重触发（有效输入）> 浏览器 UI > 复用已有批次 | 选择路径 1：补全输入后 API 重触发 |
| Step 4 分层执行 | 用合法 seed_image_url 重新触发 → BT_7352 | BT_7352 在 11 秒内到达 approve/HANDLING |
| Step 5 后置验证 | 对比 BT_7350（0 条记录/卡死）vs BT_7352（1 条 approve/HANDLING） | 修复验证通过 |
| Step 6 知识沉淀 | 空字符串 API 不校验但 workflow 不推进；无效 seller_id 有通用模板包兜底不会失败 | 已记录 |
| BLOCKED 子分类 | **BLOCKED_DATA**（输入数据不满足） | 可自愈 |

**补充发现——无效 seller_id 不会失败**：尝试 seller_id=9999999999 时，系统自动使用通用模板包兜底，BT_7349 正常通过。说明平台对无效 seller 有容错机制，但对空输入缺乏防御。

**经验沉淀**：
- 空输入（空字符串）是比无效值更危险的故障模式——不会报错，只会静默卡死
- 诊断"批次卡死 PROCESSING 但无 workflow 记录"时，优先检查输入参数的必填字段是否为空
- 修复路径明确：补全有效输入后重触发即可

### 场景 2：生产真实失败分析（BT_7062）

**故障现象**：BT_7062 批次 workflow_record_log 共 11 条记录，状态混合（SUCCESS/FAIL/HANDLING），失败记录 errorMsg 显示"图文上传节点，图片列表为空"。

**诊断结论**：上游 gen_img 节点对特定商品生图失败（算法超时或商品特征不适合），但 workflow 仍推进到下游节点，下游发现输入为空后报错。BLOCKED 子分类：**BLOCKED_DEP**（外部算法依赖失败）。
