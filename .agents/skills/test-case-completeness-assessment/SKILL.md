# 测试用例完整性评估技能

## 技能元数据

- **技能名称**: test-case-completeness-assessment
- **技能描述**: 根据需求文档（PRD、系分文档、技术方案等）对测试用例进行完整性评估，生成 HTML 格式的评估报告
- **触发关键词**: 测试用例评估、用例完整性检查、测试覆盖度分析、PRD 对比测试用例
- **版本**: v2.0
- **最后更新**: 2026-04-07

---

## 功能概述

本技能用于评估测试用例对需求文档的覆盖完整性，通过对比需求文档（PRD、系分文档、技术方案等）和测试用例，输出：

1. **需求覆盖度统计**：需求功能点与测试用例的映射关系
2. **覆盖缺口分析**：未覆盖或覆盖不足的功能点
3. **用例质量评估**：用例设计的完整性和规范性
4. **评估报告**：生成美观的 HTML 报告，便于分享和查看

## 核心优势

- ✅ **多源文档支持**：支持钉钉文档、其他在线文档链接、本地 Markdown/Txt 文件
- ✅ **灵活用例格式**：支持 Markdown、XMind、Excel、纯文本等多种用例格式
- ✅ **智能解析能力**：自动识别结构化和非结构化用例，语义分析提取测试意图
- ✅ **可配置输出**：支持自定义报告保存路径，默认使用当前工作区目录
- ✅ **通用性强**：不依赖特定 MCP 工具，适配多种文档获取方式

## 使用场景

- 测试用例评审前自检
- 测试覆盖度量化评估
- 发布前测试完整性确认
- 生成评估报告供团队 review
- 迭代回归测试范围分析

## 前置条件

- 用户提供了需求文档（PRD、系分文档、技术方案等，支持在线链接或本地文件）
- 用户提供了测试用例（支持 Markdown、XMind、Excel、Txt 或直接粘贴）
- 报告保存路径：**默认使用当前工作区下的 `output/` 目录**，也支持用户自定义路径
- **命名规则**：`[需求名称]_[评估日期]_[版本].html`

**命名示例：**
- `自动续期功能_20250407_v1.html`
- `登录改造_20250407_v1.html`

## 工作流程

### Step 1: 获取基础信息

询问用户以下信息：

#### 需求文档来源（可多选，至少提供一个）

- **PRD 文档**：在线链接（钉钉文档/其他文档平台）或本地文件路径（.md/.txt/.docx）
- **系分文档**：在线链接或本地文件路径
- **技术方案**：在线链接或本地文件路径
- **其他需求文档**：如会议纪要、需求变更单等

#### 测试用例来源

- 本地 Markdown 文件（.md）
- 本地 XMind 文件（.xmind）
- 本地 Excel 文件（.xlsx/.xls）
- 本地 Txt 文件（.txt）
- 用户直接粘贴的测试用例内容

#### 其他信息

- **需求名称**：用于报告命名（可从 PRD 标题自动提取或用户指定）
- **输出格式**：简要报告 / 详细报告
- **报告保存路径**（可选）：
  - 默认：当前工作区 `/output/` 目录
  - 自定义：用户指定绝对路径

### Step 2: 获取需求文档内容

#### 2.1 在线文档链接获取

**支持的文档平台：**
- 钉钉文档（alidocs.dingtalk.com）
- 语雀（yuque.com）
- 飞书文档（feishu.cn）
- 腾讯文档（docs.qq.com）
- 其他公开可访问的文档链接

**获取方式：**
- 优先使用 `read_url` 工具读取网页内容
- 如需要登录或动态渲染，使用 `use_browser(namespace="bootstrap", action="openTab")` 打开并提取内容

#### 2.2 本地文件路径获取

**支持的文件格式：**
- Markdown（.md）
- 纯文本（.txt）
- Word 文档（.docx）- 使用 `parse_file` 工具解析

**获取方式：**
- Markdown/Txt：使用 `read_file` 工具读取
- Word/Excel：使用 `parse_file` 工具解析

#### 2.3 文档内容合并

将所有获取的需求文档内容合并，形成完整的需求基线：

- 以 PRD 为主文档，提取业务功能点
- 以系分为补充，提取技术实现细节和约束
- 以技术方案为参考，提取架构设计和接口定义

**合并优先级：**

| 信息类型 | 主要来源 | 补充来源 |
|---------|---------|---------|
| 业务功能 | PRD | 系分 |
| 技术实现 | 系分 | 技术方案 |
| 接口定义 | 系分/技术方案 | PRD |
| 数据模型 | 系分 | 技术方案 |
| 异常处理 | 系分 | PRD |
| 性能要求 | 技术方案 | PRD |

### Step 3: 获取测试用例内容

#### 方式 A：本地 Markdown/Txt 文件

使用 `read_file` 工具读取

#### 方式 B：本地 XMind 文件

**XMind 文件解析流程：**
1. **读取 XMind 文件**
   - XMind 文件是 ZIP 格式的压缩包
   - 使用 `execute_shell` 命令解压到临时目录
   - 提取 `content.xml` 文件内容

2. **解析 content.xml**
   - 使用 XML 解析库提取思维导图的层级结构和节点文本
   - 保持原有的父子关系

3. **转换为文本结构**
   - 将思维导图节点转换为层级列表
   - 提取每个节点的文本内容和备注

**XMind 内容提取规则：**

| XMind 元素 | 提取内容 | 用途 |
|----------|---------|-----|
| 根主题 | 需求/模块名称 | 作为顶层分类 |
| 子主题 | 功能点/用例标题 | 作为测试意图 |
| 备注 | 详细描述 | 作为操作步骤/预期结果 |
| 标签 | 优先级标记 | 作为 P0/P1/P2标识 |

#### 方式 C：本地 Excel 文件

使用 `parse_file` 工具解析 Excel 文件，提取测试用例表格数据

#### 方式 D：用户直接输入

直接使用用户粘贴的内容

### Step 4: 解析需求功能点

从合并后的需求文档中提取以下信息：

#### 功能模块识别
- 根据 PRD 的章节结构识别功能模块
- 提取每个模块的核心功能点
- 记录功能点的优先级（如有标注）

#### 需求类型分类

| 需求类型 | 识别特征 | 测试重点 |
|---------|---------|---------|
| 新增功能 | "新增"、"新增功能"、"新特性" | 全量测试 |
| 功能优化 | "优化"、"改进"、"提升" | 回归 + 新逻辑 |
| Bug 修复 | "修复"、"解决"、"Bugfix" | 验证修复 + 回归 |
| 配置变更 | "配置"、"开关"、"参数" | 配置验证 |

#### 关键要素提取
- 业务规则（如：权限校验规则、状态流转规则）
- 输入输出（接口参数、返回值）
- 异常场景（错误码、异常处理）
- 边界条件（数值范围、长度限制）
- 性能指标（响应时间、并发量等）

### Step 5: 解析测试用例

从测试用例内容中智能提取信息，支持结构化或非结构化用例：

#### 5.1 用例格式识别

系统会自动识别用例的组织形式：

| 用例格式 | 识别特征 | 处理方式 |
|---------|---------|---------|
| **标准格式** | 有明确的用例编号、标题、前置条件、操作步骤、预期结果 | 按字段提取 |
| **列表格式** | 用 `-`、`1.` 等列表符号组织的用例 | 智能解析列表层级 |
| **段落格式** | 纯文本段落描述，无明确结构 | 语义分析提取测试意图 |
| **表格格式** | Markdown 表格或类表格结构 | 按行列解析 |
| **XMind 格式** | 思维导图结构（从.xmind 文件解析） | 提取层级节点和备注 |
| **Excel 格式** | 表格数据（从.xlsx/.xls 文件解析） | 按列映射字段 |

#### 5.2 智能解析策略

对于非结构化用例，采用以下策略提取信息：

**关键词识别：**
- 用例标识：查找 "测试"、"验证"、"检查"、"确认" 等关键词开头的句子
- 步骤标识：查找 "步骤"、"操作"、"输入"、"点击" 等动作词
- 结果标识：查找 "结果"、"预期"、"应该"、"显示" 等结果描述词
- 优先级标识：查找 "P0"、"P1"、"P2"、"高优先级"、"核心" 等标注

**语义分析：**
- 识别测试意图（验证什么功能）
- 识别测试数据（输入值、参数）
- 识别验证点（检查什么结果）
- 识别测试类型（正向/异常/边界）

**用例分组：**
- 根据内容相似度自动归类
- 按功能模块组织用例
- 识别场景类型（正向/异常/边界）

#### 5.3 提取内容

**基础信息：**
- 用例数量统计
- 功能模块分布（自动推断）
- 场景类型分布（正向/异常/边界）

**测试意图：**
- 每个用例要验证的功能点
- 测试数据/输入条件
- 预期结果/验证标准

**覆盖场景识别：**
- 正向场景（正常流程、主路径）
- 异常场景（错误输入、异常流程、权限不足）
- 边界场景（极限值、空值、最大值、最小值）
- 并发场景（多用户、多设备、重复操作）

### Step 6: 覆盖度对比分析

建立 PRD 功能点与测试用例的映射矩阵：

#### 覆盖度评估标准

| 覆盖等级 | 判定标准 | 说明 |
|---------|---------|-----|
| 完全覆盖 | 每个功能点都有对应测试用例，且场景完整 | ✅ 优秀 |
| 部分覆盖 | 功能点有测试用例，但缺少某些场景 | ⚠️ 需补充 |
| 未覆盖 | 功能点完全没有对应测试用例 | ❌ 需新增 |

#### 场景完整性检查

对于每个功能点，检查是否覆盖以下场景：
- [ ] 正向主流程
- [ ] 异常分支（参数错误、权限不足等）
- [ ] 边界条件（最大值、最小值、空值等）
- [ ] 状态流转（如适用）
- [ ] 并发场景（如适用）

#### 覆盖度计算方式

- 整体覆盖度 = 已覆盖功能点数 / 总功能点数 × 100%
- 完全覆盖的功能点按 100% 计算
- 部分覆盖的功能点按 50% 计算
- 未覆盖的功能点按 0% 计算

### Step 7: 用例质量评估

#### 7.1 规范性检查

**结构化用例检查项：**
- 用例编号是否规范
- 标题是否清晰描述测试意图
- 前置条件是否完整
- 操作步骤是否可执行
- 预期结果是否明确可验证

**非结构化用例检查项：**
- 是否能识别出明确的测试意图
- 是否包含可执行的验证点
- 描述是否足够清晰（非模糊）

#### 7.2 完整性检查

| 检查项 | 结构化用例 | 非结构化用例 |
|-------|-----------|-------------|
| 前置条件 | 是否有明确的前置条件字段 | 是否隐含描述了前置条件 |
| 操作步骤 | 是否有明确的步骤描述 | 是否能提取出操作动作 |
| 预期结果 | 是否有明确的结果字段 | 是否能识别验证标准 |
| 优先级 | 是否有 P0/P1/P2标注 | 是否有"核心"、"重要"等暗示 |

#### 7.3 可测试性检查

- 操作步骤是否具体可执行
- 预期结果是否可验证
- 是否存在模糊描述（如"正常显示"、"功能正常"等）

#### 7.4 非结构化用例特殊评估

对于非结构化用例，重点评估：

**可识别性：**
- 能否从文本中识别出独立的测试点
- 测试意图是否清晰

**完整性风险：**
- 缺少明确的预期结果
- 缺少前置条件说明
- 步骤描述不完整

**改进建议：**
- 建议转换为标准用例格式
- 补充缺失的字段
- 明确验证标准

### Step 8: 生成评估报告

报告生成 **HTML 格式**，具有以下特点：
- 美观的样式设计，支持表格、颜色标识
- 可直接用浏览器打开查看
- 便于通过邮件、钉钉等方式分享给团队成员
- 支持打印和导出 PDF

#### HTML 报告结构

```html
<!DOCTYPE html>
<html>
<head>
    <title>测试用例完整性评估报告</title>
    <style>
        /* 现代化样式设计 */
        body { font-family: -apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, ... }
        .header { background: linear-gradient(...); color: white; }
        .section { margin: 20px 0; }
        table { border-collapse: collapse; width: 100%; }
        th, td { border: 1px solid #ddd; padding: 12px; }
        .coverage-full { color: #388e3c; font-weight: bold; }
        .coverage-partial { color: #f57c00; }
        .coverage-none { color: #d32f2f; font-weight: bold; }
    </style>
</head>
<body>
    <!-- 报告内容 -->
</body>
</html>
```

#### 报告包含模块

1. **页头**：标题、PRD 来源、评估时间、评估人
2. **概览卡片**：
   - PRD 功能点总数
   - 测试用例总数
   - 功能点覆盖数
   - 整体覆盖度百分比
3. **覆盖度矩阵**：
   - 功能模块列表
   - 每个模块的功能点
   - 对应的测试用例
   - 覆盖状态（完全/部分/未覆盖）
4. **缺口分析**：
   - 未覆盖功能点列表
   - 部分覆盖功能点及缺失场景
5. **用例质量评估**：
   - 规范性评分
   - 完整性评分
   - 可测试性评分
6. **改进建议**：
   - 需补充的测试用例
   - 需完善的用例
   - 测试重点推荐
7. **总结**：评估结论和发布建议

#### 质量评估标准

- **优秀**：覆盖度 >= 90%，用例质量高
- **良好**：覆盖度 70%-89%，用例质量良好
- **一般**：覆盖度 50%-69%，需要补充
- **不足**：覆盖度 < 50%，需要大幅补充

## 注意事项

### 文档格式要求

- 需求文档支持：Markdown（.md）、Txt（.txt）、Word（.docx）、在线文档链接
- 测试用例支持：Markdown（.md）、XMind（.xmind）、Excel（.xlsx/.xls）、Txt（.txt）
- **支持多文档合并**：可同时提供 PRD、系分、技术方案等多个文档，系统会自动合并分析
- **支持非结构化用例**：即使是用例没有标准格式，系统也会智能解析
- **支持 XMind 思维导图**：可直接读取.xmind 文件，提取思维导图结构作为测试用例

### 路径处理

- **默认保存路径**：当前工作区 `/output/` 目录
- **自定义路径**：用户可指定任意有写入权限的路径
- **路径不存在时**：自动创建目录

### 覆盖度计算方式

- 整体覆盖度 = 已覆盖功能点数 / 总功能点数 × 100%
- 完全覆盖的功能点按 100% 计算
- 部分覆盖的功能点按 50% 计算
- 未覆盖的功能点按 0% 计算

- 良好：覆盖度 70%-89%，用例质量良好

## 错误处理

### 常见问题及处理策略

1. **文档链接无法访问**
   - 尝试使用 `use_browser` 打开并提取内容
   - 提示用户提供本地文件副本

2. **文件格式不支持**
   - 明确告知用户支持的格式列表
   - 建议转换为支持的格式

3. **XMind 解析失败**
   - 检查文件是否损坏
   - 尝试手动解压并提取 content.xml
   - 建议用户导出为 Markdown 格式

4. **路径权限问题**
   - 检查目标路径是否有写入权限
   - 建议使用默认工作区路径
   - 提示用户调整安全设置

5. **需求文档内容过少**
   - 提示用户补充更多需求细节
   - 建议提供系分文档或技术方案作为补充
