# 原创保护-测试报告踩坑

撰写测试报告时易踩的坑。报告产出前 checklist。

## 内容质量类

### 1. 风险点必须具体展开
- 已沉淀USER：用户偏好详细具体的风险点解释，不喜欢高层级概括
- 错误示例："结算模块存在金额计算风险"
- 正确示例："SettlementCalcJob 在 70% 阈值边界（69.999%-70.001%）使用浮点比较，存在精度误差导致提前/延迟触发结算的风险，影响补贴档位与官费扣减"

### 2. 区分"已发现"vs"可能存在"
- 已沉淀SOUL：区分"确定的事实"和"我的判断"
- 用 `已发现：xxx` / `推测：xxx` / `待验证：xxx` 三类标签

### 3. 数据要有来源
- 缺陷数据：附 a1 链接
- DB 数据：附查询 SQL + 查询时间
- API 数据：附 traceId

### 4. 不堆砌通用风险
- 错误：照搬"所有平台都可能有数据一致性问题"
- 正确：聚焦本迭代/本模块的实际风险

---

## 格式类

### 5. 标题与文件命名
- 文件命名：`原创保护-{报告类型}-{时间}.md`（如 原创保护-日报-20260618.md）
- 报告内标题与文件名一致

### 6. 表格使用
- 缺陷分布、覆盖率必须用表格
- 不要用嵌套列表展示数据

### 7. 链接形式
- 钉钉文档：`alidocs.dingtalk.com/i/spaces/...` 全 URL
- a1 缺陷：`a1.alibaba-inc.com/v3/projects/{pid}/work-items/{wid}`
- DMS：附查询条件而非结果链接（链接会过期）

## AOne 集成类（参考 F88 经验）

### 8. KindEditor 内容设值
- 已沉淀MEMORY：内容设 `iframe.body.innerHTML`，标题 id=dailyReportName
- 不能直接 `document.querySelector('.editor').innerHTML = ...`
- 必须先 focus iframe 再 setHtml

### 9. 字段填充规则
- 开发=参与者-测试-产品（去重仅名字）
- 用例评审人=测试人员
- bug 空间=缺陷页链接

### 10. 保存按钮可见性
- 已沉淀MEMORY：保存按钮可能不可见，先 scrollIntoView 再点击
- 成功标志：URL 由 #finalReport/new 变为 #finalReport/detail/{id}
- 导航离开会重置表单（提示用户保存后再切页）

## 数据准确性类

### 11. 通过率计算口径
- 通过率 = passed / (executed - skipped)
- 跳过用例不计入分母（避免 skipped 多导致通过率虚高）

### 12. 覆盖率计算口径
- 覆盖率 = executed / total
- 包含 skipped（skipped 也算执行过）

### 13. 跨迭代对比
- 必须用相同模块清单（参考 `模块清单.md`）
- 不能因模块拆分导致数字膨胀/缩水

## 节奏类

### 14. 日报应聚焦今日
- 不重复上一天已沉淀的内容
- 重点：今日新发现 + 今日变化 + 明日计划

### 15. 迭代报告应回顾计划
- 与迭代初定义的测试范围对齐
- 漏测项必须明确说明（环境/资源/优先级原因）

### 16. 月报应有趋势
- 至少展示 3 个月的环比数据
- 关键指标：缺陷率、通过率、回归覆盖率、生产 BUG 数

## 快审扣减验证专项 [需求#83368125, 2026-06-24]

### 17. 扣减证据用settle_order而非trade_record
- `yc_service_trade_record` 无 DEDUCT 类型，只有 BUY/REFUND/INCOME
- 验证扣减应查 `yc_right_settle_order`（TO_DO → DONE）
- `remainRightCount` 由服务市场侧计算，当已购次数消耗完时显示0，不能作为扣减证据

### 18. 结算单处理延迟约50分钟
- settle_order 从 TO_DO 到 DONE 约需50分钟（后台定时任务）
- 报告中需注明创建时间和处理完成时间，不要立即断言 TO_DO 为失败

### 19. HSF模拟调用不等于真实审核
- `TopRightHsfService.syncAuditOperation` 仅写入 op_record，不推进 DB 状态
- 报告中标注"HSF为模拟调用"，不要写成"快审已通过"
- 真实审核须钉钉@卢彩xq操作

### 20. 新旧代码驳回行为差异需在报告中对比
- 旧代码: 提交时扣减 → 驳回时 settle CANCEL 返还
- 新代码: 提交时不扣减 → 驳回时无 settle，无需返还
- 报告中应用表格对比两种代码的 settle_order 状态
